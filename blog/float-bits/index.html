为什么 0.1 存不进计算机？我做了个「拆开看」的工具，10 分钟搞懂 FP8

Tim Chan 发布于 2026 年 8 月 26 日

0.1 + 0.2 为什么不等于 0.3？把浮点数拆成三段二进制格子，做了五个可交互的插画，从 IEEE 754 一路看到 FP8。

在 Python 里敲一句：

>>> 0.1 + 0.2
0.30000000000000004

每个写过代码的人都见过这个结果。它不是 bug，也不是你的电脑坏了——是 0.1 这个数，从一开始就没被完整地存进计算机。

再看看最近大模型圈的新闻：GPT 说自己用了 FP8，DeepSeek V3.1 的技术报告里蹦出一个 UE8M0，国产芯片板块应声大涨……

看起来八竿子打不着的两件事，其实是同一件事：

计算机只有 0 和 1，它到底是怎么存一个小数的？

为了把这件事彻底讲透，我给自己的网站做了一个交互工具：把一个数字拆成一个个可以点击的二进制格子，让你亲手翻转每一位，实时看到数字如何变化。这篇文章就沿着工具的节奏走——每讲一个概念，你就上手玩一步，看完就能学会。

工具地址（手机可开，纯本地计算，不需要注册登录，数据不出浏览器）：

https://chenyuqing.github.io/tools/float-bits/

一句话总结

浮点数 = 用科学计数法存数字：符号位管正负，指数位管小数点在哪，尾数位管有多准。

记住这一句，下面的所有内容都是它的展开。

第 1 站：整数很好办，就是 8 个格子

先从最简单的开始。计算机内存就像一排小格子，每个格子只能放 0 或 1。

要存一个整数？直接转成二进制就行。用 8 个格子存的整数，就叫 int8。

比如 100，转成二进制是 01100100，正好 8 位。

带负数怎么办？业界约定用「补码」：最高位当符号用。于是 int8 能表示的范围是 -128 ~ 127。

🔧 动手环节 ①：感受一下 8 个格子的贫穷

  1. 打开工具，格式选 INT8
  2. 输入 100 → 看到 8 个格子亮出 01100100
  3. 输入 200 → 工具提示「超出范围，已饱和到边界」，数字被摁回 127——8 个格子就这么大，装不下就是装不下
  4. 再切到 INT2，输入 3 → 只有两个格子的世界里，能表示的整数只有 -2、-1、0、1，3 也被饱和成 1

记住这个感觉：格子不够，要么截断，要么爆掉。 下面所有格式的斗争，都是围绕这一点展开的。

第 2 站：小数来了，最朴素的方案叫「定点数」

那小数呢？也很直觉：转成二进制，中间点上个小数点，完事。

但有个问题——这 8 个格子里，可没有地方放那个「点」。

最简单的办法：大家说好了，点固定在某一位。比如前 4 位表示整数部分，后 4 位表示小数部分。小数点位置固定不动，所以叫定点数（fixed-point）。

听起来很完美？可惜定点数有个致命问题：不够灵活。

还是那 8 个格子：

  • 小数点靠左 → 小数部分位多，精度很高，但最大只能表示几十，范围太小
  • 小数点靠右 → 整数部分位多，范围很大，但小数部分只剩一两位，精度太差

你可能不服：一共就这么大点空间，肯定要做取舍啊，怎么还能既要又要？

哎，还真就可以既要又要。

第 3 站：既要又要的答案，小学就学过——科学计数法

回忆一下十进制的科学计数法：

12300 = 1.23 × 10⁴
         └┬┘    └┬┘
        尾数    指数

用三位存尾数（1.23），一位存指数（4），原来五位的数就被压缩成了四份信息。

关键在于指数是可以调节的天平：

  • 把指数调小，比如 1.23 × 10⁻⁹ → 能表示 0.00000000123，精度高到小数点后九位
  • 把指数调大，比如 1.23 × 10⁹ → 能表示十几亿，范围大到天边

尾数负责「多准」，指数负责「多大」。指数本质上，就是让小数点来回浮动——区别于位置固定的定点数，这种方式就叫浮点数（floating-point）。

当然，天上不会掉馅饼。它「既要又要」的代价是：

牺牲大数的绝对精度，保住相对精度。

什么意思？对于一亿这个数来说，「一亿零点零零零零一」和「一亿」相比，差距完全可以忽略不计。所以很大的数并不需要绝对精度很高——两个相邻大数之间的间隔，本来就可以很大，就像高速公路上相邻里程碑隔了一公里，你不能说它「不准」，因为在这个尺度上，相对误差小到毫无意义。

这个直觉非常重要，第 6 站我们会亲手验证它。

第 4 站：二进制版的三段式——红、绿、蓝三个色块

回到二进制。二进制的科学计数法长这样：

(−1)^s × 1.mmm… × 2^E

翻译成人话，一个浮点数由三段拼成：

部分 干什么的 工具里的颜色
符号位 s（sign） 正数还是负数 🔴 红
指数位 E（exponent） 小数点浮到哪里 🟢 绿
尾数位 m（mantissa） 有效数字有多准 🔵 蓝

这就是工具页面上那一排彩色格子的含义——每种浮点格式，本质上只是这三段颜色的位数分配方案不同而已。

两个容易困惑的细节，工具都会直接展示给你：

细节一：隐含的首位 1。 二进制科学计数法规定整数部分永远是 1，既然永远是 1，就不用浪费格子去存它。所以尾数格子全是 0 时，代表的其实是 1.0，而不是 0。

细节二：负指数怎么存？ 指数经常是负的（比如 0.1 ≈ 1.6 × 2⁻⁴），但格子里没法存负号。办法是加一个固定偏移量（bias）：实际指数 = 字段值 − 偏置。比如 FP8·E4M3 的偏置是 7，字段存 0111（十进制 3），实际指数就是 3 − 7 = −4。

🔧 动手环节 ②：亲手掰弯每一个比特

  1. 格式选 FP8·E4M3（1 红格 + 4 绿格 + 3 蓝格，正好 8 个），输入 0.1
  2. 注意看「实际存储的数」：0.1015625——这是这 8 个格子真正能表达的最接近 0.1 的数
  3. 看公式行：「实际指数 = 字段值 − 偏置 7」——细节二就活生生摆在那里
  4. 点击任意一个红色格子，把它翻成 1 → 数字瞬间变成 -0.1015625
  5. 点击任意一个绿色格子 → 数字直接 ×2 或 ÷2，这就是「小数点在浮动」
  6. 点击蓝色格子 → 数字在小范围内微调，这是精度在起作用

玩满一分钟，你对「符号 / 指数 / 尾数」的理解就会超过背十天书。

第 5 站：0.1 的真相——一个惯犯

现在可以正面回答开头的问题了。

十进制的 0.1 转成二进制是 0.000110011001100…，0011 无限循环。而格子数量有限，循环必须在某处被掐断——所以 0.1 从进计算机那一刻起，就注定是个近似值。

问题是：它到底被存成了什么？

工具用 BigInt 做精确十进制展开——不是显示截断，而是把这个格子组合真正代表的那个数，一位不差地打印出来。

在 FP32 里输入 0.1，实际存进去的是：

0.100000001490116119384765625

比 0.1 大了一点点。0.2、0.3 同样各有各的偏差。所谓 0.1 + 0.2 ≠ 0.3，就是两个「近似犯」相加之后，误差恰好露出了马脚。

🔧 动手环节 ③：看着 0.1 越来越像 0.1

  1. 点预设按钮 0.1
  2. 依次切换格式，盯着「实际存储的数」的变化： - FP8·E4M3 → 0.1015625（差了 0.0016，很粗糙） - FP16 → 0.10009765625（接近了一些） - FP32 → 0.100000001490116119384765625（非常接近了） - FP64 → 显示「精确」（因为输入先变成了 64 位双精度数）
  3. 拉到底部的对比表：同一个 0.1 在全部 10 种格式下的精确存储值和误差并排躺着，点任意一行还能直接切换主格式

一句话带走：精度不是玄学，是尾数位数的直接后果。

第 6 站：一亿 + 0.00001——大数的贫富差距

还记得第 3 站说的「牺牲绝对精度、保住相对精度」吗？现在亲手验证。

FP32 在「一亿」附近的刻度间隔是多少？算一下：一亿介于 2²⁶ 和 2²⁷ 之间，尾数只有 23 位，所以相邻两个可表示数的间隔是 2²⁶⁻²³ = 2³ = 8。

8！ 也就是说在 FP32 的世界里，一亿附近根本没有「一亿零一」这种数，邻居们手拉手站在 …99999992、100000000、100000008…

这时候往一亿上加 0.00001，就像往太平洋里倒一杯水——四舍五入之后，什么都没发生。

🔧 动手环节 ④：眼睁睁看着 0.00001 凭空消失

  1. 点预设按钮 「一亿+0.00001」
  2. 格式选 FP32 → 看「实际存储的数」：就是 100000000，0.00001 完全消失，误差栏写着 0.00001
  3. 切到 FP64 → 这次保住了（64 位里这个间隔约 0.0000000149，装得下），但依然不是精确值
  4. 再点预设 「极小 1e-9」，选 FP16 → 直接下溢变成 0，工具会提示「太小了，子正常区也装不下」

这就是浮点数的世界观：它不在乎每一米都准，它在乎每一个量级都够得着。

第 7 站：FP8——大模型时代的极限压榨

时间线推到今天。大模型参数以千亿计，显存和带宽按 GB 卖，FP32 太占空间，于是有了 FP16；还不够，就开始对 8 个格子下手——这就是 FP8。

但别忘了第 4 站的结论：浮点格式 = 三段颜色的位数分配方案。8 个格子怎么分给符号、指数、尾数？每一种分法都是一种新格式，本质都是精度和范围的权衡。其中最重要的两种：

格式 分配 性格
FP8·E4M3 1 红 + 4 绿 + 3 蓝 指数少尾数多 → 更准
FP8·E5M2 1 红 + 5 绿 + 2 蓝 指数多尾数少 → 更广

NVIDIA 的 GPU 对这两种格式做了专门的硬件级支持，让 FP8 矩阵运算跑得飞快。

一个有趣的细节：它们连「装不下」时的行为都不一样——

  • E4M3 没有无穷大：超出范围时饱和（saturate）到最大值 ±448，硬生生摁在边界上
  • E5M2 学 IEEE 标准：留了全 1 指数当无穷大，超范围就变成 ∞

🔧 动手环节 ⑤：同一个 1000，两种死法

  1. 选 E4M3，输入 1000 → 提示「溢出：E4M3 最大只能到 ±448，已饱和」
  2. 切到 E5M2，同样输入 1000 → 得到的不是 448，而是 ∞
  3. 分别点预设 「最大值」，对比两种格子的天花板：一个 448，一个 57344

没有谁对谁错，又是那次熟悉的权衡：一个选择体面地撞墙，一个选择体面地爆炸。

第 8 站：UE8M0——把尾数砍光的极端操作

还能更极致吗？能。干脆：

  • 尾数：0 位，砍掉
  • 符号位：也不要，改用无符号
  • 8 个格子全部给指数

这就是 UE8M0——一种只会表示 2 的整数次幂（…0.25、0.5、1、2、4、8…）的浮点格式。

砍成这样还有什么用？用处恰恰在于「砍」：

  • 没有 0 和 1 组成的复杂电路，乘以 2 的幂就是纯粹的位移操作
  • 硬件实现简单到令人发指，速度自然快

所以在不追求精度、只追求速度的场景里，它是完美的配角——比如大模型里的缩放因子（scaling factor）：本身只需要记录「数量级在哪」，不需要精细的有效数字。

这就是 DeepSeek V3.1 发布时提到的那个名词，也是后来让国产芯片概念一夜暴涨的故事主角之一——剥开新闻外壳，内核其实就是「8 个格子全给指数」这么朴素的道理。

🔧 动手环节 ⑥：体验一把「只有 2 的幂」的人生

  1. 格式选 UE8M0 → 你会看到只剩一排绿色的指数格子，红蓝全部消失
  2. 输入 3 → 工具提示这不是 2 的幂，就近吸附到某个纯 2 的幂上
  3. 输入 1024 → 完美命中，因为它本来就是 2¹⁰
  4. 看公式行只剩 2^k 一个因子——这就是「乘法即位移」的全部秘密

第 9 站：全家福——一张表看完 10 种格式

工具里共 10 种格式，正好串起了从入门到大模型前沿的完整谱系：

格式 结构（符/指/尾） 偏置 特征速记 典型岗位
INT2 2 位补码 — 只能表示 -2~1 极限量化实验
INT4 4 位补码 — -8~7，GPTQ/AWQ 量化常见 压缩权重
INT8 8 位补码 — -128~127 传统量化
FP8·E4M3 1+4+3 7 更准，±448 封顶无∞ 大模型前向/权重
FP8·E5M2 1+5+2 15 更广，有∞ 反向传播/梯度
UE8M0 0+8+0 127 只剩 2 的幂 缩放因子（DeepSeek V3.1）
FP16 1+5+10 15 传统半精度 老款混合精度训练
BF16 1+8+7 127 范围≈FP32 的半精度 当今训练主力
FP32 1+8+23 127 单精度，Java 的 float 常规计算
FP64 1+11+52 1023 双精度，Java 的 double 科学计算

特别说一下 BF16 vs FP16 这对冤家：同样是 16 个格子，BF16 把指数位抄成了和 FP32 一样的 8 位——范围一模一样大，绝不上溢下溢，代价是尾数更糙。训练时梯度的大小跨度极其夸张，「装得下」比「算得细」更重要，所以如今 BF16 成了训练场上的主流。这再次印证那句话：没有绝对优势的格式，只有场景分工——有的存权重，有的存梯度，有的存缩放因子。

写在最后

我觉得大模型这些逐位优化的工程尝试，很像早期计算机内存和磁盘都极小的年代——那时的程序员绞尽脑汁压榨性能，代码写得都非常「秀」。后来硬件发达了，我们存个整数都无脑上 int，反正空间管够。

而现在，为了在大模型这块难再突破的性能底座上再多挤一点，工程师们又开始一位一位地锱铢必较。

历史仿佛在打转，但每一次转身都比上一次站得更高。也许多年以后，今天这些精确到单个 bit 的权衡，又会成为一段被人津津乐道的计算机史佳话。
