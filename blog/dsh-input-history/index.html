给 Web 对话框装一个 ↑ 键：我在 DeepSeek Harness 上写「输入历史」插件的完整记录

Tim Chan 发布于 2026 年 8 月 28 日

终端里 ↑ 调出上一条命令是肌肉记忆，Web 对话框里却什么都没有。用纯插件方式补上它：一百来行代码，读穿了半个框架。

需求一句话：在 DSH 的 Web 对话框里，按 ↑ 调出上一条发过的输入，↓ 再走回来——跟终端一样。 代码量：一百来行。为了这一百来行，我读穿了半个框架。

用终端的人都有肌肉记忆：命令打一半，↑ 一下，上一条命令回来了。可当我在 DeepSeek Harness（下称 DSH，一个本地优先的 AI Agent 框架，自带 Web GUI）的对话框里按下 ↑，什么也没发生——光标乖乖上移一行，历史一个字都没有。

这篇文章记录我用纯插件方式给 DSH Web GUI 补上这个肌肉记忆的完整过程：怎么在几十个槽位里找到落脚处、为什么写输入框内容只有一条合法路径、以及一场和端口 3080 的重启拉锯战。

一、先确认：这不是「没开设置」，是「能力不存在」

动手前惯例排查。全局搜 ArrowUp，命中分布在模型选择器、目录浏览器、菜单组件里——全是菜单导航用途。composer（输入框）自己的 onKeyDown 里没有任何历史逻辑。结论和上一篇「删除会话」如出一辙：框架里压根不存在这个能力，不是配置没打开。

那就写插件。DSH 的插件体系我在上一篇里已经摸清：主机端是普通 ESM 模块，浏览器端是挂到 window.__ModuleLoader__ 的工厂闭包，require('react') 解析到宿主共享的那份 React，零构建零依赖。这次的全部战场在浏览器端。

二、在槽位森林里找落脚处：conversation.composer.dock

DSH 的 UI 是一个具名"洞"（slot）组成的系统，对话相关的洞声明在 ui-conversation 的 contract/slots.ts 里，光 composer 周边就有七八个：

  • conversation.composer：接管链，选中就整个替换默认输入框——我要的是增强，不是替换，pass；
  • conversation.composer.bar：默认输入框本体，单占槽，pass；
  • conversation.input.left / .right：工具行里的小控件位，要渲染可见 UI，pass；
  • conversation.composer.dock：composer 卡片下方的一条"环境读数带"，官方统计行就住在这里。列表槽、 additive（纯增量）、session 作用域——正合适。

关键在于：槽位条目是一个 React 组件，而 React 组件可以返回 null。我要的不是显示什么，而是挂载一个"幽灵组件"：不渲染任何 UI，只在 useEffect 里装一个 document 级 capture 阶段 keydown 监听器。

选 dock 还有第二个理由，文档原话：

everything a control needs comes from the framework session kit (sessionId, useSession, useInput, inputActions)

session 作用域的槽位组件自动拿到整套"会话标准件"：useSession 读会话快照、inputActions 写输入框、sessionId 知道当前是哪个会话。一个幽灵组件需要的所有缝，全在这里。

三、写输入框只有一条合法路径：inputActions.setDraft

读完 input/contract.ts 我理解了为什么不能直接操作 DOM。DSH 的输入框背后是一台输入状态机：草稿文本、光标、undo 栈、斜杠命令 chip、粘贴匹配尝试，全部是机器内部状态，且"所有草稿变更都是一次事务"。ComposerKeyboard 那套更完整的键盘接口（undo/redo/pasteBegin/track……）文档写明 InputBar-private, never across a plugin boundary——插件边界之外拿不到。

插件能碰的只有一个公开动词：

export interface InputActions {
  /** Single public draft write path (full next draft; ...) */
  setDraft(text: string): void
  ...
}

这反而是好事：让状态机继续当唯一写者，我调 setDraft，undo 栈、chip 对齐这些内部账本由机器自己记，插件不碰私有字段，卸载后框架毫发无伤。

历史从哪来？同一个标准件里的 useSession。会话快照的 nodes 数组里，kind === 'user' 的节点就是已发送的用户消息，把其中 type === 'text' 的块拼起来、按时间序排好，就是历史列表：

function historyOf(nodes) {
  const out = []
  for (const node of nodes) {
    if (node?.kind !== 'user') continue
    const text = (node.content ?? [])
      .filter(b => b?.type === 'text' && typeof b.text === 'string')
      .map(b => b.text).join('\n').trim()
    if (text) out.push(text)
  }
  return out   //  oldest first
}

注意这里拿到的是已发送的消息，正好就是"历史"的语义——草稿箱里没发出去的内容不算历史，和终端一致。

四、细节魔鬼：一份守卫清单

核心逻辑二十行，守卫占了另外四十行。每一条都对应一个真实会发生的冲突：

1. 只认 composer 的 textarea。 页面里不止一个 textarea，设置页也有。InputBar 的卡片容器上有 data-composer-card 属性（读 InputBar.tsx 找到的），于是判定条件是 target instanceof HTMLTextAreaElement && target.closest('[data-composer-card]')。

2. 斜杠菜单和 @ 引用菜单打开时，方向键是菜单的。 这两个弹层渲染 role="listbox"（读 ui-input-trigger 源码确认），所以按键前先 document.querySelector('[role="listbox"]')，命中就直接放行。忘了这条，↑ 就会在选命令的时候把整个输入框内容换掉——灾难。

3. IME 组词中不拦截。 event.isComposing 为真时放行，中文用户按 ↑ 选候选词的姿势千奇百怪，不能抢。

4. 多行草稿里，↑ 首先是光标上移。 Shift+Enter 能换行，草稿可能是多行的。规则仿照终端系应用的折中：光标在首行（或空输入框）才召回历史，光标在 deeper 的行里保持原生导航；但一旦已经进入召回模式，↑↓ 就持续翻页，不再看光标位置。判定一行就够：target.value.slice(0, target.selectionStart).indexOf('\n') === -1。

5. ↓ 翻过最新一条时，恢复"进历史前正在编辑的内容"。 这是终端手感里最容易被忽略的一条：用户打了半行字，↑ 翻看历史，↓ 回来，那半行字必须还在。所以进入召回的那一刻先 saved = 当前草稿，翻出界时 setDraft(saved)。

6. 任何其他按键退出召回。 printable 键、Enter、Backspace、Escape 一律把召回状态清零——召回出来的内容一旦开始编辑，就是新文本，再按 ↑ 从最新历史重新开始。

7. 换会话要重置。 dock 是 session 作用域，但保险起见还是 useEffect(..., [props.sessionId]) 里把游标归零——别的会话的历史不能串进来。

最后是事件姿态：capture 阶段 + preventDefault() + stopPropagation()。capture 保证我比 composer 自己的 onKeyDown 先拿到按键；两个 prevent/stop 保证被召回接管的那次按键不会同时触发光标移动或别的手势。

召回后还有一个小动作：setDraft 是异步重渲染的，光标位置要在 setTimeout(0) 里设到文末，否则浏览器会把光标丢在随机位置。

五、打包挂载：四个文件的插件

完全复刻我上一个插件的扁平结构，不需要构建工具：

dsh-input-history/
├── package.json        # dsh.client 声明浏览器端入口；dsh.bundle.patch 指配置层
├── cordis.patch.yml    # 往 profile 组合里插一行宿主身份
├── index.js            # 主机端：no-op 锚点（本插件全部行为在浏览器端）
└── client.js           # 幽灵组件 + keydown 监听（手写 bundle，零构建）

client.js 的骨架：

window.__ModuleLoader__.load({
  id: "dsh-input-history",
  factory: (require) => {
    const React = require('react')          // 宿主基线模块表，不打包
    function InputHistory(props) {
      const nodes = props.useSession(s => s.nodes)
      // refs 保存最新值供全局监听器读；browse ref 保存召回游标
      useEffect(() => {
        const onKey = (e) => { /* 第四节的全部守卫 + 翻页逻辑 */ }
        document.addEventListener('keydown', onKey, true)
        return () => document.removeEventListener('keydown', onKey, true)
      }, [])
      return null                            // 不渲染任何东西
    }
    exports.inject = ['slots']
    exports.apply = (ctx) => {
      ctx.slots.inject('conversation.composer.dock', () => ctx.slots.register(
        { name: 'conversation.composer.dock', id: 'input-history', order: 10 },
        InputHistory,
      ))
    }
    return exports
  }
})

挂载到 profile 是两步：package.json 里加 "dsh-input-history": "link:/path/to/plugin" 依赖和 bundles 数组一行，然后 pnpm install。这里连踩两个 pnpm 的坑：

  1. ERR_PNPM_ABORTED_REMOVE_MODULES_DIR_NO_TTY——profile 的 node_modules 要重建，非交互终端不肯确认，加 --config.confirm-modules-purge=false；
  2. 顺手设了 CI=true 想绕过上一个，结果 CI 模式默认 frozen-lockfile，lockfile 里没有新依赖直接报 ERR_PNPM_OUTDATED_LOCKFILE——去掉 CI、改 --no-frozen-lockfile，237ms 装完。

六、重启拉锯战：谁在守着 3080

插件装好，要重启 DSH 才下发新 bundle。然后我发现杀掉 DSH 比写插件难。

进程树是四层套娃：bash start_dsh.sh → pnpm → pnpm（.tools 里那份） → 真正干活的 node --import tsx/esm apps/cli/src/bin.ts web。对着最外层发 SIGTERM，trap 是有的，但整棵树迟迟不退出；发 SIGKILL 杀掉外层，真正的服务器是曾孙进程，端口还守着。第一版"detach 重启脚本"等到 30 秒超时强行拉起新实例，被一句 port 3080 is already in use 打回。

更魔幻的是：因为真正的 DSH 进程就是我的 GUI、我的会话所骑的宿主，杀掉它的那条工具调用自己也会死在半路——两次收到"调用被中断，结果未知"。最后的手术姿势是：一条命令里先 kill -9 真正的 tsx 节点进程，同一命令里立刻 nohup bash start_dsh.sh & + disown 把新实例 detached 拉起；调用本身断了没关系，操作系统层面的交接继续完成。几秒后 GUI 自动重连，会话从磁盘日志恢复，一切如常。

验证不用开浏览器也能做一半：DSH 把每个 client 插件以 /plugins/<包名>/client.js 下发，

curl -s http://127.0.0.1:3080/plugins/dsh-input-history/client.js | grep -c input-history
# 4

200 + 命中，说明组合层已经认了这个插件，浏览器刷新即生效。剩下的一半手感验证（↑↓ 翻页、菜单冲突、IME）交给真实使用——这类交互插件的最终测试永远是你的手指。

七、收获与反思

  1. additive 槽位 + 返回 null 的组件 = 无侵入增强。 框架把"替换"和"追加"分得很清楚；选对槽位，一个不渲染任何东西的组件就能拿到整套会话标准件，安安静静给框架加肌肉记忆。卸载插件，行为立即消失，不留一滴残留。
  2. 公开契约是插件的氧气。 setDraft 作为"唯一公开写路径"不是限制，是保护：插件永远不需要知道 undo 栈和 chip 对齐怎么算。读契约文档（input/contract.ts 里那句 never across a plugin boundary）比读十遍实现更能告诉你边界在哪。
  3. 守卫清单就是产品定义。 ↑ 键这件"小事"的最终形态，是由七条守卫定义的：菜单打开让路、IME 让路、多行光标让路、↓ 出界恢复草稿、换会话重置……每删一条守卫，就是一个真实场景下的事故。小功能的质感全在这些边界里。
  4. 杀不掉的进程树是运维课。 四层套娃、SIGTERM 慢退、曾孙守端口、"杀宿主者宿杀己"——以后给 DSH 做热更新类操作，我会先画进程树再动手。
  5. 肌肉记忆是最诚实的需求。 没有一个用户会写 RFC 要求 ↑ 键；但每个从终端来的人按下 ↑ 落空的那一下，都在扣分。给 Web GUI 补终端手感，是本地优先工具值得做的细活。
