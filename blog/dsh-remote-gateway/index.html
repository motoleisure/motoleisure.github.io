DSH 远程控制实战：无需 VPS，用 Cloudflare Tunnel 把电脑工作台装进手机

Tim Chan 发布于 2026 年 8 月 24 日

电脑上的 DSH 工作台只听本机，出门在外够不着。用 Cloudflare Named Tunnel 配认证网关：需要时手机扫码访问，不用时一键关闭。

记录时间：2026-08-24
主角：DeepSeek Harness / DSH、dsh-remote-web-gateway、Cloudflare Named Tunnel、cloudflared
目标：电脑上的 DSH 平时只听本机；需要时手机扫码访问；不用时一键关闭。

0. 背景：使用 DSH 时，我发现了一个远程控制插件

这件事开始于我正常使用 DSH 的时候。DSH 是我电脑里的高权限工作台，能进入工作区、读写文件、执行任务、调用工具，不是普通网页应用。平时它只监听：

http://127.0.0.1:3080

这很安全，但也很不方便。我经常遇到一个场景：任务已经在电脑上跑着，人却不在电脑前——可能在客厅看资料，可能拿着手机站在白板前，也可能临时出门后还想看一眼工具执行到哪一步。

就在这个场景下，我在插件市场里看到了 dsh-remote-web-gateway：

https://deepseek1024.com/plugins/summer1238/dsh-remote-web-gateway/plugin

它的介绍正好打中我的兴趣点：通过 Cloudflare 给 DSH Web 提供远程入口，支持手机登录、二维码配对、手动配对码、设备管理和可选 GitHub 登录。我当时的第一反应不是“我要马上装”，而是“如果安全模型成立，这就很有意思——手机打开网页就能控制电脑里的 DSH”。

不过我没有直接把它当成可用方案。它离本地权限太近，必须先弄清两件事：

1. 它的安全模型是不是真的成立；
2. 默认的 Quick Tunnel 是否适合长期使用。

我让 AI 先做了一次源码级安全审查，重点看监听地址、凭据保存、配对流程、管理接口和 cloudflared 二进制来源。结论是：没有发现恶意行为，核心拓扑也确实把公网请求挡在认证网关外。但这时我也确认了一个关键事实：它默认使用的是随机 Quick Tunnel，也就是临时 trycloudflare.com 地址。方便是真的方便，可长期使用的稳定性、域名可控性和运维体验都不够。

于是目标变得明确：

保留它的安全模型，
但把随机 Quick Tunnel 换成自己的固定域名 Named Tunnel，
让 DSH 远程控制无需 VPS 也能长期可用。

这篇文章先交代背景和原理，再把所有踩坑集中记录，最后给出现在可用的架构和使用方式。

1. 原理：这不是“把端口暴露出去”

很多人一听到“手机访问电脑里的 Web 应用”，第一反应是改监听地址：

127.0.0.1:3080  →  0.0.0.0:3080

这对 DSH 这种高权限工作台非常危险。DSH 不是普通宣传页，它能进入工作区、读写文件、执行任务、调用工具。如果直接暴露端口，等于把一个有本机操作能力的控制台挂到局域网甚至公网。

所以这次要做的是五件事同时成立：

1. DSH 继续只监听 127.0.0.1
2. 公网入口不直连 DSH
3. 流量先经过认证网关
4. 新设备必须扫码或输入一次性配对码
5. 不用时能立刻关闭入口

最终链路可以画成这样：

┌────────────┐
│ 手机浏览器 │
└─────┬──────┘
      │ ① HTTPS 访问固定域名
      ▼
┌─────────────────────────────┐
│ Cloudflare Edge             │
│ https://dsh.example.com     │
└─────┬───────────────────────┘
      │ ② Cloudflare Tunnel 转发
      ▼
┌─────────────────────────────┐
│ 本机 cloudflared 进程       │
│ 只向外连接 Cloudflare        │
│ 不在家宽路由器开端口         │
└─────┬───────────────────────┘
      │ ③ 指向本地回环网关
      ▼
┌─────────────────────────────┐
│ dsh-remote-web-gateway      │
│ 127.0.0.1:61238             │
│ 校验配对码 / 设备会话        │
└─────┬───────────────────────┘
      │ ④ 只有认证后的请求才继续
      ▼
┌─────────────────────────────┐
│ DSH Web                     │
│ http://127.0.0.1:3080       │
└─────────────────────────────┘

这里的关键是：公网请求的终点不是 DSH，而是插件网关。DSH 始终躲在回环地址后面。

再把安全层拆开看：

层级 控制点 失败时的表现
传输层 浏览器到 Cloudflare 是 HTTPS 明文访问不应存在
隧道层 cloudflared 只从本机向外连接 Cloudflare 不需要在路由器做端口映射
入口层 固定域名只指向插件网关 61238 不能绕过网关直达 DSH
认证层 第一次接入需要一次性配对凭据 未配对访问返回 401 / 403
会话层 已配对设备有可撤销会话 设备丢失时可立即撤销
管理层 开启 / 停止远程控制只能在电脑端管理 手机页面不能反向开启入口
应用层 DSH 仍监听 127.0.0.1:3080 公网无法直接触达 DSH

一次完整开启的生命周期是这样：

[电脑 DSH 设置页]
      │ 点击「开启远程控制」
      ▼
[插件读取本地私有配置]
      │ publicHostname / tunnelToken / gatewayPort
      ▼
[启动回环网关]
      │ 监听 127.0.0.1:61238
      ▼
[spawn cloudflared]
      │ cloudflared tunnel ... run --token ... --url http://127.0.0.1:61238
      ▼
[等待 Registered tunnel connection]
      │ Cloudflare Edge 确认连接
      ▼
[publicOrigin 置为可用]
      │ https://dsh.example.com
      ▼
[签发一次性配对票据]
      │ 二维码 secret + 8 位手动码
      ▼
[手机扫码 / 输入配对码]
      │ 成功后票据消费
      ▼
[设备获得受控会话]
      │ 后续请求通过设备 Cookie 认证
      ▼
[网关代理到 DSH Web]
      │ http://127.0.0.1:3080

停止时则要反着收尾：

点击「停止远程控制」
      ↓
publicOrigin 立即关闭
      ↓
未使用配对票动作废
      ↓
cloudflared 收到终止信号
      ↓
本地网关关闭
      ↓
公网重新不可达

理解这张图后，后面第 8 章的每一个坑都会变得很好解释：要么是链路断在 Cloudflare，要么是断在本机端口，要么是认证层没生效，要么是生命周期定时器误杀进程。

2. 需求与约束

DSH 默认 Web 地址是：

http://127.0.0.1:3080

这很安全，但也很不方便。我希望在手机上完成这些事：

  • 查看正在跑的任务；
  • 发送新的指令；
  • 观察工具执行进度；
  • 必要时暂停或者调整任务；
  • 在客厅、阳台或者外出时继续掌控电脑上的工作流。

直接改监听地址当然最快，但风险太大。我的候选方案因此收敛到一个方向：使用带认证网关的 Cloudflare Tunnel 插件：

dsh-remote-web-gateway

它的描述很接近我的需求：

  • 一键远程访问 DSH Web GUI；
  • 通过 Cloudflare Quick Tunnel 提供公网入口；
  • 二维码扫码配对；
  • 支持手动输入配对码；
  • 有设备管理；
  • 可选 GitHub Device Flow 登录。

它不是简单反代，而是试图解决“远程访问必须带认证和生命周期”的问题。这引起了我的兴趣。

3. 先审计，再安装

这个插件的权限太敏感，不能看到 README 就装。它一旦有问题，影响的不只是浏览器页面，而是整个本地工作区。

我把源码拉到临时目录里重点看了几类内容：

1. 是否监听公网；
2. 是否收集或上传敏感数据；
3. 配对码如何生成、保存、过期；
4. 设备 Cookie 是否明文落盘；
5. 管理 RPC 是否可能被远程页面调用；
6. cloudflared 二进制是否会被任意替换；
7. 隧道关闭后是否会留下孤儿进程；
8. 日志是否会把 token 或二维码凭据打出来。

这次静态审计结论是干净的。它的架构和宣传基本一致：

  • 本地网关绑定回环地址；
  • cloudflared 只向外连接 Cloudflare；
  • 新设备必须经过一次性配对；
  • 设备原始 Token 只保存在浏览器 Cookie；
  • 服务端保存的是 SHA-256 哈希；
  • 管理面走 loopback 权限，并拒绝公网路径；
  • 可选 GitHub 登录使用 Device Flow。

但我仍然给自己定了几个原则：

1. 版本锁定，不盲目自动更新；
2. 只在本机配置里保存 Tunnel Token；
3. 远程控制按需开启，用完即关；
4. 定期检查已配对设备；
5. 不把二维码、配对码、Token 截图发出去。

4. Quick Tunnel 是什么？它到底有没有风险？

插件默认使用 Cloudflare Quick Tunnel。命令形式大致是：

cloudflared tunnel --url http://127.0.0.1:61238

运行后会得到一个临时地址：

https://random-words.trycloudflare.com

它的优点很明显：

优点 说明
免配置 不需要提前建 Named Tunnel
免域名 不需要自己的域名
快速验证 几分钟就能打通
无公网 IP 也能用 cloudflared 从内网向外连 Cloudflare

但长期使用时，我开始担心几件事。

4.1 地址不稳定

Quick Tunnel 的 URL 是临时的。进程退出、电脑重启、隧道重开，URL 很可能变化。

这意味着：

昨天手机收藏的链接 → 今天可能失效
旧二维码 → 可能指向旧入口
自动化脚本 → 需要重新取地址

4.2 入口身份不可控

随机域名虽然不容易猜，但它仍然是公共 trycloudflare.com 空间下的地址。链接一旦泄露，别人至少能打到我的插件网关入口。

后面还有认证保护，不代表能进入 DSH，但我更希望入口本身也可管理、可撤销、可审计。

4.3 运维面太弱

Quick Tunnel 不方便绑定自己的 DNS，也不容易接自己的访问策略、日志和告警。它适合试用，不适合作为长期私人工作台入口。

4.4 公共域名的信誉不可控

trycloudflare.com 是公共服务空间，历史上可能被各种用途共享过。某些公司网络、校园网或安全软件可能会对它采取更严格的策略。

4.5 但也不能妖魔化它

要说句公道话：Quick Tunnel 并不是“天生不加密”或者“必然被入侵”。

它的正确评价应该是：

传输上：浏览器到 Cloudflare 是 HTTPS；
拓扑上：cloudflared 从内网向外建立连接；
风险上：主要来自临时入口、泄露二维码、运维不可控和公共域名信誉；
边界上：真正的安全仍然取决于插件认证、设备会话和 DSH 权限。

所以我的结论是：

Quick Tunnel：适合第一次试通。
Named Tunnel：适合长期使用。

我已经有自己的域名，而且 DNS 托管在 Cloudflare，没有理由继续忍受随机地址。

5. 为什么选 Named Tunnel？

Named Tunnel 的结构变成：

dsh.example.com
      ↓ CNAME / Public Hostname
Cloudflare Tunnel
      ↓ 出站连接
本机 cloudflared
      ↓ 固定指向
http://127.0.0.1:61238
      ↓ 认证
http://127.0.0.1:3080

对比一下：

维度 Quick Tunnel Named Tunnel
公网地址 随机临时域名 自己的固定域名
DNS 管理 不可控 可控
二维码稳定性 差 好
手机收藏体验 差 好
入口撤销 关进程即可，但地址不可预测 可停 Tunnel / 删除 Public Hostname
长期运维 弱 强
初始成本 最低 需要有域名并配置 Cloudflare

目标体验也明确了：

平时：公网不可达。
要用：电脑端点击开启。
接入：手机打开固定域名。
首次：扫码或输配对码。
后续：设备会话认证。
异常：电脑端一键撤销设备。
结束：一键停止远程控制。

6. 创建 Cloudflare Named Tunnel

这一步分三件事：创建 Tunnel、绑定 Public Hostname、让本机 cloudflared 接入。

6.1 创建 Tunnel

进入 Cloudflare Zero Trust 控制台：

Networks → Tunnels → Create a tunnel

给 Tunnel 起名：

dsh

Cloudflare 会生成一个 Connector Token。这个 Token 必须当成密码保管，本文统一写作：

<CLOUDFLARE_TUNNEL_TOKEN>

6.2 配置 Public Hostname

假设自己的域名是：

example.com

想让 DSH 使用：

dsh.example.com

那么 Public Hostname 应该类似：

Subdomain: dsh
Domain:     example.com
Service:    http://localhost:61238

注意这里的 Service 是 61238，不是 DSH 的 3080。

原因看这张图就清楚了：

正确：
手机 → Cloudflare → cloudflared → 61238 认证网关 → 3080 DSH

危险或错误：
手机 → Cloudflare → cloudflared → 3080 DSH
                         ↑
                    绕过了认证网关

Cloudflare 通常会自动创建类似的 DNS 记录：

dsh.example.com  CNAME  <TUNNEL_ID>.cfargotunnel.com

6.3 手动验证 Connector

为了排除插件因素，我先手动跑最小命令：

cloudflared tunnel run \
  --token '<CLOUDFLARE_TUNNEL_TOKEN>' \
  --url http://127.0.0.1:61238

日志出现这类内容才算注册成功：

Registered tunnel connection

如果这时访问域名返回：

HTTP 401 / 403
forbidden

反而是好现象，说明流量已经穿过 Cloudflare 到达认证网关，只是还没有配对。

7. 开始魔改插件：让它支持一键 Named Tunnel

我不想每次都手动开终端。目标是在 DSH 设置页点击按钮后，插件自己完成：

读配置 → 启动网关 → 启动 cloudflared → 等 Tunnel Ready → 展示二维码

于是给插件增加三个关键配置概念：

tunnelToken?: string      // Cloudflare Tunnel Token
publicHostname?: string   // dsh.example.com
gatewayPort: number       // 固定 61238

插件配置样例：

- id: dsh-remote-web-gateway
  config:
    gatewayPort: 61238
    publicHostname: dsh.example.com
    tunnelToken: "<CLOUDFLARE_TUNNEL_TOKEN>"

Web profile 中使用本地魔改版：

{
  "dependencies": {
    "dsh-remote-web-gateway": "link:/absolute/path/to/dsh-remote-web-gateway"
  }
}

运行时的启动参数最终应该等价于：

cloudflared tunnel \
  --protocol http2 \
  --no-autoupdate \
  --logfile /path/to/cloudflared.log \
  run \
  --token '<CLOUDFLARE_TUNNEL_TOKEN>' \
  --url http://127.0.0.1:61238

其中：

  • --protocol http2：避开默认 QUIC 在个别网络下带来的不确定性；
  • --no-autoupdate：避免长连接期间自动更新干扰；
  • --logfile：让问题能追到日志；
  • --url：明确告诉 cloudflared 本地目标是哪个服务；
  • --token：只从本地私有配置读取，绝不写进文章或仓库。

8. 踩坑实录：所有问题集中在这里

这一章把整个过程里散落的坑集中记录。它们分别发生在四个层面：

层面 问题 结果
DSH Profile bundle 路径失效 启动失败
Cloudflare Tunnel 没有 ingress / 连接未注册 503、1033、空白页
本地端口 网关随机端口和固定转发端口错位 公网打不到认证网关
插件生命周期 定时器误杀、构建产物陈旧、输入清洗缺失 30 秒断开、配对失败

8.1 DSH 启动报 cannot resolve profile bundle

还没走到 Tunnel，项目搬家后 DSH 就先失败了：

dsh: cannot resolve profile bundle "dsh-plugin-session-delete"

这个错误说明 Web profile 解析不到某个 bundle。常见原因有三类：

1. profile/package.json 里的 link 路径还是旧机器或旧目录；
2. bundle 名字没有加入 profile 的 bundles 列表；
3. 插件没有被正确 install 到当前 profile。

我的处理方式：

# 检查当前 Web profile 依赖
cat ~/.dsh/profiles/web/package.json

# 把插件依赖改成当前绝对路径
"dsh-plugin-session-delete": "link:/current/path/to/dsh-plugin-session-delete"
"dsh-remote-web-gateway": "link:/current/path/to/dsh-remote-web-gateway"

同时确认 bundles 里包含对应 id：

{
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dsh-plugin-session-delete",
        "dsh-remote-web-gateway"
      ]
    }
  }
}

这件事提醒我：DSH 是插件化架构，profile 不只是配置文本，还会解析依赖、bundle 和补丁层。目录一搬家，所有隐含路径都要重查。

8.2 No ingress rules，公网全部 503

手动测试 Named Tunnel 时，日志反复出现：

WRN No ingress rules were defined in provided config (if any) nor from the cli,
cloudflared will return 503 for all incoming HTTP requests

这句话已经把问题说得很直白：cloudflared 不知道 HTTP 请求进来以后该转发到哪里。

用图表示就是：

手机请求 dsh.example.com
        ↓
Cloudflare 找到了 Tunnel
        ↓
cloudflared 也在线
        ↓
但是问：我要转发到哪个本地服务？
        ↓
没有 ingress 规则，也没有 --url
        ↓
只能 503

修复方式有两种。

方式一，在 Cloudflare Dashboard 明确配置：

Public Hostname: dsh.example.com
Service:         http://localhost:61238

方式二，命令行显式指定：

--url http://127.0.0.1:61238

为了避免两边不一致，我最后要求两者同时对齐：

Dashboard Service: http://localhost:61238
插件启动参数:      --url http://127.0.0.1:61238

这也是这次的一个重要原则：关键链路上的端口不要靠默认值猜。

8.3 公网打开是空白页，或者 Cloudflare Error 1033

这个问题最容易误判成“前端炸了”。实际上要先判断错误发生在哪一层。

我用这张表分流：

返回结果 含义 检查方向
Cloudflare 530 + Error 1033 Cloudflare 找不到健康 Tunnel 连接 cloudflared 是否运行、Token 是否正确、Tunnel ID 是否匹配
503 unavailable 请求接近网关，但入口未开放或上游不可达 是否真的点了开启、网关端口是否一致
401 / 403 forbidden 已经到达认证网关但未配对 正常中间态，去扫码或输码
浏览器空白页 可能是资源加载失败、路由错误或代理层拦截 打开开发者工具看 Network 和 Console
ERR_CONNECTION_REFUSED 本地目标端口没人监听 检查 61238 或 3080

当时最迷惑的是“空白页”。它不像 530 那样一眼看出是 Cloudflare 错误页，也不像 401 能明显提示认证。后来靠分层请求才定位：

# 第一层：DSH 本体是否活着
lsof -nP -iTCP:3080 -sTCP:LISTEN

# 第二层：插件网关是否监听
lsof -nP -iTCP:61238 -sTCP:LISTEN

# 第三层：公网到底返回什么
curl -i https://dsh.example.com/

# 第四层：cloudflared 是否注册
tail -f /path/to/cloudflared.log

日志里必须有：

Registered tunnel connection

如果没有这行，UI 显示什么都不能算成功。

8.4 网关随机端口，Cloudflare 却固定打向 61238

这是整条链路里最关键的坑之一。

插件原来的默认配置是：

gatewayPort: 0

Node.js 里端口 0 表示交给操作系统分配一个随机可用端口。这在 Quick Tunnel 模式下没问题，因为插件自己知道实际端口，可以把 cloudflared 的 --url 动态指过去。

但 Named Tunnel 场景不同。我在 Cloudflare Dashboard 里已经写死了：

Service: http://localhost:61238

于是出现了这种错位：

Cloudflare：我永远把流量送到 61238。
cloudflared：收到，我去找 127.0.0.1:61238。
插件网关：不好意思，我今天被分配的是 59xxx。
手机：所以我看到空白 / 失败。

修复很简单，但要改变思路：

config:
  gatewayPort: 61238

然后验证：

lsof -nP -iTCP:61238 -sTCP:LISTEN

必须看到：

node xxxxx tim IPv4 TCP 127.0.0.1:61238 LISTEN

这一步修完后，“完全空白”开始变成“认证拒绝”。虽然还没成功，但这是正确的中间状态，因为流量终于走到了安全门。

8.5 开启 30 秒后突然自动关闭

这是最折磨人的问题。

现象非常稳定：

00:00 点击「开启远程控制」
00:02 显示「已开启」
00:03 出现二维码和剩余时间
00:30 左右自动退回「未开启」或显示「连接已断开」

界面有时给出错误码：

connection-lost

我一开始怀疑很多方向：

1. 插件里有 30 秒定时器没清理；
2. cloudflared 被 macOS 或网络杀掉；
3. Cloudflare 边缘主动断开；
4. QUIC 协议在这个网络不稳定；
5. 插件构建产物没有更新；
6. Token 权限不足。

最后证明，多个因素叠加。

8.5.1 根因 A：ready 之后没有清掉启动定时器

启动逻辑应该是一个很清晰的状态机：

idle
  ↓ start()
resolving / verifying / downloading
  ↓
starting
  ↓
connecting
  ↓ Registered tunnel connection
ready

为了保证不会无限等待，代码里有一个启动超时定时器：

const timer = setTimeout(() => {
  killChild()
  fail(new TunnelStartError('start-timeout', '...'))
}, startTimeoutMs)

正常语义必须是：

30 秒内没 ready → 杀进程并失败
一旦 ready    → clearTimeout(timer)

如果 finish() 里漏掉清理，就会出现诡异现象：

cloudflared 明明已经注册成功，
但旧的 30 秒定时器还在事件循环里，
时间一到，它把健康进程杀了。

修复逻辑：

const finish = (url: URL): void => {
  if (settled) return
  settled = true

  // 关键：ready 后取消启动超时
  clearTimeout(timer)

  phase = 'ready'
  publicUrl = url
  options.onReady?.(url)
  resolve(url)
}

8.5.2 根因 B：cloudflared 参数顺序放错

我想给长连接加上稳定参数：

--protocol http2
--no-autoupdate
--logfile ...

一开始把这些放在 run 后面，cloudflared 直接报：

Incorrect Usage: flag provided but not defined

更麻烦的是，有些尝试看起来退出码还不吓人，很容易误判成“正常退出”。

最后验证可用的顺序是把这类参数放在 run 前：

cloudflared tunnel \
  --protocol http2 \
  --no-autoupdate \
  --logfile /path/to/cloudflared.log \
  run \
  --token '<CLOUDFLARE_TUNNEL_TOKEN>' \
  --url http://127.0.0.1:61238

这不是说所有版本的 cloudflared 都一定一样，而是提醒：参数顺序本身就是协议的一部分，不能靠感觉排。

8.5.3 根因 C：源码修好了，但运行的不是新源码

这是最隐蔽的一层，也是这次最有价值的工程教训。

当时的现象是：

源码里明明已经加了 --url；
源码里已经在 finish() 里 clearTimeout(timer)；
类型检查也通过；
但 DSH 里跑出来的行为仍然是旧的。

我把构建链路拆开看，发现问题出在 vendored core 复制逻辑。

真实的新编译产物在这里：

dsh-remote-web-gateway/core-src/dist/

但打包脚本却去找上一级的陈旧目录：

const repoRoot = resolve(pluginRoot, '..')
const sourceDist = join(repoRoot, 'dist')

也就是说：

你以为是：
core-src/src
  → core-src/dist
    → vendor/
      → DSH 运行时

实际变成了：
core-src/src
  → core-src/dist          新产物躺在这里
某个上级旧 dist           被复制进 vendor
DSH                       继续加载旧逻辑

修复脚本语义：

const coreDistRoot = join(pluginRoot, 'core-src')
const sourceDist = join(coreDistRoot, 'dist')

然后强制重建：

cd /absolute/path/to/dsh-remote-web-gateway/core-src
npx tsc -p tsconfig.build.json

cd /absolute/path/to/dsh-remote-web-gateway
npm run build

再重启 DSH。

这一步完成后，同一个按钮的行为终于变了。

我总结成一句话：

TypeScript 编译通过，不代表运行时代码更新了。一定要证明最终加载的那份 JS 是新产物。

8.5.4 怎么确认 30 秒问题真的消失

我没有靠肉眼感觉，而是做了四组验证。

第一，独立运行原始命令：

cloudflared tunnel run \
  --token '<CLOUDFLARE_TUNNEL_TOKEN>' \
  --url http://127.0.0.1:61238

连续超过 45 秒正常，日志出现两条注册连接：

Registered tunnel connection
Registered tunnel connection

这说明 Token、域名、网络都没问题。

第二，直接调用插件编译后的 createQuickTunnelService()。

旧产物会在 ready 后大约 30 秒触发：

onClosed
phase: error
lastErrorCode: connection-lost

新产物持续保持：

phase: ready
publicUrl: https://dsh.example.com

第三，观察 UI 倒计时。

开启后显示：

远程控制 · 已开启
剩余 04:40

超过 40 秒再看，仍然是：

远程控制 · 已开启
剩余 03:56

总开关没有退回「未开启」，倒计时自然减少。

第四，看日志和公网响应。

日志确认：

protocol=http2
Registered tunnel connection

公网未配对访问返回：

HTTP 401 / 403
forbidden

这不是故障，而是认证层在工作。

8.6 配对码格式不正确

隧道稳定后，我以为马上能用，结果手机提交配对码时报：

配对码格式不正确

电脑上显示的是：

ABCD EFGH

中间那个空格只是为了人眼阅读。但手机端最初的处理是：

var code = input.value.trim().toUpperCase()

trim() 只删首尾空格，不删中间空格，所以实际提交值仍是：

"ABCD EFGH"

长度是 9，当然匹配不了 8 位正则：

/^[A-HJ-NP-Z2-9]{8}$/

流程画出来就是：

屏幕展示："ABCD EFGH"
            ↑ 这里只是视觉分隔

用户复制 / 输入："ABCD EFGH"

旧代码：
.trim()          → "ABCD EFGH"
.toUpperCase()   → "ABCD EFGH"
正则校验          → 长度 9，失败

新代码：
.replace(/\s+/g, '') → "ABCDEFGH"
.trim()              → "ABCDEFGH"
.toUpperCase()       → "ABCDEFGH"
正则校验              → 通过

前端修复：

var code = input.value.replace(/\s+/g, '').trim().toUpperCase()

服务端也必须同样清洗，不能只信前端：

credential = body.code.replace(/\s+/g, '').trim().toUpperCase()

if (!CODE_PATTERN.test(credential)) {
  // reject
}

这是一个很典型的人机交互边界问题：展示格式不能等同于机器格式。

顺带说一下配对码设计，它比看上去讲究：

设计点 目的
去掉 I / L / O 避免字母混淆
去掉 0 / 1 避免数字与字母混淆
拒绝采样 避免简单取模造成概率偏差
256-bit QR secret 二维码通道具备高强度熵
8 位手动码约 39.6 bits 熵 人能输入，同时暴力猜测不现实
一次性消费 同一个票据不能复用
默认 5 分钟过期 缩短泄露窗口
全局限速 抑制在线暴力尝试
隧道停止即作废 避免票据跨生命周期残留

8.7 GitHub 绑定来不及点完

插件支持可选的 GitHub Device Flow 登录。流程大致是：

DSH 页面显示设备码
      ↓
用户打开 GitHub 授权页
      ↓
输入设备码
      ↓
GitHub 显示授权请求
      ↓
用户确认
      ↓
插件轮询拿到结果
      ↓
设置页显示已绑定身份

以前 30 秒断开的问题会让这个流程几乎不可能顺利完成。你可能刚切到 GitHub 页面，插件那边已经开始倒计时甚至断开。

30 秒生命周期修复后，这个入口恢复正常。设置页最终只显示非敏感信息：

已绑定
@username · id xxxx · 时间

我的理解是：GitHub 登录是辅助身份能力，不应该替代一次性配对。两者职责不同：

机制 解决什么问题
配对码 / 二维码 “这台设备能不能第一次接入”
设备会话 “这台已接入设备后续是否还能访问”
GitHub 身份 “这个远端身份是否是允许的绑定人”
管理开关 “公网入口现在是否应该存在”

9. 最终架构定稿

最后固定下来的链路是：

手机 / 平板
   │ HTTPS
   ▼
https://dsh.example.com
   │ Cloudflare Public Hostname
   ▼
Cloudflare Tunnel
   │ 出站连接
   ▼
本机 cloudflared
   │ --url http://127.0.0.1:61238
   ▼
dsh-remote-web-gateway
   │ 配对码 / 设备会话认证
   ▼
http://127.0.0.1:3080
   ▼
DSH Web

每个端口都有明确职责：

端口 服务 是否公网直达 作用
3080 DSH Web 否 真正的应用界面
61238 插件网关 仅经 Cloudflare Tunnel 到达 认证、代理、生命周期管理
Cloudflare 443 公网入口 是 固定域名和 TLS

关键配置保持三处一致：

Cloudflare Dashboard:
  Service = http://localhost:61238

DSH 插件配置:
  gatewayPort = 61238
  publicHostname = dsh.example.com
  tunnelToken = <CLOUDFLARE_TUNNEL_TOKEN>

cloudflared 参数:
  --url http://127.0.0.1:61238

任何一处不一致，都会出现“看似启动成功，实际手机打不开”的情况。

10. 安全模型：便利不能吃掉安全边界

自建 Tunnel 只是解决了入口稳定问题，不能放松认证。

我最终保留的安全边界如下。

10.1 DSH 永远只听本机

DSH Web 保持：

http://127.0.0.1:3080

不改成 0.0.0.0。

10.2 公网只进插件网关

Cloudflare Service 不指向 DSH，而是指向：

http://localhost:61238

10.3 配对码只是短期门禁

默认 5 分钟有效、一次性消费、可重新生成。它不是长期密码。

10.4 设备可单独撤销

每台已配对浏览器都是一个 device session。可以在设置页单独撤销，也可以全部撤销。

10.5 Token 只放本机

tunnelToken 属于高价值凭据。它只能放在本机私有配置里。

如果曾经误发到聊天、截图、仓库或公开文章，应立即在 Cloudflare 里刷新或重建 Tunnel。

10.6 按需开启，用完关闭

远程控制在 DSH 设置页手动开启。不用时点停止。

停止后应满足：

cloudflared 退出；
publicOrigin 清空；
未使用票据作废；
公网重新返回不可达；
必要时撤销设备会话。

11. 排障速查表

这次踩坑后，我把最常见症状整理成表。

现象 大概率含义 处理
Cloudflare 530 / Error 1033 Tunnel 没有健康连接 检查 cloudflared 进程、Token、Tunnel ID、日志
No ingress rules cloudflared 不知道本地目标 显式 --url，检查 Dashboard Service
503 unavailable 请求到达网关附近，但入口未开放或上游异常 确认是否已开启、网关端口是否正确
401 / 403 forbidden 已到认证网关，但未配对 正常，去扫码或输配对码
页面空白 分层不清，可能是资源、路由或代理层问题 分别测 3080、61238、公网响应
30 秒断开 定时器未清或运行的是旧构建 检查 clearTimeout(timer) 和最终 vendor 产物
配对码格式不正确 展示空格进入提交值 前后端统一清除所有空白
GitHub 授权来不及 总开关生命周期太短 先修 30 秒断开，再重新绑定
重启后又失效 配置未持久化或加载了旧 profile 检查 profile patch、link 路径、bundle 列表

遇到问题时，推荐按这个顺序查：

1. cloudflared 日志有没有 Registered tunnel connection？
2. 127.0.0.1:61238 有没有人监听？
3. Cloudflare Public Hostname 是否指向 61238？
4. 公网 curl 返回的是 530 / 503 / 401 哪一种？
5. UI 显示的 phase 和错误码是什么？
6. 最终加载的 JS 构建产物是不是刚刚编译出来的？

12. 这次学到的六件事

12.1 高权限应用不能裸露端口

DSH 不是普通网页。只要它能触达文件和工作区，就必须把公网入口挡在认证网关之外。

12.2 Quick Tunnel 适合试，Named Tunnel 适合用

Quick Tunnel 能快速验证可行性，但长期使用需要一个稳定、可管理、可撤销的入口。

12.3 图比直觉可靠

把链路画出来后，很多问题立刻显形：

Cloudflare → cloudflared → 61238 → 3080

只要有一段指错，症状就会往后传播。

12.4 日志是最短路径

Registered tunnel connection、No ingress rules、connection-lost 这些信息，比 UI 表象可靠得多。

12.5 构建产物必须验尸

源码对了、类型检查过了、UI 还旧行为，就要去看最终加载的 JS 文件到底来自哪里。

12.6 人机输入边界要显式规范化

屏幕上的 "ABCD EFGH" 是给人看的；提交前应转换成机器格式 "ABCDEFGH"。前后端都要做同样的清洗。

13. 现在的使用体验

最终流程非常干净：

1. 电脑启动 DSH；
2. 设置 → 远程控制；
3. 点击「开启远程控制」；
4. 插件自动启动固定域名 Tunnel；
5. 手机打开 https://dsh.example.com；
6. 扫码，或输入 8 位配对码；
7. 配对成功，进入 DSH；
8. 用完点「停止远程控制」。

不再需要手动开终端，不再追着一串 trycloudflare.com 地址跑，也不会因为 30 秒断开来不及配对。

更重要的是，整个系统始终保留了一个原则：

公网入口存在时，必须经过认证；
不需要它存在时，就让它彻底消失。

14. 上线前检查清单

如果你也想复刻这套方案，建议逐项确认：

[ ] DSH 仍监听 127.0.0.1:3080
[ ] 插件网关固定监听 127.0.0.1:61238
[ ] Cloudflare Public Hostname Service 指向 http://localhost:61238
[ ] publicHostname 与 Cloudflare 域名一致
[ ] tunnelToken 只存在于本机私有配置
[ ] cloudflared 启动参数显式包含 --url
[ ] 日志出现 Registered tunnel connection
[ ] 未配对公网访问返回 401 / 403
[ ] 配对码展示中的空格不会导致校验失败
[ ] 配对码 5 分钟内一次性使用
[ ] 已配对设备可在设置页撤销
[ ] 用完点击停止远程控制
[ ] 重启后确认不会遗留 cloudflared 孤儿进程

15. 结语

这次折腾表面上是“让手机打开一个网页”，实际上是把五个问题串起来解决：

入口从哪来？
入口是否稳定？
谁能通过入口？
通过后能做什么？
不用时怎么收回权限？

Quick Tunnel 回答了第一问，Named Tunnel 回答了第二问，配对码和设备会话回答了第三、四问，「开启 / 停止远程控制」回答了第五问。

少任何一层，都会在某次重启、换网、分享二维码或误点按钮时变成一次惊吓。

现在它终于变成了一个干净的私人工具：平时安静，用时可控，用完即走。
