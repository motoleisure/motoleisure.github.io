你的 AI Agent 正在偷偷烧钱？搞懂「提示词缓存」，费用直接降 90%

假设你正在用一个编程 Agent 干活，对话已经积累了 5 万 token 的上下文。这时你追加了一个 1 千 token 的小问题，总上下文变成了 5.1 万 token。

问题来了：这 5.1 万个 token，会不会全部按全价计费？

答案是：只要你的 Agent 脚手架实现正确，就不会。 但如果实现不对，你就得为整段内容支付全价——那会非常非常贵。

今天这期视频讲的就是这件事：提示词缓存（Prompt Caching），以及如何正确使用它，在使用 AI Agent 时省下一大笔钱。

先打破一个误区：缓存的是「输入」，不是「输出」

搞软件开发的朋友都熟悉缓存：数据库把查询结果存起来，下次同样的查询直接命中，不用再去数据库重新算一遍。

很多人以为提示词缓存也是这个逻辑——把大模型的输出缓存下来，下次发同样的提示词，直接把缓存的回复返回。

这是完全错误的。

提示词缓存缓存的不是输出，而是输入。

在大模型的每一次推理中，真正的开销在于：模型需要重新"处理"你发送的全部上下文。

  • 你的对话进行到一半，已有 5 万 token；
  • 你又问了一个问题，追加 1 千 token；
  • 为了让模型理解完整上下文，你必须把 5.1 万 token 全部重新发送过去；
  • 下一次提问，又要重新发送 5.5 万、5.8 万、6 万……

你会发现：同样的 token，被一遍又一遍地重复发送。 每一轮，模型都在重复处理之前已经看过的内容。

有些 API（比如某些响应式 API）会包装得很好，让你感觉模型"记得"之前说过什么。但后台发生的，其实是模型在每次响应时把全部上下文重新处理了一遍。

顺便说一句——这也是为什么在编码会话里追求超大上下文不是个好主意：它会让费用迅速失控。

缓存命中价：同样的内容，第二次只要 10%

既然如此，各家大模型 API 是怎么解决这个问题的？

答案就是提示词缓存：

  • 模型第一次看到某个 token，按全价收费；
  • 之后第二次、第三次再读到完全相同的 token，只收约 10% 的缓存命中价。

实现上，提供商会把相同的处理过程路由到同一台之前处理过的机器上，直接命中缓存。

这意味着：一个 5 万 token 的会话，并不是只消耗 5 万 token，而是 5 万 + 5.1 万 + 5.4 万 + 5.5 万…… 累加。如果全价支付，费用增长是指数级的；而启用缓存后，大部分重复 token 都按 10% 计费，成本曲线从指数级变成线性级，甚至趋近于免费。

关键实践：4 条规则让你的缓存一直「命中」

既然缓存能省这么多钱，那怎么保证高命中率？作者给出了几条非常重要的实操建议。

1. 系统提示词里，绝对不要放「动态内容」⚠️

这是最容易被忽略、也最致命的一条。

假设你的系统提示词有 1 万 token，每次请求都带着它，本来这部分能稳定命中缓存。但如果你在系统提示词里塞了时间戳、当前工作目录、动态更新的工具列表这类会变化的内容——

哪怕只改了一个字，也会让此后的整个缓存全部失效。 之后的每一轮，都要重新按全价处理。

所以：系统提示词、线程、历史记录，在对话过程中都不应该动态变化。

2. 对话历史「只追加，不修改」

对话历史应该始终是 append-only（只追加）。不要在中间插入、修改、删除内容，任何一点"小错误"都会导致缓存失效。

3. 了解你的提供商：缓存默认开没开？多久过期？

不同提供商的缓存策略差异很大：

提供商 是否默认启用 缓存有效期（约）
OpenAI / Hugging Face ✅ 默认启用 约 1 小时
Anthropic ❌ 需手动启用 默认 5 分钟
Claude Code 认证 — 约 1 小时
Gemini ❌ 需手动启用 视配置而定

特别是使用 Chat Completion API 时，缓存并不总是默认开启，你需要自己去确认、显式启用。如果你用的是托管在后台处理了一切的响应式 API，通常默认就开着。

4. 压缩（Compaction）会重置缓存，这是正常代价

当对话太长需要把历史内容压缩成摘要时，缓存必然会失效——因为内容已经被重写了。压缩本身没问题，但你心里要有数：压缩之后，下一轮需要重新"喂"一遍全价输入。

总结：记住这几句话

  1. 提示词缓存缓存的是输入，不是输出；
  2. 系统提示词里别放时间戳、工作目录这类动态内容；
  3. 对话历史只追加，别因小失大；
  4. 搞清楚你的提供商是否默认启用、缓存多久过期；
