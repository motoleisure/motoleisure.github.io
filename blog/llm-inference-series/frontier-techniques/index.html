13 · 前沿技术：Prefix Caching 进阶、Chunked Prefill、Disaggregated Inference、MoE 服务

前面的篇章讲"现在已经成熟"的技术。这一篇讲"正在发生"的前沿——它们已经开始落地，是未来 1-2 年推理工程师要掌握的方向。

一、Disaggregated Inference（预填充/解码分离）

1.1 动机

回顾 prefill 和 decode 的特性（第 2 篇）：prefill 是 compute-bound，decode 是 memory-bound。它们对硬件的需求完全不同：

  • prefill 要算力（高 FLOPS GPU）
  • decode 要带宽（高 HBM 带宽 / 大显存放 KV cache）

把它们混在同一个集群/同一批 GPU 上跑，结果是要么 prefill 抢 decode 的带宽，要么 decode 拖 prefill 的算力。这就是 disaggregated inference 的出发点：把两个阶段分开到不同资源池。

1.2 架构

请求 → Prefill 池（算力强 GPU，专跑 prefill）
         │ 算完 KV cache
         ▼
       KV cache 传输（NVLink / RDMA / 落盘）
         │
         ▼
       Decode 池（高带宽 GPU，专跑 decode，接收 KV cache）
         │ 一个一个 token 生成
         ▼
       返回

1.3 收益与挑战

收益：

  • 每个池按自己特性优化硬件（prefill 池选高 FLOPS，decode 池选高带宽/大显存）。
  • 资源利用率更高（不互相抢）。
  • prefill 池可以批处理更多 prefill，decode 池可以装更多 KV cache。

挑战：

  • KV cache 传输：prefill 算出的 KV cache 要搬到 decode 池，几十 GB 数据要快传（NVLink/RDMA），否则传输成新瓶颈。
  • 调度复杂：两个池要协调，KV cache 要找到对应 decode 副本。
  • 工程复杂度高。

1.4 现状

vLLM 已有 disaggregated prefill 的实验支持（V1 架构里的 Disaggregated Serving）。SGLang、Mooncake、NVIDIA Dynamo 等都在推进。这是大规模推理的明确方向。

实践判断：中小规模先不上 disaggregated（复杂度不值），到几十卡以上、prefill/decode 比例严重失衡时再考虑。

二、Chunked Prefill 进阶：动态调度

2.1 基础（第 6 篇讲的）

把长 prompt 的 prefill 切块，和 decode 交错，防 prefill 独占 GPU。

2.2 进阶：动态块大小

固定块大小不优：短 prompt 切太碎增加开销，长 prompt 块太小 prefill 慢。前沿做法是动态块大小：

  • 看当前 decode batch 多大、剩多少算力，动态决定这个 iteration 给 prefill 多少 token。
  • decode 空闲时大块 prefill，decode 忙时小块或暂停 prefill。

2.3 与 disaggregated 的关系

chunked prefill 是"同一池内交错"。disaggregated 是"彻底分池"。两者是同一线索的不同力度——chunked 是软交错，disaggregated 是硬分离。

三、Prefix Caching 进阶：跨请求 / 跨副本 / 持久化

3.1 基础（第 3 篇讲的）

同引擎内、同副本的 prefix 复用。

3.2 进阶方向

  • 跨副本共享：多个 vLLM 副本共享一个分布式 KV cache 池（如 LMCache、Mooncake），任一副本算的前缀别的副本能用。对多轮对话/agent 跨副本路由场景意义重大。
  • 持久化：把热点 prefix 的 KV cache 落盘，重启/扩容后恢复，不重算。
  • 智能预取：预测哪些 prefix 会被请求，提前 prefill 填 cache。
  • 层级 cache：GPU HBM → CPU 内存 → SSD 多级，按热度和成本放。

3.3 一个量化

跨副本共享 KV cache 池，对 agent 平台（每轮带大量相同 system prompt + 工具定义）能把 TTFT 再降一截。但要监控命中率 和 TTFT 改善一致（第 3、10 篇的审计教训）。

四、MoE（Mixture of Experts）服务

4.1 MoE 为什么服务难

MoE 模型（DeepSeek-V3/R1、Mixtral、GLM-5 等）参数量巨大（几百 B 到万亿），但每次推理只激活一部分 expert。挑战：

  • 权重巨大：全量 expert 权重放不下单机，要 EP（专家并行）把不同 expert 分到不同卡。
  • 动态路由：每个 token 激活哪些 expert 运行时才知道，路由 + all-to-all 通信复杂。
  • 负载不均：热门 expert 被频繁激活（容量热点），冷 expert 闲着。

4.2 服务优化

  • Expert Parallel (EP)：expert 分布到多卡，按 token 路由分发。
  • expert 缓存：热门 expert 保持在快显存，冷 expert 换到慢层或别的卡。
  • 细粒度 expert / 共享 expert：DeepSeek 的细粒度 design 让负载更均衡。
  • EP × DP × TP 组合：大规模 MoE 要复杂并行组合。

4.3 现状

SGLang 在服务 DeepSeek/GLM 等 MoE 上表现抢眼（如 "GLM5.2 NVFP4 agentic workloads 500 TPS" 的 blog）。vLLM 也支持 MoE。这是万亿参数模型服务的主战场。

4.4 MoE 路由机制：top-k、aux loss vs aux-loss-free（Atlas #34 补强）

前面 4.2 讲了 MoE 服务优化，但没讲透「token 怎么分配到 expert」这个路由机制。这一节补 Atlas #34：top-k 路由、两种负载均衡策略，以及为什么 DeepSeek 选了 aux-loss-free。

top-k 路由：每个 token 经过一个门控（gate）算出对每个 expert 的分数，选 top-1 或 top-k（如 top-2/4）个 expert 处理。其余 expert 不激活——这就是 MoE 省算力的根：每个 token 只走一小部分 expert。

问题：如果门控总把 token 往同一批「热门 expert」送，热门的爆、冷门的闲——负载不均 → 吞吐不稳、部分设备闲置。两种解决路线：

策略 怎么做 代价
aux loss（辅助损失） 训练时加一个负载均衡 loss，惩罚 expert 不均匀 要调 loss 权重；可能伤主任务质量（和主目标打架）
aux-loss-free（辅助无损） 不加额外 loss，用门控分数的 bias 偏置动态调节——某 expert 过载就降偏置、过闲就升偏置 不干预主 loss、质量更稳；DeepSeek-V3 路线
  • aux-loss-free 是 DeepSeek 的选择：用 bias 偏置替代 aux loss，均衡效果不靠损失项打架，质量更稳。这是为什么 DeepSeek MoE 服务能压住 expert 失衡。
  • tradeoff（Atlas 告诫）：「Training-time MoE balancing objectives are different from serving-time expert placement.」——训练期的均衡策略（aux loss / bias 偏置）固化在权重里，服务期改路由 = 改模型行为。别在生产里随便把 top-1 改成 top-2、或关掉 bias 调节。

4.5 服务期 expert 失衡与卸载

服务期失衡：真实流量下 expert 受欢迎度不均，热门 expert 成瓶颈、冷门 expert 闲置 → 吞吐不稳、延迟突刺。这和训练期的「均匀分布」假设不同——服务期的 token 分布才是真分布。

expert 卸载（offload）：把不常用的 expert 挪到 CPU/SSD，按需加载。热门 expert 常驻 GPU HBM，冷门按需搬——和第 17 篇 KV 分层存储同款「快慢层」思路。

  • 代价：按需加载有延迟（PCIe/SSD 搬运），要算「搬回 vs 算别的」成本（同第 17 篇铁律）。
  • tradeoff：容量限制 + token dropping 会改输出——硬限 expert 容量、丢超量 token 会改变质量，Atlas 明确警告。

责任边界：MoE 路由与均衡是 Model / MoE-systems engineer 的事。inference engineer 要懂：拿到 MoE 模型问清路由是 top-k 几、有没有 aux-loss-free bias、热门 expert 会不会爆；服务期监控 expert 负载方差，失衡大时考虑 EP 调度或卸载——但不改路由规则（那是改模型）。

五、其他前沿方向速览

5.1 量化前沿

  • FP4 / NVFP4：Blackwell 原生支持 4-bit 浮点，质量优于 INT4。SGLang 已在用 NVFP4 服务 GLM。
  • 2-bit / 1-bit：BitNet 等探索极低比特，质量-压缩边界推进。
  • 激活量化（W8A8）：不只权重量化，激活也量化，prefill 也加速。要处理异常值。

5.2 投机解码前沿

  • 新一代（DFlash / Spec V2）：SGLang 推进，更高接受率、更大模型。
  • 多 draft 并行：多个 draft 候选并行验证。
  • target-drived draft：用 target 自身的浅层预测（n-gram 或小 head）当 draft。

5.3 长上下文

  • 1M+ context：Qwen 等推百万级上下文，靠 Ring Attention / CP + GQA 省 cache。
  • KV cache 量化：把 KV cache 也量化（FP8/INT4），省带宽。但要测精度退化（长上下文放大）。
  • KV cache 压缩 / 蒸发：丢弃不重要的 KV，减 cache（如 H2O、StreamingLLM 的 sink token）。

5.4 异构 / 多模态

  • 多模态服务：图/音/视频输入，attention 形状变化大，调度更复杂。
  • 扩散模型推理：SGLang Diffusion 把推理引擎思路用到图/视频生成。
  • 实时语音：低延迟流式语音（turn-taking），TTFT 要 <300ms。

5.5 跨厂商 / 开放标准

  • MLX 扩到多设备：mx.distributed 支持分布式推理。
  • 开放推理标准：llm-d、KubeAI 等 Kubernetes 原生推理栈，标准化部署。

六、怎么跟进前沿

  1. 关注 LMSys/SGLang blog：前沿落地最快。
  2. vLLM release notes + 文档 features：新功能 day-0。
  3. NVIDIA / 各 chip 厂白皮书：硬件能力边界。
  4. arxiv 速览：speculative decoding、KV cache、attention 的新论文。
  5. 本地复现：看一个新技巧，先用小模型在本地复现验证再判断（Inference Lab 的实证精神）。

前沿判断原则：别被"声称的加速比"带跑。 每个新技巧都要问：在什么 workload、什么 batch、什么硬件下成立？对质量影响多大？Inference Lab 反复示范的——声明要有边界，"这不证明什么"要写出来。

八、原书补强：条件式解耦、xPyD/NIXL/门槛、MoE 批服务近似全激活（Kiely §5.5/§2.2.4）

精读原书后补三条本篇没讲透的工程事实。

1. 条件式解耦（conditional disaggregation）——真实流量的正确形态。 朴素解耦是“请求一律进 prefill 引擎→传 KV→decode 引擎”。条件式解耦改成：请求先进 decode 引擎，它先查“这输入是否已缓存或够短”→命中就本地处理、跳过解耦；不命中才转 prefill 引擎。原书原话：条件式解耦更适合真实流量。它把 prefix cache hit 的短请求留在 decode 侧，只把真正需要的大 prefill 才走解耦流水线。

2. xPyD 记法 + NIXL 传输 + 启用门槛。

  • xPyD：解耦不是 1:1，记作 x prefill + y decode，如 5P3D = 5 个 prefill 引擎 + 3 个 decode 引擎。新瓶颈是 prefill 队列大小（别让它涨太大：调本地 prefill 阈值 + 运行时改 xPyD 多给 prefill 资源）和 decode 侧 KV 耗尽（用量化 + offload 解）。
  • NIXL：Dynamo 用 NIXL 跨引擎传 KV，且带一个转置 kernel——当 prefill/decode 两端 TP 配置不同时把 KV block 在布局间转置。
  • 启用门槛（三件套全中才值得）：① 日 token 量 ≥100M–1B（视模型大小）；② 模型 ≥100B 参数；③ prefill-heavy 长输入。三点任一不满足就是浪费硬件。代码编辑器 + 万亿参数 LLM 是教科书场景。

3. MoE 在批服务下近似“全激活”——稀疏红利基本消失。 MoE 单请求稀疏（如 Qwen3-235B-A22B 只激活 22B/235B），但生产批处理流量下不同请求激活不同 expert，除非大规模 EP，否则几乎全参数都在活跃。这是为什么 MoE 的吞吐红利在批服务里要靠 EP 兑现、而不是“自动”获得。expert router 因体量小复制到每张卡，跨卡通信只在 token 传 expert 之间（不像 TP 要收每层结果），这正是 EP 能扩到多节点、而 TP 不能的根因。
