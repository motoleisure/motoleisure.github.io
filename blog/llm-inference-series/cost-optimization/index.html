11 · 成本优化实战：autoscaling、spot 实例、智能路由、预算门控

Tim Chan 发布于 2026 年 9 月 14 日

推理是持续燃烧的成本。这一篇讲怎么把每美元花出最大价值：从单 token 成本到集群级的弹性扩缩、spot 实例、请求路由、缓存策略，以及花真金白银前的预算门控纪律。

一、推理成本的拆解

先把成本拆成可优化的部件：

单请求成本 ≈ (GPU 租金 + 网络带宽 + 存储 + 运维) / 单位时间处理的 token 数
           ≈ GPU 成本主导（推理是 GPU 密集）

单 token 成本 = GPU $/秒 ÷ 系统吞吐 (token/秒)

优化方向：

  1. 降单 GPU $/秒：spot/preemptible 实例、 Reserved 容量、自建 vs 托管。
  2. 提吞吐：batching、量化、cache（同样 GPU 跑更多 token）。
  3. 路由：简单请求走便宜小模型，复杂走大模型。
  4. 缓存：相同请求不重复算。
  5. 弹性：按负载扩缩，闲时不浪费。

二、Autoscaling：按负载弹性扩缩

2.1 为什么推理 autoscaling 比 Web 难

Web 服务按 QPS 扩缩，响应快。推理服务：

  • 单请求慢（秒级到分钟级），扩容来不及救已经在排队的请求。
  • 冷启动重（加载几 GB-几十 GB 权重 + 模型 init 几十秒到几分钟），新副本上线慢。
  • GPU 实例稀缺，扩容不一定抢得到。

所以推理 autoscaling 要提前扩（看队列趋势），且冷启动成本要算进扩容决策。

2.2 扩缩信号

信号 优点 缺点
CPU/GPU 利用率 简单 滞后，到瓶颈才扩
请求队列长度 直接反映积压 要有队列监控
TTFT P99 用户体验直接信号 滞后
预测式（按历史模式） 提前扩 要历史数据 + 准确预测

实践组合：队列长度（主）+ GPU 利用率（辅）+ 预测（高峰前预热副本）。

2.3 冷启动优化

  • 常驻 warm pool：保留少量 warm 副本，扩容时从 warm 池取（已加载模型）。
  • 模型预热：副本启动后先跑 dummy 请求热身（编译 kernel、填 cache）。
  • 镜像优化：权重打进镜像或挂载共享存储，避免每次下载。

2.4 KPA/KEDA 示例

Kubernetes 上常用 KEDA（事件驱动 autoscaler）按自定义 metric（队列长度）扩 vLLM 副本：

# KEDA ScaledObject，按队列消息数扩缩
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
spec:
  scaleTargetRef: { name: vllm-deployment }
  minReplicaCount: 2          # warm pool
  maxReplicaCount: 20
  triggers:
  - type: rabbitmq            # 或 redis-stream / prometheus
    metadata:
      queueLength: "8"         # 每副本处理的并发
      mode: AverageThreshold

三、Spot / Preemptible 实例：省 60-90% 但有风险

3.1 收益与风险

  • 收益：spot 实例价格是按需的 1/3 到 1/10。
  • 风险：随时被回收（通知 30s-2min），要能优雅降级。

3.2 推理用 spot 的策略

  1. 混合策略：一部分 on-demand 保底（处理必须完成的），一部分 spot 拉吞吐。spot 回收时流量降级到 on-demand。
  2. 优雅终止：收到回收通知，停止接新请求，把在跑请求跑完或迁移（KV cache 迁移复杂，常直接重新 prefill）。
  3. checkpoint 复用：副本被回收前把 prefix cache 状态持久化（如 vLLM 的 KV cache 落盘），新副本恢复。
  4. 多 AZ/region 容量池：单 AZ spot 抢不到时切换。

3.3 不适合 spot 的场景

  • 长会话、强一致（agent 多轮、KV cache 强依赖）：回收中断体验差。
  • SLA 极严：宁可花钱要稳定。
  • 批处理离线推理：最适合 spot（可重试）。

四、智能路由：让便宜模型干简单活

4.1 分级路由

请求进来
  │
  ├─ 简单分类/抽取/格式化 → 小模型（便宜快）
  ├─ 中等复杂度 → 中模型
  └─ 复杂推理/长生成 → 大模型

用一个轻量分类器（甚至小 LLM）判断请求复杂度，路由到不同规模模型。简单请求占多数时，整体成本大降。

4.2 质量门控路由

Inference Lab 的 GLM 文章给了一个干净的路由范式：质量先做 gate，再按目标排名。 它比较 GLM-5.3（快但贵）和 Flash（慢但便宜）：

两个模型都通过 4/4 质量门后：
- 若目标是 correct cases/min（吞吐）→ 选 GLM-5.3
- 若目标是 correct cases/$（成本效率）→ 选 Flash

Flash 的成本效率是 GLM-5.3 的 11.9-18.4 倍（不同 workload）。"最快"和"最便宜"回答不同问题。 路由器要按你的实际目标（延迟 vs 成本）决定。

4.3 关键：质量是 gate 不是 score

不要把质量、延迟、成本压成一个分数。Inference Lab 的教训：压缩成一个分数会让"决策消失，结果看着果断其实丢了目标"。正确：质量做 gate（过了才进排名），然后选一个明确目标（吞吐 or 成本）排名。

五、缓存策略：相同请求不重算

5.1 Prefix caching（第 3 篇讲的）

system prompt、few-shot、RAG 文档、对话历史复用。这是最大的"免费午餐"——命中率高的场景 TTFT 大降、成本大降。

5.2 响应缓存（语义缓存）

对相同/相似请求直接返回缓存结果。适合：

  • FAQ / 知识问答（重复问法多）。
  • 确定性请求（temperature=0 + 固定 prompt）。

实现：用 embedding 做语义匹配，相似度高的命中。注意：

  • 缓存命中率要带 provenance（命中≠正确）。
  • 语义相似但意图不同的要谨慎（"今天天气"vs"今天天气如何"语义近但可能是不同上下文）。

5.3 缓存对成本的影响量化

prefix cache 命中率 50% → prefill 计算减半 → TTFT 成本部分降
（注意：cache 命中要和 TTFT 改善对照，别只信命中率数字）

六、预算门控：花真金白银前的纪律

Inference Lab 的 GLM 文章展示了一套值得学的预算纪律。在花托管 API 的钱之前：

6.1 dry-run 计划

authorized lifetime cap: $5.00        ← 授权总上限
planned ceiling: $0.07453260          ← 保守计划上限
final usage-block cost: $0.00615262  ← 实际花费
remaining authorization: $4.99384738

流程：

  1. 先在本地做 dry-run，写请求计划（不读 credential、不联网）。
  2. 用保守上限（按最坏 token 数 × 最坏价格）预算。
  3. 跑完后逐条核对 provider usage block 的实际 cost。
  4. 账户余额 delta 作为旁证（账户端可能 lag、含其他活动，不是主真相）。

6.2 一个重要的诚实声明

Inference Lab 老实写明：本地预算门控不是绝对的 provider 计费上限。 一个能删改 ledger 和 anchor 文件的恶意操作者能绕过；只有 provider 侧限制或外部单调服务能真正封死。所以它叫"bounded local spend control"。

实践：花公司的钱跑实验，永远先 dry-run 计划 + 预留最坏预算 + 跑完逐条核对。这是成年人心态。别"先跑跑看花了多少"。

七、成本优化的常见反模式

  1. 只看 GPU 利用率高就觉得省：利用率高但 batch 小、单 token 慢，其实贵。要看单 token 成本。
  2. 无脑堆 GPU 解延迟：延迟问题可能是调度/带宽，加卡边际收益递减。先定位瓶颈再加卡。
  3. spot 全用：回收中断体验差，长会话/强 SLA 场景翻车。混合策略。
  4. 路由只看延迟不看质量：便宜模型快但答错，correct cases/$ 反而低。质量做 gate。
  5. 缓存命中率当唯一指标：命中≠真的省了计算（第 3、10 篇讲过），要对照 TTFT。
  6. 不量化排除项：把不同契约的数字放一张表比，得出错误"最便宜"结论。

八、实践 checklist：成本优化

  • [ ] 拆解单 token成本，找最大项再优化
  • [ ] autoscaling 按队列长度+预测，保留 warm pool
  • [ ] 冷启动优化（镜像/预热/warm pool）
  • [ ] spot 混合 on-demand，长会话慎用 spot
  • [ ] 智能路由：质量做 gate，再按延迟/成本目标排名
  • [ ] prefix caching + 语义缓存，命中率对照 TTFT
  • [ ] 跑托管实验先 dry-run + 预留最坏预算 + 逐条核对
  • [ ] 看单 token 成本不只看 GPU 利用率
  • [ ] 量化排除项，别把不可比放一张表

九、原书补强：LoRA-aware 路由与 scale-to-zero 立场（Kiely §7.2.3/§7.2.4）

精读原书后补两条与成本直接相关的路由/弹性决策。

1. LoRA-aware routing。 智能 routing 不止 KV-cache-aware 一种：还有 LoRA-aware routing——把请求发到已把目标 LoRA 权重载入内存的副本，免去重复加载/切换。多 LoRA 服务时它与 KV-cache 路由并列，都是“用副本状态信息做请求级路由”。router（请求级：“这请求该去哪”）与 load balancer（系统级：“均匀分摊”）是两件事，复杂系统里两者多层交错。

2. scale-to-zero 的诚实立场。 缩容到零能省钱，但原书明确：它只适合三类——开发/测试（突发、首请求延迟无所谓）、周期性流量（如只在工作时段被调用的 agent、日批处理）、离线系统。不适合延迟敏感 + 轻量 + 无规律流量：那说明你的应用还没到该上专属基础设施的规模，先用 pay-per-token API 直到上量，别靠 scale-to-zero 硬省。冷启动速度与队列健壮性是 scale-to-zero 的两个前置条件，缺一不可。
