05 · 推理框架横评：vLLM vs SGLang vs TensorRT-LLM vs llama.cpp vs MLX

Tim Chan 发布于 2026 年 9 月 14 日

框架选型是 inference engineer 最高频的决策。选错了，不是慢几倍的问题，是某些功能根本做不了、或生产稳定性踩坑。这一篇用"决策视角"横评五大主流框架——不是 API 复读，是"什么场景该用谁、为什么"。

二、vLLM：事实标准的"通用瑞士军刀"

2.1 为什么是事实标准

vLLM 凭 PagedAttention 一战成名，加上 OpenAI 兼容 API、广泛的模型支持、活跃社区，成了开源推理的默认选择。大多数团队第一次上大模型，从 vLLM 开始不会错。

2.2 优势

  • 模型覆盖最广：几乎所有主流开源模型 day-0 支持（Llama、Qwen、Mistral、DeepSeek、GLM、多模态）。
  • PagedAttention + continuous batching + prefix caching 三件套默认开，开箱即用。
  • OpenAI 兼容 API：客户端代码几乎不用改。
  • 量化全谱：AWQ、GPTQ、FP8、INT8、bitsandbytes 都支持。
  • 生产特性齐：LoRA 热加载、多模态、speculative decoding、chunked prefill、disaggregated prefill。

2.3 什么时候不用 vLLM

  • 要极致 kernel 性能且只有 NVIDIA 卡 → TensorRT-LLM 可能更快。
  • 重度结构化输出 / agent 场景 → SGLang 的 RadixAttention 更强。
  • 边缘 / CPU / Apple Silicon → llama.cpp 或 MLX。

2.4 启动一个 vLLM 服务（实战）

# 基础启动
vllm serve Qwen/Qwen2.5-14B-Instruct \
  --tensor-parallel-size 2 \
  --max-model-len 32768 \
  --enable-prefix-caching \
  --gpu-memory-utilization 0.90 \
  --port 8000

# 客户端（OpenAI 兼容）
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-14B-Instruct",
    "messages": [{"role":"user","content":"用一句话解释 KV cache"}],
    "max_tokens": 100
  }'

关键参数解读：

  • --tensor-parallel-size：张量并行卡数。70B+ 模型单卡放不下要开。
  • --max-model-len：最大上下文。影响 KV cache 预分配，别设太大（吃显存）。
  • --enable-prefix-caching：开前缀缓存（V1 默认开）。
  • --gpu-memory-utilization：GPU 显存利用率上限，留余量给系统。

2.5 vLLM 的坑

  • 编译模式（VLLM_COMPILE）有冷启动债。Inference Lab 的 vLLM 编译对比实测：compiled 配置 12 个请求的 complete-response latency 总和低 5.8 秒，但初始化多了 54 秒。"编译更快"不等于"上线更快"——要算上冷启动债，看多少请求才能回本（那次实验要 113 个请求才建模回本，但只跑了 12 个，所以不能声明 break-even）。
  • 版本迭代快，breaking change 多：固定版本 + 锁 commit。
  • V0 vs V1 引擎：V1 是新架构（更快的调度、默认 prefix cache），但部分功能还在迁移。看清楚你跑的是哪个。

三、SGLang：结构化/Agent 场景的"新锐"

3.1 为什么值得关注

SGLang（LMSYS 出品）的核心创新是 RadixAttention：用基数树管理所有请求的 prompt 前缀，自动找最长公共前缀复用 KV cache。对以下场景效果显著：

  • Agent / 多轮对话：每轮都带相同 system prompt + 工具定义 + 历史。
  • 结构化输出：JSON 模式、正则约束（SGL 语法），对 tool calling 场景原生优化。
  • few-shot / RAG：固定示例或文档被反复引用。

它的 speculative decoding 也很激进（社区已有 DFlash、Spec V2 等新一代方案）。

3.2 实战启动

# SGLang 服务
python -m sglang.launch_server \
  --model-path Qwen/Qwen2.5-14B-Instruct \
  --tp 2 \
  --port 30000 \
  --enable-radix-cache

3.3 适合与不适合

  • 适合：agent 平台、tool-heavy 应用、需要大量结构化 JSON 输出、多轮长对话。
  • 不适合：单次冷 prompt 生成（RadixAttention 优势发挥不出来）、纯边缘部署。

四、TensorRT-LLM：NVIDIA 官方的"极限 kernel"

4.1 定位

TensorRT-LLM 是 NVIDIA 基于 TensorRT 的 LLM 推理库，把 kernel 优化做到极致：融合算子、FP8、INT4/INT8 weight-only、in-flight batching、KV cache quantization。

4.2 优势

  • 极致延迟/吞吐：在 NVIDIA 硬件上，kernel 级优化通常最好。
  • FP8 原生：Hopper/Blackwell 上 FP8 是杀手锏。
  • in-flight batching：NVIDIA 版的 continuous batching。

4.3 代价

  • 要编译：模型要先 build 成 TensorRT engine（几分钟到几十分钟），不像 vLLM 直接 load。改个参数要重新 build。
  • 模型支持滞后：新模型要等官方适配，不如 vLLM/SGLang 灵活。
  • 绑定 NVIDIA：跨厂商部署不行。
  • 学习曲线陡。

4.4 什么时候用

  • 大规模生产、稳定模型、追求极致 GPU 利用率、有 NVIDIA Hopper/Blackwell 集群。

五、llama.cpp：边缘与 Apple Silicon 的王者

5.1 定位

llama.cpp 是 C/C++ 实现的推理引擎，无依赖、跨平台、CPU/GPU/Apple Silicon 混合。它的 GGUF 量化生态（Q4_K_M 等）是本地部署的事实标准。

5.2 优势

  • 零部署门槛：单二进制，不需要 Python/CUDA 环境。
  • CPU 也能跑：没 GPU 的服务器、笔记本、树莓派都行。
  • Apple Silicon 极致优化：用 Metal/MPS，统一内存利用率高。
  • GGUF 量化生态最全：Q2 到 Q8，混合精度（k-quant）。
  • 社区极大：TheBloke / bartowski 等量化了几乎所有模型。

5.3 代价

  • 吞吐不如 vLLM/SGLang：单请求延迟还行，高并发批处理弱（不是为大规模服务设计的）。
  • 多卡弱：张量并行支持有限。
  • 新模型适配滞后：复杂架构（如 MoE）支持慢一拍。

5.4 什么时候用

  • 本地开发原型、边缘设备、无 GPU 环境、Apple Silicon 本地推理、个人/小团队部署。

5.5 Inference Lab 的关联

Inference Lab 文章里的本地实验大量用了 llama.cpp / MLX 做对照（比如 GLM 托管 vs 本地 Qwen3-8B MLX 对照、27B OOM 尸检用 MLX）。本地小模型是验证托管结果、做 dry-run 的好工具。

六、MLX / mlx-lm：Apple Silicon 原生

6.1 定位

MLX 是 Apple 官方的机器学习框架（类似 PyTorch 但为 Apple Silicon 统一内存设计）。mlx-lm 是上面的 LLM 推理包。

6.2 优势

  • 统一内存：Apple Silicon 的 CPU 和 GPU 共享内存，不需要 CPU-GPU 拷贝（MLX 文档强调这点）。
  • 量化简单：mlx_lm.convert --q-bits 4 一行量化。
  • Python API 友好：from mlx_lm import load, generate。
  • mlx-community 生态：HF 上 mlx-community 量化了海量模型。

6.3 代价

  • 只跑 Apple Silicon：不能上 NVIDIA/AMD GPU 集群。
  • 吞吐有限：适合本地/原型，不是大规模服务。
  • 生产服务特性弱：没有 vLLM 那套连续批处理/调度。

6.4 关键认知（来自 Inference Lab OOM 文章）

"权重放得下"不等于"推理跑得动"。 Inference Lab 实测：16 GB 权重的 27B 模型，在 24 GiB M5 Pro 上，clean boot 79% 空闲内存，256 token prompt 就 OOM。因为：

  • 可用显存 ≠ 物理内存（系统、其他进程占走一部分）。
  • 推理峰值 = 权重 + KV cache + 激活 + 临时 workspace + 框架开销。
  • MLX active/cache/peak、RSS、swap 是四套不同账本，不能加成一个数。

这是 MLX 用户最容易踩的坑：看着 24G 内存、16G 权重，以为随便跑，结果小 prompt 就 OOM。原因在于"文件字节 ≠ 推理内存预算"。

七、选型决策树

你的部署目标是？
│
├─ 大规模生产服务（高 QPS）
│   ├─ NVIDIA H100/B200 → TensorRT-LLM（极致） 或 vLLM/SGLang（灵活）
│   ├─ A100/消费级 GPU → vLLM（默认） 或 SGLang（agent/结构化）
│   └─ 多厂商混部 → vLLM（兼容性最好）
│
├─ 中小规模 / 团队内部
│   └─ vLLM（默认，生态最广）
│
├─ 重度 agent / 结构化输出
│   └─ SGLang（RadixAttention + 语法约束）
│
├─ 本地 / 边缘 / 无 GPU
│   ├─ Apple Silicon → MLX 或 llama.cpp
│   ├─ CPU only → llama.cpp（GGUF Q4_K_M）
│   └─ 消费级单卡 → vLLM 或 llama.cpp
│
└─ 原型 / 实验 / dry-run
    └─ 任意，按熟悉度选（Inference Lab 倾向 MLX + llama.cpp 做本地对照）

八、一个常被忽略的选型维度：可比性

Inference Lab 的 GLM 文章提了一个深刻观点：选型时不要只看延迟/成本数字，要看数字背后的契约。

它举了个例子：本地 Qwen3-8B MLX 跑出 23.12 correct cases/min，托管 GLM-5.3 跑出 18.3。能不能把 Qwen 放进托管排行榜当"最快"？不能，因为契约不同：

  • 不同模型身份（Qwen3-8B vs GLM-5.3）
  • 不同运行时（MLX 本地 vs 托管 client timing）
  • 不同推理模式（本地 thinking 关闭 vs 托管强制 reasoning）
  • 不同 seed、不同系统身份

一个图表能对齐任何三个数字，但不等于它们的分母相等。 选型横评时，要么把契约对齐（同一模型、同一硬件、同一测量方法），要么明确标注"这是不同契约下的观察，不可直接排名"。把不可比的放一张表里，是误导。

九、实践 checklist：框架选型

  • [ ] 先按部署目标（大规模/中小/边缘/原型）分流，再在分支内选
  • [ ] 评估时对齐契约：同模型、同硬件、同测量方法、同输出 cap
  • [ ] 算上冷启动债（编译/加载时间），别只看稳态延迟
  • [ ] 测你要的场景（agent？长上下文？结构化？），不只跑通用 benchmark
  • [ ] 锁定框架版本 + commit，避免 breaking change
  • [ ] 对每个框架记一份"已知坑"清单，团队共享
