02 · 推理基础原理：一个 prompt 进来，GPU 上到底发生了什么

Tim Chan 发布于 2026 年 9 月 14 日

上一篇讲了岗位定位。这一篇回到最底层：一个 prompt 从进入推理引擎到吐出最后一个 token，GPU 上发生了什么。理解了 prefill/decode 两阶段、memory-bound 本质，你才能看懂后面所有优化（KV cache、量化、batching）到底在优化什么。

上一篇讲了岗位定位。这一篇回到最底层：一个 prompt 从进入推理引擎到吐出最后一个 token，GPU 上发生了什么。理解了 prefill/decode 两阶段、memory-bound 本质，你才能看懂后面所有优化（KV cache、量化、batching）到底在优化什么。

一、推理 vs 训练：看起来像，实则完全不同

很多人从训练迁移到推理，会带着错误直觉。先把差异讲清楚：

维度 训练 推理
方向 前向 + 反向（前向算 loss，反向算梯度） 只前向
batch 通常固定、大、凑满 动态、请求随时来随时走
计算密度 高（矩阵乘都是大块 GEMM，compute-bound） prefill 较密，decode 极稀疏（memory-bound）
关键状态 优化器状态、梯度 KV cache（要长期驻留显存）
瓶颈 算力 FLOPS 显存带宽（尤其是 decode）
目标 降低 loss 降低延迟 + 提高吞吐 + 降成本

最关键的认知是最后一行：训练优化算力，推理优化带宽。 这一行决定了本系列后面几乎所有的技术选择。

二、Transformer 前向：从 token 到 logits

一个大模型推理的"一次前向"，本质是这么一回事（以 decoder-only 的 GPT 风格模型为例）：

输入 token ids: [t1, t2, ..., tn]
   │
   ▼  embedding 查表
   [E1, E2, ..., En]   每个 token 变成一个向量
   │
   ▼  过 N 层 Transformer block
   每层 = LayerNorm → Attention → 残差 → LayerNorm → MLP → 残差
   │
   ▼  最后一层 hidden state
   [h1, h2, ..., hn]
   │
   ▼  lm_head（线性层，共享或独立的 embedding 矩阵）
   logits: [l1, l2, ..., ln]   每个位置一个词表大小 V 的分布
   │
   ▼  对最后一个位置 ln 做 softmax + 采样
   下一个 token: t_{n+1}

两个要点：

  1. attention 让每个位置都能"看到"前面所有位置。这要求对每对 (i, j), j ≤ i，算一个 attention score。代价是 O(n²) 的，但更致命的是它需要每层的 K 和 V 向量。
  2. autoregressive：一次前向只生成一个新 token。要生成 100 个 token，就要跑 100 次前向。每次前向，前面所有 token 的 K/V 都要重新算（除非缓存）——这就是 KV cache 存在的理由。

三、KV Cache：为什么需要它，它有多大

3.1 没有 KV cache 时发生了什么

假设不缓存。生成第 k 个 token 时，模型要对位置 1..k 算 attention。这意味着重新计算位置 1..k-1 的 K 和 V——而这些在第 1..k-1 步早就算过了。复杂度退化到 O(n³) 级别的重复计算。 这不可接受。

所以所有现代推理引擎都缓存：每生成一个 token，只算新位置的 Q/K/V，把新的 K/V 追加到缓存里。下一层 attention 时，新 Q 和缓存里所有旧 K 做点积。

生成第 1 个 token：算 K1,V1，缓存 [K1,V1]
生成第 2 个 token：算 K2,V2，缓存 [K1,V2,...]，新 Q2 与 [K1,K2] 算 attention
...
生成第 k 个 token：只算新位置的 Qk,Kk,Vk，复用缓存里 k-1 个旧 K/V

这就是 KV cache：用空间换时间，把重复的 attention 计算变成一次 O(1) 追加 + 一次 O(k) 的 attention。

3.2 KV cache 有多大：一个必须会算的数

很多人不会算这个，结果部署时 OOM 才懵。学会 back-of-envelope 估算 KV cache 大小，是 inference engineer 的基本功。

公式：

KV cache 字节数 = 2 (K和V) × num_layers × seq_len × hidden_dim × dtype_bytes × batch_size

对一个 Llama-3-8B（32 层，hidden 4096，FP16）跑 batch=1、序列长 8192：

2 × 32 × 8192 × 4096 × 2 (fp16) = 4,294,967,296 字节 ≈ 4.0 GB

光 KV cache 就 4 GB，而 8B 模型权重 FP16 才 16 GB。序列越长，cache 占比越高。到 32K 上下文，KV cache 就 16 GB，和权重一样大。到 128K，KV cache 64 GB——比模型本身大 4 倍。

这就是为什么长上下文推理特别贵：不是计算贵，是显存贵，KV cache 随序列线性涨。也是为什么 GQA / MQA（减少 KV 头数）能省 cache、为什么 PagedAttention 能省碎片。

实践提示：面试和容量规划时，永远先算这三个数：权重、KV cache（按你最长序列+最大 batch）、激活/临时。三者加起来要小于可用显存，留 10-20% 余量。Inference Lab 的 OOM 文章里，一个 16 GB 权重的模型在 24 GiB Mac 上 256 token 就 OOM——因为可用显存不是 24 GiB，而是被系统、激活、KV cache 吃掉后的剩余。

四、Prefill vs Decode：推理的两个截然不同阶段

这是本篇最核心的认知。推理不是"一次前向"，而是两个计算特性完全相反的阶段：

4.1 Prefill（预填充阶段）

用户发来一个 prompt（比如 2000 token）。引擎要把它一次"吃进去"：对整段 prompt 做一次完整的前向，算出所有位置的 hidden state，并把这段 prompt 的 K/V 写进 KV cache。

  • 特点：一次前向处理一长串 token。attention 是大块矩阵乘（prompt 长度 × 隐藏维度），计算密度高，compute-bound。
  • 时间：和 prompt 长度大致成 O(n²) 关系（attention 部分）。2000 token 的 prefill 通常几十到上百毫秒。
  • TTFT 的主要来源：用户发的请求到第一个 token 出现，大头就是 prefill（加上排队、网络）。

4.2 Decode（解码阶段）

prefill 完后，引擎开始一次一个 token地生成。每生成一个 token：算这个 token 的 Q/K/V，把 K/V 追加到 cache，新 Q 和 cache 里所有 K 做 attention，最后采样。

  • 特点：每次只处理 1 个 token，但要把整个模型权重读一遍。计算密度极低，memory-bound。GPU 计算单元大部分时间空转，等权重从 HBM 搬过来。
  • 时间：每个 token 几毫秒到几十毫秒。生成长输出时，decode 总时间 = 单 token 时间 × 输出长度。
  • TPOT（time per output token）的主要来源。

4.3 两个阶段的对比（这张表请记牢）

Prefill Decode
一次处理几个 token 整段 prompt（几十到几千） 1 个
计算密度 高 极低
瓶颈类型 compute-bound（偏算力） memory-bound（偏带宽）
主要影响指标 TTFT TPOT / 吞吐
attention 形状 大块 GEMM 一个 Q × 全部 K
优化方向 chunked prefill、并行 batch、prefix caching、量化、投机解码

这个区别解释了几乎一切推理优化设计的动机：

  • 为什么 continuous batching 按 iteration 级别调度？因为 decode 阶段每个请求的长度不同，要能动态插拔。
  • 为什么 prefix caching 有用？因为 prefill 是 TTFT 大头，相同前缀的 prompt 复用 cache 就能跳过 prefill。
  • 为什么量化对 decode 提速明显？因为 decode 是 memory-bound，权重小一半，搬运时间就少一半。
  • 为什么 chunked prefill 把长 prompt 切块？防止一个长 prefill 独占 GPU、阻塞 decode，让两者交错执行。

实践直觉：拿到一个性能问题，第一步永远是判断它卡在 prefill 还是 decode。TTFT 高 → prefill 慢（看 prompt 长度、排队、prefix cache 命中）。TPOT 高 / 吞吐低 → decode 慢（看 batch、量化、带宽）。两个阶段要分开测、分开优化，不要混成一锅。

五、采样：token 是怎么选出来的

前向算完，最后一层 lm_head 给出 logits（词表大小 V 的原始分数）。要变成"下一个 token"，还要经过采样。这一步看似简单，但有几个坑：

5.1 采样参数

  • temperature：logits / T。T→0 趋近 argmax（确定性），T 高则更随机。
  • top-k：只在 logits 最高的 k 个里采样。
  • top-p（nucleus）：选概率累计达 p 的最小 token 集，在里面按概率归一化采样。
  • repetition penalty / frequency penalty：惩罚已出现 token，防重复。

5.2 工程上的坑

  1. 采样是非确定性的。同样 prompt 不同次结果不同。对比实验时要么 temperature=0，要么固定 seed 并记录。
  2. 采样本身有开销。词表 V 可能十几万（如 GPT-4 的 tiktoken 词表、Qwen 的 15 万），softmax + top-p 排序在 CPU 上也要几毫秒。高 QPS 场景这会成为瓶颈，有些引擎会把它放到 GPU 或用 fused sampling kernel。
  3. structured output（JSON 模式） 要在采样层强行约束只允许合法 token。vLLM/SGLang 都有 guided decoding（正则/JSON schema 约束），代价是采样变慢，但保证输出合法。

5.3 停止条件

生成什么时候停？三个条件：

  1. EOS token：模型输出结束符。
  2. max_tokens：达到上限。
  3. stop strings：匹配到指定字符串（API 的 stop 参数）。

注意：没收到合法终止信号的流不算成功。Inference Lab 的 TTFT 文章专门讲了这点——连接半截断了、没收到 [DONE] 或 finish_reason 的，应该标 truncated 而不是 success。一个把半截流算成功的 benchmark，会奖励"坏但快"的响应。

六、把一次推理画成时间线

把上面拼起来，一个完整的请求时间线长这样（以 streaming API 为例）：

t0  客户端发出请求
    │  网络传输 + 网关排队 + provider 排队   ← TTFT 里"非计算"的部分
    ▼
t1  引擎拿到请求，开始 prefill                ← TTFT 的计算大头
    │  prefill: 处理整段 prompt，写 KV cache
    ▼
t2  第一个 token 生成，开始流式返回           ← TTFT 到这里结束（客户端可见）
    │  decode: 一个一个 token 生成
    │  每个 token: 读权重 + 读 KV cache + attention + 采样
    ▼
t3  最后一个 token / EOS / 达到 max_tokens
    │  终止信号（finish_reason / [DONE]）
    ▼
t4  客户端收到完整响应                        ← 完整响应延迟 E2E

对应的指标：

  • TTFT = t2 - t0（首 token 延迟）
  • TPOT = (t3 - t2) / 输出 token 数（每 token 延迟）
  • E2E latency = t4 - t0（完整响应延迟）
  • 吞吐 = 总 token 数 / 总时间（多请求并发时）

七、实践 checklist：理解推理生命周期

  • [ ] 能背出 KV cache 字节数公式，会算任意模型的 cache 大小
  • [ ] 能说出 prefill 和 decode 的 5 个区别（计算密度、瓶颈、影响指标…）
  • [ ] 拿到一个延迟问题，能判断该看 prefill 还是 decode
  • [ ] 知道 TTFT、TPOT、E2E、吞吐的正确定义和它们之间的关系
  • [ ] 理解为什么没收到终止信号的流不算成功
  • [ ] 能解释"为什么推理是 memory-bound 而 decode 尤其是"
