06 · 连续批处理与调度：iteration-level batching、抢占、优先级

Tim Chan 发布于 2026 年 9 月 14 日

如果说 KV cache 是推理引擎的心脏，调度器就是大脑。它决定 GPU 在每一毫秒干什么、哪个请求先跑、谁被挤掉。理解连续批处理和调度策略，你才能解释"为什么并发高了反而更慢"、"为什么有的请求延迟突刺"。

如果说 KV cache 是推理引擎的心脏，调度器就是大脑。它决定 GPU 在每一毫秒干什么、哪个请求先跑、谁被挤掉。理解连续批处理和调度策略，你才能解释"为什么并发高了反而更慢"、"为什么有的请求延迟突刺"。

一、从静态批处理说起：它为什么不行

1.1 静态批处理（naive batching）

最朴素的做法：攒够 N 个请求，凑成一个 batch，一起跑，等最长的那个结束才解锁，再放下一个 batch。

问题：

  • 队头阻塞：batch 里有个请求要生成 500 token，另一个只要 20 token。那个 20 token 的请求干等 480 个 token 的时间才和 batch 一起结束返回。它的延迟被最慢的请求拖垮。
  • 凑 batch 的等待：要凑 N 个才跑，低峰期请求来了要等。TTFT 爆炸。
  • GPU 空转：凑 batch 期间 GPU 闲着；batch 里多数请求结束了但等最长那个时，GPU 又只跑一个请求，利用率低。

1.2 连续批处理（continuous / iteration-level batching）

核心思想：不以"batch"为调度粒度，而以"iteration（生成一个 token 的步骤）"为粒度。 每个 iteration 结束后，调度器重新决定 batch 里有哪些请求：

  • 有请求生成完了？移出 batch，立刻返回结果。
  • 有新请求到了？如果显存够，立刻塞进 batch，开始 prefill。
  • batch 里还剩的请求继续 decode。

效果：GPU 几乎从不空转，新请求零等待加入，短请求不被长请求拖。这就是 vLLM/SGLang/TGI 吞吐远高于静态批处理的原因。

二、调度器的核心难题

连续批处理把调度从"批"细化到"iteration"，但带来几个难题：

2.1 何时插新请求：prefill vs decode 的资源争用

新请求加入要先 prefill。但 prefill 是 compute-bound 的大块计算，一个长 prompt prefill 时会独占 GPU，阻塞正在 decode 的请求，造成 decode 请求延迟突刺（TPOT 飙高）。

两种解法：

  • Prefill priority（prefill 优先）：来一个 prefill 一个，decode 等。TTFT 低，但 decode 延迟不稳。
  • Decode priority（decode 优先）：先保证 decode 平滑，prefill 排队。decode 稳，但 prefill 排队长 → TTFT 高。

实际引擎用混合策略，配合下面的 chunked prefill。

2.2 Chunked Prefill：把长 prefill 切块

vLLM/SGLang 的解法：把一个长 prompt 的 prefill 切成固定大小的块（如 512 token 一块），和 decode iteration 交错执行。

iteration 1: [prefill chunk 1] + [decode req A, B, C]
iteration 2: [prefill chunk 2] + [decode req A, B, C]
...
iteration n: [prefill chunk n 完成] → 新请求 D 加入 decode

这样长 prefill 不再独占 GPU，decode 请求的延迟更平滑。代价是单个长 prompt 的 TTFT 略升（prefill 被拆散），换来整体平滑。

2.3 显存不足时：抢占

显存不够放新请求的 KV cache 时，调度器要回收。vLLM 的做法（上一章讲过）：

  • RECOMPUTE：丢掉某请求的 cache，显存空了再从头 prefill（prefix cache 能恢复一部分）。
  • SWAP：把 cache 搬到 CPU 内存，需要时搬回。

被抢占的请求延迟突增。生产监控指标：抢占频率。频繁抢占 = 容量不足，加卡或限流。

三、调度策略详解

3.1 FCFS（先来先服务）

最简单：按请求到达顺序排队，显存够就塞进 batch。公平但可能让 VIP 请求等。

3.2 优先级调度

多租户场景按优先级：

P0 VIP 请求：优先塞 batch，必要时抢占低优先级
P1 付费用户：正常调度
P2 免费用户：best-effort，闲时才跑

实现：vLLM 支持请求优先级（部分版本），SGLang 有多队列。代价：低优先级请求可能饿死，要配 aging（等待久了提升优先级）。

3.3 短作业优先（SJF）变体

预知输出长度时，优先跑短请求，减少队头阻塞。但 LLM 输出长度通常不可预知，所以实际用估计（基于 prompt 类型/历史）或 max_tokens 上限做近似。

3.4 公平调度（fair scheduling）

SGLang 用 fair scheduling，给每个租户/请求类一个时间片配额，防止某个大户挤占所有资源。

四、一个 iteration 调度器的决策流程

把上面拼起来，一个 iteration 结束时调度器大概这样决策：

1. 检查 batch 内请求
   - 有请求生成完 / 达到 max_tokens / EOS？→ 移出，返回结果，释放 KV cache block
   
2. 检查显存
   可用 KV cache 池 = 总池 - 已占用 block
   能再容纳几个新请求的 cache？

3. 从等待队列选请求加入（按策略）
   - FCFS：队首
   - 优先级：最高优先级
   - 估计 cache 大小（input_len × cache_per_token + 预留 output）
   
4. 显存不够？
   - 尝试驱逐（LRU）空闲低价值 cache
   - 还不够 → 抢占低优先级请求（recompute / swap）
   - 都不行 → 新请求继续排队（TTFT 上升）

5. 决定这个 iteration 的混合
   - 有 prefill 待跑：和 decode 交错（chunked prefill）
   - 全是 decode：纯 decode iteration

6. 执行前向，回到 1

五、调度对延迟分布的影响：为什么有突刺

理解调度后，很多"诡异"延迟现象就解释通了：

5.1 P99 远高于 P50

请求大部分时间跑得快（P50 好），但偶尔遇到：恰好赶上大批 prefill 涌入、被抢占、显存紧张被 swap。这些请求被拖到 P99。只看平均延迟会掩盖这些长尾。 生产必须看 P95/P99。

5.2 并发升到某点后延迟陡升

并发低时，调度器游刃有余，延迟平稳。到某个临界点，KV cache 池满了，开始抢占/排队，延迟陡升。这个拐点就是你的有效容量上限。压测要找到它，而不是无脑堆并发看延迟一直涨。

5.3 TTFT 和 TPOT 可能此消彼长

调 prefill 优先 → TTFT 降但 decode 突刺多；调 decode 优先 → decode 稳但 TTFT 排队长。这是个权衡，没有免费午餐。要根据业务对 TTFT 还是 TPOT 更敏感来调。

六、关键可调参数（vLLM 为例）

vllm serve model \
  --max-num-seqs 256 \         # 同时在跑的最大请求数（batch 上限）
  --max-num-batched-tokens 8192 \  # 单 iteration 最大 token 数（prefill+decode）
  --gpu-memory-utilization 0.90 \  # 显存利用率上限
  --max-model-len 32768 \       # 最大上下文（影响 KV cache 预留）
  --enable-prefix-caching \     # 前缀缓存
  --preemption-mode swap        # 抢占模式：swap 或 recompute

调参思路：

  • --max-num-seqs：太大 → 每个 request KV cache 摊薄，易抢占；太小 → 并发上不去。
  • --max-num-batched-tokens：控制单 iteration 计算量。chunked prefill 时决定 prefill 块大小。
  • --gpu-memory-utilization：留 10% 给系统/临时。0.95+ 容易 OOM。

七、调度相关的生产监控指标

指标 含义 告警阈值思路
running / waiting 请求数 在跑 vs 排队 waiting 持续 > running 说明容量不足
抢占次数 / 分钟 recompute/swap 频率 >0 持续 = 容量紧
KV cache 利用率 已用 / 总池 >90% 危险
prefix cache 命中率 前缀复用率 突降 = prompt 模式变了
TTFT P50/P99 首 token 延迟分位 P99 突升 = prefill 拥塞
TPOT P50/P99 每 token 延迟分位 P99 突升 = decode 抢占
GPU 利用率 计算单元占用 低 + 高延迟 = 调度/带宽问题

八、实践 checklist：调度调优

  • [ ] 压测找到"延迟陡升拐点"，那是你的有效容量，别超它定 SLO
  • [ ] 看 P95/P99 不只看 P50，长尾才是用户体验
  • [ ] 监控 waiting 队列长度和抢占频率，持续 >0 = 该扩容
  • [ ] 长 prompt 场景开 chunked prefill，防 decode 突刺
  • [ ] 多租户设优先级 + aging，防 VIP 被挤、免费用户饿死
  • [ ] TTFT 敏感业务调 prefill 优先；TPOT 敏感调 decode 优先
  • [ ] KV cache 利用率留 10%+ 余量，别顶到 100% 抢占
  • [ ] max-num-seqs 不是越大越好，要和显存/KV cache 池平衡
