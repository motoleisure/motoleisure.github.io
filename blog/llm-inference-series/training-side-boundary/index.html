19 · 训练侧边界认知：inference engineer 该懂的 9 件事

一、为什么推理工程师要懂训练侧

两个真实交叉点：

  1. checkpoint 是训练侧决策的产物：模型用了 BF16 还是 FP16 训、有没有 QAT、MoE 路由怎么均衡——这些都固化在权重里，推理时改不了，但影响你怎么部署。
  2. 推理侧的并行/通信概念来自训练侧：TP/PP/DP/ZeRO/通信原语最早都是训练概念，推理的多卡并行（第 09 篇）就是它们的"服务化复用"。看懂训练侧才能看懂推理侧 bubble 来源。

Atlas 把这 9 项明确标成 Training-systems / Distributed-training engineer 的责任，不是 inference engineer 的。本篇定位 = 边界认知，不是"教你训练"。

二、QAT（Quantization-Aware Training，#13）

  • 是什么：训练时在 forward 里模拟量化误差（伪量化），让模型在反向时"适应"低精度，从而量化后质量比纯 PTQ 好。
  • 和 PTQ 的边界（第 04 篇）：PTQ 是推理工程师的事（训完用校准数据转换），QAT 是模型方的事（要重训，成本高）。
  • inference engineer 要懂：你拿到的"INT4 模型"是 PTQ 还是 QAT 训出来的，质量差很多——QAT 通常质量更高。选模型时问清楚。

三、Activation Checkpointing（#25）

  • 是什么：训练时不存全部前向激活，反向时重算前向激活——用算力换显存（"用时间换空间"）。
  • 推理侧也有用：长上下文 prefill 时，激活很占显存。某些推理框架在 prefill 阶段也对长序列做激活重算，省显存换延迟——这正是第 13 篇 chunked prefill 背后的同类思想（把长 prefill 拆小，激活峰值降低）。
  • inference engineer 要懂：长上下文 OOM 时，"重算激活"是一个选项（不是只有 offload KV cache）。但要算清重算成本 vs offload 成本——和第 17 篇"搬回 vs 重算"同一个权衡。

四、Sequence Packing（#26）

  • 是什么：训练时把多个短序列拼（pack）成一条长序列一起跑，填满 batch 的算力，避免 padding 浪费。靠 attention mask 把不同序列隔开（block-diagonal mask）。
  • 对推理心智的影响：
  • 训练时 packing 让模型见过"拼接长序列"，推理时变长 batch 也类似——调度心智一致。
  • 影响 tokenizer / 调度：推理侧的变长 batch 调度（continuous batching，第 06 篇）是 packing 的服务化版本。
  • inference engineer 要懂：为什么框架能高效处理变长——根子在训练侧的 packing 设计。

五、Mixed-precision Training（#27）

  • 是什么：训练用 FP16/BF16（甚至 FP8）做前向/反向，主权重用 FP32 维护（master weights）。
  • Atlas 的关键告诫："BF16 和 FP16 指数范围不同；FP16 风格的 loss scaling 不是 BF16 通用。"——
  • FP16 动态范围小，要 loss scaling 防梯度下溢。
  • BF16 动态范围和 FP32 一样（指数位多），通常不需要 loss scaling。把 FP16 的 loss scaling 套到 BF16 是常见错误。
  • inference engineer 要懂：模型是 BF16 还是 FP16 训的，影响你推理时的精度选择（BF16 模型推理直接用 BF16，不用操心 scaling）。

六、DDP（Data-Parallel Training，#28）

  • 是什么：每个 GPU 拿完整模型副本，跑不同数据 batch；反向后all-reduce 同步梯度，各卡梯度一致后各自更新。
  • 核心 = all-reduce：这就是第 09 篇"通信原语"的源头。DDP 的同步成本 = 每步一次全模型梯度的 all-reduce。
  • 和推理侧 DP 的区别（第 09 篇 4.3）：推理的 DP 是"多副本各跑各的请求"，不需要同步（没有梯度）——所以推理 DP 便宜得多。训练 DDP 贵在每步 all-reduce。
  • inference engineer 要懂：为什么"训练的 DP"和"推理的 DP"听起来一样、成本差几个数量级——训练要同步梯度，推理不用。

七、ZeRO State Sharding（#29）

  • 是什么：DDP 每卡存完整模型副本太贵。ZeRO 把优化器状态 / 梯度 / 参数分片到各卡（ZeRO-1/2/3 逐步分片更多），用 all-gather 在需要时重组。
  • Atlas 的关键告诫："ZeRO 内存减少取决于 exact state 和 layout。Avoid universal 4×/8× claims."——
  • 别信"ZeRO-3 省 8 倍显存"这种万能数字，取决于分了什么 state、什么 layout、通信能不能藏住。
  • ZeRO-3 省 memory 但增加通信（all-gather 参数），是 memory↔communication 的交换。
  • inference engineer 要懂：
  • ZeRO 是训练时技术，推理一般不用（推理没优化器状态要分）。但理解它才能看懂"为什么训练能单卡放不下、靠 ZeRO 切开训"。
  • 推理侧对应的"分片"是 TP（切参数）——ZeRO-3 切的是优化器/参数副本，TP 切的是计算。

八、GPipe / PipeDream / Zero-bubble（#31 / #32 / #33）——流水线调度演进

这三项是训练侧流水线并行（Pipeline Parallelism）的调度演进。理解它们才能看懂推理侧 pipeline parallelism（第 09 篇 4.2）的 bubble 从哪来、怎么藏。

8.1 GPipe（朴素）

  • 把模型按层切到多卡（卡 1 跑前几层、卡 2 跑后几层），micro-batch 串行流过。
  • 朴素 GPipe = 先全部 forward micro-batch，再全部 backward。问题：前向时反向卡在空等，bubble 大（流水线灌满前的空泡）。

8.2 PipeDream / 1F1B

  • 改成 1F1B（一个 forward 紧跟一个 backward）交替调度，让前向和反向重叠，bubble 变小。
  • 代价：需要管理多版本权重（不同 micro-batch 用不同 step 的权重），PipeDream 就是为这个设计的。

8.3 Zero-bubble（ZB / ZB-H1）

  • 更激进：在 1F1B 基础上把通信和计算重叠到极致（ZB-H1 调度），把 bubble 进一步压到接近零。

  • 用"把 backward 拆成 B1/B2 两段、在中间塞通信"实现重叠。

  • Atlas #33 列出的具名变体（inference engineer 听到能对上号即可）：ZB-H1 / ZB-H2（不同显存约束下的调度设计）、breadth-first 与 depth-first looped schedule（虚拟 stage 排序方式不同）、Llama 式 stage balancing（把层围绕昂贵边界重分布）、DualPipe（DeepSeek-V3，双向流水线重叠计算与通信）。命名调度不是通用保证，每种都要各自的 trace + 收敛核对——和 Atlas“别喊通用 4×/8×”同源。

8.4 对推理侧的意义

  • 推理的 PP（第 09 篇）bubble 来源 = 训练 GPipe 同款"灌满前的空泡"。
  • 推理侧用 inflight batching + micro-batch 流水来填 bubble——思路和 1F1B 同源。
  • inference engineer 要懂：推理 PP 的延迟开销不是"切层"本身，是 bubble。优化 PP 的方向 = 减 bubble = 训练侧 1F1B/Zero-bubble 的服务化映射。

十、责任边界：训练期 ≠ 服务期

Atlas 在 limits 里反复强调的一条，跨这些技术通用：

"Training-time MoE balancing objectives are different from serving-time expert placement. Dropping tokens can change quality." "训练期的 MoE 均衡目标 ≠ 服务期 expert 放置。丢 token 会改变质量。"

推广到全篇：训练时的优化目标 / 路由规则 / 精度策略，固化进权重后，推理时不能随便改——

  • 训练用 top-1 MoE 路由，服务期别随便改成 top-2（改路由 = 改模型行为）。
  • 训练用 BF16，推理别"为了省显存降 FP8"而不测质量。
  • 训练用 ZeRO 切开训，推理用 TP 切开服务——切的东西不同，别混为一谈。

这和第 14 篇 Inference Lab 方法论、"测量边界先于指标"完全同源。

十一、实践 checklist：训练侧边界认知

  • [ ] 选模型时问清：PTQ 还是 QAT？BF16 还是 FP16 训？
  • [ ] 长 prefill OOM 时考虑激活重算，但算清重算 vs offload 成本
  • [ ] 别把 FP16 的 loss scaling 套到 BF16 模型
  • [ ] 推理 DP（不同步）≠ 训练 DDP（每步 all-reduce），成本差几个数量级
  • [ ] ZeRO 是训练技术，推理用 TP——别混
  • [ ] 别信"ZeRO 省 4×/8×"这类万能数字，看实际 state/layout
  • [ ] 推理 PP 的延迟开销是 bubble，优化方向 = 1F1B/Zero-bubble 的服务化
  • [ ] 训练期路由/精度/均衡固化进权重，服务期别随便改
  • [ ] 跨团队对话：能说清"你这个 checkpoint 训的时候是怎么切/怎么均衡的，我推理时能/不能复用"

十二、原书补强：QAT 已有实例（Kiely §5.1.2）

本篇 §二讲了 QAT 的机制与边界。精读原书后补一条：哪些模型是原生 QAT 训出来的——让“QAT 是训练侧事”落到具体模型。

原书点名两个 QAT 实例：GPT-OSS 原生 MXFP4、Kimi K2 Thinking 原生 INT4。也就是说 lab 会把权重直接按目标低精度训出来、随模型一起发布。推理工程师拿到的只是成品权重，无法对开源模型做 QAT——你能做的只有 PTQ（见第 4 篇）。所以遇到“这模型是 MXFP4/INT4 原生”的 checkpoint，要意识到那是训练期就定的精度，不是你能量化的；你能调的是 PTQ 那一侧的校准/选择性精度。这正好印证本篇的责任边界：训练期路由/精度决策 ≠ 服务期放置/量化。
