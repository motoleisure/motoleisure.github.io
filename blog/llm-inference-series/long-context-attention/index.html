一、为什么标准 attention 在长上下文撑不住

回顾第 02 篇：dense self-attention 里，第 t 个 token 要对前面所有 t 个 token 算 attention，计算量随序列长度 平方增长；同时每层都要把每个历史 token 的 K、V 存进 KV cache，显存随长度 线性增长。

两个瓶颈，分开看：

计算瓶颈（prefill 主导）:  O(n² · d)     ← prefill 是 compute-bound
显存瓶颈（KV cache）:      O(n · d · L)  ← 每多一个 token，所有层都要存

以 Llama-2 70B、128K 上下文、64 层、GQA（8 组 KV head、head_dim 128）粗算 KV cache：

KV cache ≈ 2(K和V) × 128K × 128 × 64 × 8 ≈ 16 GB（仅 KV，不含权重）

换 MHA（64 个 KV head）就直接 8 倍 → 128 GB，一张 H100 80G 根本放不下。长上下文的两个杀手：prefill 算力平方爆炸 + KV cache 线性但常数很大。 下面三类技术分别攻这两个瓶颈，但思路完全不同。

二、稀疏 / 滑动窗口 / 膨胀注意力（Atlas #03）

核心思想：不是每个 token 都需要看全部历史。让每个 token 只对一部分历史 token 算 attention，把 O(n²) 降到 O(n·w)（w 是窗口/稀疏规模）。

2.1 三种稀疏 pattern

变体 机制 感受野 典型模型
Sliding-window（滑动窗口） 每个 token 只看前面 w 个 局部 w Mistral（w=4096）、Longformer 局部窗口
Strided / dilated（膨胀空洞） 窗口内跳着取（步长 s），扩大感受野 w·s 但仍 O(n·w) Sparse Transformer、Dilated Attention
Global + local（全局点） 局部窗口 + 少量"全局 token"看所有 近似全局但稀疏 Longformer、BigBird

2.2 滑动窗口的 KV cache 红利

滑动窗口有个推理侧的直接好处：KV cache 只需保留最近 w 个 token，超出窗口的旧 KV 可以丢弃。所以滑动窗口模型的 KV cache 是 O(w·d·L) 而非 O(n·d·L)——128K 上下文也能把 KV 控制在窗口大小内。这是 Mistral 选 sliding-window 的关键理由之一。

2.3 tradeoff 与质量评估

  • 稀疏降低了计算和显存，但可能丢掉远距离依赖。
  • 质量评估不能只看 perplexity：要测长距离检索任务——needle-in-a-haystack（大海捞针）、长文档 QA、跨段推理。一个 sliding-window 模型 perplexity 可能很好，但"第 1 万 token 埋的针、第 10 万 token 问"会彻底失败。
  • Atlas 的纪律："Architecture changes such as sparse attention require compatible weights and evaluation."——不能在推理时对一个 dense 训练出来的模型随便套窗口，权重没训过这种 pattern，质量会崩。

2.4 责任边界

这是 model engineer 的架构选择。inference engineer 的活是：看 config 确认 sliding_window 字段、确认推理框架支持该 pattern、按窗口大小做 KV 预算。

三、低秩 / 潜空间注意力（Atlas #04）

核心思想：attention 矩阵往往是低秩的，可以用低秩投影或核近似来逼近，把 O(n²) 压到 O(n·k) 甚至 O(n)。

3.1 两条路线

变体 机制 复杂度 代表
Linformer（低秩投影） 把 K、V 的序列维度 n 投影到 k（n→k），attention 变 O(n·k) O(n·k) Linformer
Performer / 线性 attention 用 random features / kernel feature map 把 softmax attention 近似成线性，去掉显式 n×n 矩阵 O(n) Performer、Linear Transformers、RWKV、RetNet

3.2 tradeoff

  • 近似有误差：低秩投影丢信息，线性 attention 的核近似对长距离精度有退化。
  • 和标准 attention 输出不完全等价——这是和稀疏 attention 不同的"近似"本质：稀疏是"少算一些位置但算的还算准"，低秩是"算了但近似了"。
  • 这类模型通常需要专门训练才能在低秩假设下表现好。

3.3 责任边界

同样是 model engineer 的架构选择。inference engineer 看到 Linformer/linear/Performer 这类模型，要知道它的 prefill 不是平方复杂度、但质量评估要做长距离对照。

四、跨层 KV 共享（YOCO, Atlas #05）+ MLA 潜空间（Atlas #04）—— 当前最重要的一类

⚠️ Atlas 把两类分开：#04 Low-rank & latent attention（MLA、Linformer——把 KV 压进低秩/潜空间表示）与 #05 Cross-layer KV sharing（YOCO——多层共用同一份 KV 状态）。两者都是“减少需保留的 KV”，但机制不同：MLA 压维度、YOCO 跨层复用。本节合并讲（对 KV 预算影响同向），但记住 MLA 属 #04、YOCO 属 #05，别混为一谈——这是上一轮把 MLA 误挂到 #05 的纠正。

核心思想：与其减少每层看的 token 数，不如减少"需要保留几套独立的 KV 状态"。这是 2024-2026 主流大模型把 KV cache 压到极致的方向。

4.1 从 MQA/GQA 到跨层共享

第 03 篇讲了 MQA/GQA：减少 KV head 数（多 query head 共享一套 KV）。跨层共享走得更远——多层共用同一套 KV。

  • YOCO（You Only Cache Once）：多个 decoder 层复用同一份 KV cache，cache 量直接除以共享层数。
  • Cross-layer attention：上层直接读下层的 K/V，不再独立存。

4.2 MLA（Multi-head Latent Attention）—— DeepSeek 的事实标准

DeepSeek-V2 引入、V3/R1 沿用的 MLA 是当前最激进的 KV 压缩：

  • 不存每 head 的 K/V，而是存一个压缩后的低秩 latent 向量。推理时 KV cache 只存这个 latent；需要算 attention 时再"解压"出各 head 的 K/V。
  • 为什么 DeepSeek 的 KV cache 这么小：latent 维度远小于 num_heads × head_dim，压缩比比 GQA 再低一个量级。
MHA:   cache ~ 2 × n × num_heads × head_dim
GQA:   cache ~ 2 × n × num_kv_groups × head_dim      (减少 head 数)
MLA:   cache ~ 2 × n × kv_lora_rank  (+ 少量解耦部分)  (压到 latent 维度)

对 128K 长上下文，MLA 能把 KV cache 压到 GQA 的 1/3 ~ 1/5。这是 DeepSeek 能以更低显存成本服务长上下文的核心原因。

4.3 tradeoff 与责任边界

  • 架构改动需训练：MLA 不是运行时开关，权重就是按 latent 压缩训出来的。
  • 解压有额外计算：每次 attention 要从 latent 解出 K/V，多一层矩阵乘。
  • 和 GQA/MHA checkpoint 不通用：你不能拿一个 GQA 模型"开启 MLA"。
  • 责任边界：inference engineer 必须能判断"这个 checkpoint 是 MLA/GQA/MHA"——KV 显存预算公式完全不同，预算做错直接 OOM。看 config.json 里的 q_lora_rank / kv_lora_rank 字段就是 MLA 的标志。

五、一张表：拿到 checkpoint 怎么判断 attention 类型

Attention 类型 config 关键字段 KV cache 公式（每 token） 典型模型 主流框架支持
MHA num_kv_heads == num_heads 2·num_heads·head_dim Llama-2、GPT 全支持
GQA num_kv_heads < num_heads 2·num_kv_groups·head_dim Llama-3、Mistral、Qwen2 全支持
MQA num_kv_heads == 1 2·head_dim PaLM、StarCoder 全支持
Sliding-window sliding_window 2·num_kv_groups·head_dim（按窗口截断） Mistral、Gemma2 vLLM/SGLang/llama.cpp
MLA（潜空间） q_lora_rank / kv_lora_rank ~2·kv_lora_rank DeepSeek-V2/V3/R1 vLLM、SGLang
Sparse/线性 模型自定义 视实现 Longformer、Linformer、Performer 部分支持

实操：拿到一个新模型，先 cat config.json | grep -E "num_attention_heads|num_key_value_heads|sliding_window|q_lora_rank|kv_lora_rank"，再决定 KV 预算公式。没查清 attention 类型就估显存 = 盲算。

六、显存预算：不同 attention 差几倍

以 70B、64 层、128K 上下文粗算（仅 KV cache，head_dim=128）：

Attention 每 token KV 128K KV cache 相对
MHA（64 head） 2·64·128 = 16 KB ~128 GB 1×（放不下）
GQA（8 组） 2·8·128 = 2 KB ~16 GB 1/8
MQA（1 组） 2·128 = 256 B ~2 GB 1/64
MLA（latent 512） 2·512 ≈ 1 KB ~8 GB 1/16

数字为量级估算，实际看 latent 维度、是否解耦、框架实现。结论稳定：attention 类型选错，KV 预算差一个数量级。 这就是为什么"拿到 checkpoint 先判 attention 类型"是 inference engineer 的基本功。

七、责任边界与质量评估（Inference Lab 精神）

Atlas 把 #03/#04/#05 全归到 Model design · Model engineer，责任写得明白：

"An architectural change needs trained support. Reusing arbitrary layers' caches in an existing model is not equivalent." "架构改动需训练支持；在已有模型里复用任意层的 cache 不等价。"

翻译成 inference engineer 的纪律：

  1. 会读：拿到 checkpoint 能判断 attention 类型，估对 KV 预算。
  2. 会评估：长上下文模型的质量评估要测长距离检索（needle-in-haystack、跨段 QA），不是只看短 prompt perplexity。
  3. 不乱改：不能对 dense 模型"开启稀疏"、不能把 GQA 权重当 MLA 跑——架构改动不是运行时开关。
  4. null ≠ zero：config 里没有 sliding_window 字段，不等于"它用了 dense attention"——也可能是字段名不同、也可能是 MLA（看 kv_lora_rank）。缺失哨兵不变成零，要去验证。

这和第 14 篇 Inference Lab 方法论完全同源：claim 要有界，测量边界先于指标。

八、推理框架支持现状（2026）

框架 MLA（DeepSeek） 滑动窗口 稀疏/线性
vLLM ✅ 原生支持 DeepSeek MLA ✅ 支持 sliding_window 视模型实现
SGLang ✅ Day-0 支持 DeepSeek 系列 ✅ 视实现

MLX ✅ DeepSeek 支持 ✅ —

DeepSeek MLA 的普及倒逼所有主流框架都加了 latent attention 路径。但支持 ≠ 最优：MLA 的解压 kernel 在不同硬件上性能差很多，要 benchmark。Atlas 的纪律——"Use the diagram to form a hypothesis, then measure"——在这里同样适用。

九、实践 checklist：长上下文注意力变体

  • [ ] 拿到新模型先 grep config.json 判 attention 类型（MHA/GQA/MQA/MLA/滑窗）
  • [ ] 按对应公式估 KV cache，别用 MHA 公式套 GQA 模型
  • [ ] MLA 看 q_lora_rank/kv_lora_rank，预算按 latent 维度
  • [ ] 长上下文模型质量评估必测 needle-in-haystack + 跨段 QA，不只看 perplexity
  • [ ] 滑动窗口模型确认 KV 按窗口截断（不是无限增长）
  • [ ] 架构改动不当运行时开关：dense 权重不能"开稀疏"，GQA 不能当 MLA
  • [ ] null ≠ zero：缺 sliding_window 字段要去验证，别默认 dense
  • [ ] 框架声称支持 ≠ 最优，在目标硬件 benchmark MLA 解压 kernel
  • [ ] 声明写边界："MLA 在 128K 把 KV 压到 ~8GB（量级，实测为准）"
