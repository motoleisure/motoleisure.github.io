12 · 生产部署：SLO、负载测试、故障模式、灰度与回滚

Tim Chan 发布于 2026 年 9 月 14 日

模型在本地跑通了，不等于能上线。生产部署要面对真实流量、硬件故障、版本回归、长尾延迟。这一篇讲怎么把推理服务做成"扛得住"的生产系统。

一、定义 SLO：从"够快"到可量化

1.1 推理服务的典型 SLO

指标 典型 SLO 说明
TTFT P50 < 500 ms 一半请求首 token 半秒内
TTFT P99 < 2 s 99% 请求首 token 两秒内
TPOT P99 < 80 ms 每 token 延迟长尾
可用性 99.9% 每月宕机 < 44 分钟
错误率 < 0.1% 含超时、OOM、截断
完整响应率 > 99.5% 非截断的完整输出

1.2 设 SLO 的原则

  1. 从用户体验倒推：用户能忍多少 TTFT？多少 TPOT 会觉得卡？业务要多少可用性？
  2. 分位而非平均：P50 好 P99 差，用户体验差。SLO 看 P95/P99。
  3. SLO 要分场景：对话型（TTFT 敏感）vs 批处理（吞吐敏感）vs agent（多轮稳定性敏感）SLO 不同。
  4. 留 error budget：99.9% = 每月 44 分钟可"不达标"预算。用完就冻结新功能上线，优先修稳定。

二、负载测试：上线前必做

2.1 压测要测什么

  • 吞吐拐点：并发升到哪延迟陡升？（第 6 篇讲的）那是你的有效容量上限。
  • TTFT/TPOT 随并发变化曲线：找 SLO 边界。
  • 长尾：P99/P99.9 在高压下怎么变。
  • 预热效应：冷启动 vs 热稳态差异。
  • 混合负载：不同 prompt 长度、输出长度、prefix 命中率的真实分布。

2.2 压测工具

  • vLLM benchmark：自带 benchmark 脚本（vllm bench）。
  • k6 / Locust：通用 HTTP 压测，模拟并发流式请求。
  • 自定义：用 Inference Lab 的 LLMTraceFX 风格采集器，但注意第 10 篇的测量陷阱（增量读、partial 检测）。

2.3 一个压测计划模板

1. 冷启动测试：单请求测 TTFT 基线（无并发）
2. 递增并发：1 → 4 → 16 → 32 → 64 → 128
   每级稳定 60-120s，记 P50/P95/P99 TTFT/TPOT、GPU 利用率、KV cache 利用率、抢占次数
3. 找拐点：延迟陡升的并发数 = 有效容量
4. 混合负载：按线上真实 prompt 分布（短/长、命中/未命中 prefix）
5. 长跑稳定性：拐点并发下跑 30-60min，看有没有内存泄漏/退化
6. 故障注入：杀一个副本、断网、GPU OOM，看自愈

实践：压测的"成功"不是"能跑到 256 并发"，而是找到延迟陡升拐点，然后把 SLO 设在拐点以下。

三、故障模式与处理

推理服务比 Web 服务更容易出特定故障：

3.1 OOM（显存不足）

  • 原因：batch 过大、KV cache 池满、长 prompt 涌入、内存碎片。
  • 处理：限流、降 batch、降并发、加卡、监控 KV cache 利用率提前告警。
  • 容错：单请求 OOM 不该拖垮整个副本，引擎要隔离失败请求。

3.2 副本 crash / GPU 掉卡

  • 原因：驱动 bug、硬件故障、OOM kill。
  • 处理：K8s 自愈（重启 Pod）、多副本冗余、健康检查。
  • KV cache 丢失：重启后重新 prefill（prefix cache 可能恢复部分）。

3.3 网络抖动 / 流式中断

  • 原因：网关、LB、provider 端中断。
  • 处理：客户端重试（幂等）、断点续传（难，KV cache 在 provider 端可能没了）。
  • 第 10 篇讲：partial stream 要标 truncated，不当成功。

3.4 冷启动风暴

  • 原因：高峰扩容，大量副本同时冷启动，GPU 抢不到 + 加载耗时长。
  • 处理：warm pool、错峰启动、镜像优化、权重共享存储。

3.5 版本回归

  • 原因：模型/框架升级把性能或质量搞回去了。
  • 处理：持续回归测试（第 14 篇的证据体系）。每次发版前跑标准 benchmark + 业务样本对照。

四、灰度发布与回滚

4.1 灰度策略

新版本 → canary 1 副本（5% 流量）→ 观察 TTFT/TPOT/错误率
  → OK 扩到 25% → 50% → 100%
  → 任何指标回归 → 回滚

观察指标：

  • TTFT/TPOT P50/P99 是否回归
  • 错误率（OOM/截断）是否上升
  • 输出质量（采样人工/自动评估）
  • GPU 利用率/显存是否异常

4.2 回滚机制

  • 镜像版本化：每次发版打新镜像 tag，回滚切回旧 tag。
  • 配置版本化：参数改动也要可回滚（vLLM 启动参数）。
  • 模型版本化：模型权重 revision 固定，回滚切旧 revision。
  • 快速回滚：K8s kubectl rollout undo，秒级切回。

4.3 影子流量（shadow）

新版本先收镜像流量（不返给用户），只对比输出质量/延迟，确认没问题再切真流量。适合质量敏感场景。

五、监控仪表盘必备指标

实时层：
  - 请求数（running / waiting / completed/sec）
  - TTFT P50/P95/P99
  - TPOT P50/P95/P99
  - 错误率（按类型：OOM/timeout/truncated/5xx）
  - GPU 利用率 + 显存利用率 + KV cache 利用率
  - 抢占次数/min
  - prefix cache 命中率

容量层：
  - 副本数（warm / active）
  - autoscaling 事件
  - 冷启动次数/时长

成本层：
  - token 吞吐（in/out）
  - 单 token 成本趋势
  - GPU $/小时利用率

质量层：
  - 完整响应率
  - 采样人工/自动评估分趋势

六、限流与降级

6.1 限流

  • 按 QPS：超阈值拒绝/排队，保护后端不雪崩。
  • 按并发：限制同时在跑请求数（推理更适合，因为单请求长）。
  • 按 token 预算：限制单位时间总 token（防一个长 prompt 耗尽资源）。
  • 按租户：多租户配额，防大户挤占。

6.2 降级

过载时主动降级保核心：

  • 关闭非核心功能（投机解码降级回普通、关 prefix cache 降内存）。
  • 路由到更便宜模型（第 11 篇的智能路由）。
  • 降低 max_tokens / 关流式改批量。
  • 拒绝低优先级请求（free 用户），保 VIP。

七、Inference Lab 的工程纪律启示

Inference Lab 文章体现的生产纪律，直接可用于生产部署：

  1. 固定 commit + SHA-256 制品：每个线上版本可复现。出问题能回退到精确版本。
  2. 每次发版跑证据 catalog：第 14 篇讲的，把性能/质量/成本证据做成可验证包，发版前回归。
  3. 测量边界随结果写：SLO 仪表盘上每个数字旁边写清楚它测的是什么（client timing vs provider usage），避免误读。
  4. fail closed：证据/回归系统发现不一致（hash 不匹配、commit 不对）就拒绝发版，宁可慢也不发坏版本。

八、实践 checklist：生产部署

  • [ ] SLO 按用户体验倒推，看 P95/P99 不看平均
  • [ ] 压测找延迟拐点，SLO 设在拐点以下
  • [ ] 混合负载 + 长跑稳定性测试
  • [ ] 故障注入测试（杀副本、OOM、断网）
  • [ ] 灰度发布 canary→25%→50%→100%，任一指标回归即回滚
  • [ ] 镜像/配置/模型版本化，可快速回滚
  • [ ] 监控仪表盘含实时+容量+成本+质量四层
  • [ ] 限流按并发/token 预算/租户
  • [ ] 降级策略预定义（关投机、降模型、限长输出）
  • [ ] 发版前跑证据 catalog 回归，fail closed
  • [ ] warm pool 防冷启动风暴

九、原书补强：冷启动四因子分解（Kiely §7.2.2）

本篇 §3.4 讲了“冷启动风暴”。精读原书后补一条更彻底的分解：冷启动总时间 = 四个独立环节之和，每环节要单独优化。

环节 内容 优化方向
GPU 采购 多快能给集群加卡并划给模型 容量预留 / 弹性池
镜像加载 多快把容器镜像拉到新实例 镜像分层、就近仓库、预拉
模型加载 多快把权重载入容器 权重分片、本地缓存
引擎启动 多快起推理引擎，含编译时间 预编译 / CUDA graph 预 capture

第 18 篇 Inference Lab 的 vLLM 编译 break-even 案例（冷启动债 54s）正落在第四个环节：编译时间。这四因子分解给了一个可归因的冷启动预算账——某次冷启动慢，先定位是哪一环，再定向优化，而不是笼统说“冷启动慢”。autoscaling 能否放心缩容，取决于这四环加起来的冷启动速度。
