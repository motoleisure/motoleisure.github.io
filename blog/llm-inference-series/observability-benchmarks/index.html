10 · 可观测性与基准测试：TTFT/TPOT/吞吐的正确测量（Inference Lab 实证）

Tim Chan 发布于 2026 年 9 月 14 日

这是全系列的"灵魂篇"。前面所有优化——量化、batching、cache——都建立在"测量准确"之上。但测量恰恰是最容易做错的。这一篇用 Inference Lab 的实证告诉你：一个 TTFT 能错 185ms，一个 GPU trace 能有 57% 不是你的负载，一个 benchmark 截图能"真且无用"。

一、为什么这篇最重要

Inference Lab 的 8 篇文章，表面是技术教程，本质是一份"怎么正确测量推理性能"的方法论。它的核心论点：

一个基准数字（延迟/吞吐/成本/显存）若不可追溯来源——哪个模型版本、哪段代码观测的、计时从哪开始、响应是否完整、哪些制品留存、哪个价格产生成本——它就只是一张截图，可以是真的，也可以是无用的。

如果测错了，后面所有优化都在优化一个幻觉。所以这一篇详细讲正确定义和测量每个指标。

二、核心指标的正确定义

2.1 TTFT（Time To First Token）

定义分歧最大的指标。"首 token"到底是哪个事件？ 至少六种起点：

  1. 请求创建（client send）
  2. socket 写完
  3. 响应头到达
  4. 第一个 body 字节
  5. 第一个 server-sent event（SSE）
  6. 第一个非空可见内容（visible content）

Inference Lab 的立场：TTFT 应该从请求开始到"第一个非空可见内容"，因为这才是用户感知的等待。但很多实现从"第一个 SSE"算，而第一个 SSE 可能是空 delta、role metadata、keepalive——这会让 TTFT 看起来比真实等待短。

错误：TTFT = 第一个 SSE 到达时间（可能是空事件）
正确：TTFT = 第一个非空 visible content delta 到达时间

2.2 TPOT（Time Per Output Token）

TPOT = (最后一个 token 时间 - 第一个 token 时间) / 输出 token 数

只算 decode 阶段每 token 时间，不含 TTFT。

2.3 E2E latency

E2E = 客户端收到完整响应 - 请求发出

含 TTFT + decode + 终止确认。

2.4 吞吐（throughput）

两种语境，别混：

  • 单请求 token/s：输出 token / decode 时间。看模型本身快慢。
  • 系统吞吐（aggregate tokens/s）：所有请求总 token / 总时间。看服务能力。后者受 batching、并发、调度影响大。

三、实测踩坑实证（全部来自 Inference Lab）

3.1 坑一：HTTP 客户端缓冲让 TTFT 错 185ms

Inference Lab 的 TTFT 文章实测：

第一版采集器用 response.read(8192)（8KB 块）读 HTTP 流。问题：Python 的 HTTP reader 会跨多个 transport chunk 直到填满 8192 字节。一个 provider 可能早就发了可见内容，但客户端要等到攒够 8KB 才返回给采集器。

对照实验（loopback HTTP/1.1，同 67 字节可见帧，20ms 后发，180ms 后关闭）：

read1(8192) 增量读：中位首返回 25.008 ms
read(8192) 缓冲读  ：中位首返回 210.076 ms
额外观测延迟：185.068 ms（8.4 倍）

同样服务器、同样字节、同样时间表，只换客户端读法，TTFT 差 185ms。 这是纯客户端传输测量，不是模型/provider 结果。

实践：测 TTFT 的采集器要用增量读（read1 或逐字节/逐 chunk），不要用缓冲块读。否则你的 TTFT 里掺了客户端缓冲延迟。

3.2 坑二：把非可见事件当首 token

OpenAI 兼容流式 API 在可见文本前可能发一堆东西：

  • 注释 / keepalive
  • role metadata
  • 空 content delta
  • provider 标识
  • 隐藏的 reasoning delta
  • 只含 usage 的事件

把任何这些当"首 token"会让 TTFT 看着比真实等待短。 Inference Lab 的做法：TTFT 只在看到非空可见内容时开始；reasoning delta 只计数不存文本；provider 上报的 token usage 和客户端观测的时间分开记。

3.3 坑三：半截流算成功

provider 发了半截答案 → 连接断 → 没 finish_reason → 没 [DONE]

一个把这种当成功的 benchmark，会奖励"坏但快"的流（断得早所以延迟短）。正确做法：必须有合法终止信号（finish_reason 或 [DONE]）才算成功，否则标 truncated。provider 的失败 reason 即使后来有 sentinel 也算失败。

3.4 坑四：tokens-per-second 缺 provenance

一个 SSE delta 不等于一个 token。provider 可能：一个 delta 放多个 token、一个 token 跨多个 transport chunk、上报 reasoning token 但客户端没观测到。

别拿 provider 上报的 token 除以客户端观测的时间窗。 如果 reasoning token 在客户端 visible-content 窗口外到达，用它除可见窗口会伪造一个更快的速率。

3.5 坑五：GPU trace 不是你的负载

Inference Lab 的 Metal trace 文章实测：五次受控 Metal 捕获，每次已知 dispatch 数（400/250/120/77/133）。每次目标 PID 的 interval 数都精确匹配已知数。但 trace 全量还包含其他进程，已知无关 interval 占全量的 36.5%-57.5%。

错误：trace_total = sum(all intervals)
正确：target_intervals = intervals where pid == target_process

实践：profile 后按 PID 过滤，别拿含 WindowServer/其他 app 的 trace 调你的 kernel。trace 全量 ≠ 负载数。

3.6 坑六：缓存命中不证明跳过了计算

上一篇讲了。引擎报"cache hit 8 token"不等于真的跳过了那 8 个 token 的计算。Inference Lab 建独立 oracle 三方核对。生产看 cache 命中率要同时看 TTFT 是否真的降了。

3.7 坑七：文件字节当显存预算

第 9 篇讲的。"16G 权重 < 24G 内存所以能跑"是错的。峰值 = 权重 + KV cache + 激活 + 临时 + 框架。四套账本不可加成一个数。

四、测量的正确方法论

综合 Inference Lab 的做法，正确的推理测量要遵循几条原则：

4.1 分离客户端观测和供应商上报

两套账本：

  • 客户端观测：请求发出、响应头、字节、SSE、可见内容、流终止。反映用户等待。
  • 供应商上报：input/output/cached/reasoning token、usage cost。反映 provider 计费。

不要把供应商上报的 token 除以客户端观测的时间窗（除非该窗口覆盖那些 token）。两者分开记，分开报。

4.2 输出完整性作为成功门控

partial output = truncated = 失败。一个 failed stream 不该因为"快"而得更好分数。

4.3 测量边界要随结果一起写

每个数字旁边要写：

  • 模型身份（repo/revision/quantization/serving name）
  • 运行时身份（collector/framework/driver/OS）
  • workload 身份（prompt fixture/token 数/cap/重复/停止规则）
  • 评估器身份（哪些检查决定合法/完整/合格）
  • 测量 scope（client/provider/trace/log）
  • 制品身份（manifest/summary/samples/checksums）
  • 定价身份（price sheet/account/usage）
  • 失败状态（complete/truncate/timeout/OOM/refused）

4.4 null ≠ zero

first_token_ms: null      ← OOM 前没首 token，是 null 不是 0
completion_tokens: null   ← 没完成，不是 0 token
estimated_cost_usd: null  ← 没定价数据，不是免费

每个 zero 都是一个 claim。 把缺失（null）当 zero 会编造数据。缺证据就留 null。

4.5 独立 oracle 校验

引擎报 cache 命中？独立重算预期复用数核对。解析器报 400 dispatch？用已知 dispatch 数核对。永远不只信系统自己的报告。

4.6 可复现

精确到 commit hash + SHA-256 制品包。任何人能 clone 出来重跑。这不是洁癖，是工程纪律——只有可复现，才能做回归。

五、一个基准测试的契约模板

Inference Lab 的 GLM 文章给了一个范本。一个可信的比较要 pin：

- 模型 ID + revision + quantization
- provider 路由（禁 fallback，防静默换）
- 两个独立 workload（不同 evaluator，不平均）
- 重复次数（≥2，但要承认是 bounded）
- output cap / temperature / top-p / reasoning 控制
- provider parameter support 要求
- 不付 warmup/retry（否则掩盖冷启动）
- 客户端 timing vs provider usage 分开
- 缓存/reasoning 字段带 provenance，不归零
- 预留最坏预算，跑完逐条核对 usage
- 制品封 hash + 闭文件集
- 排除项也写出来（为什么 X 不放进排行榜）

六、可比性：契约不是视觉表格

Inference Lab 最深刻的洞见之一：把不可比的数字放一张表里，不等于它们可比。 它举了个例子：本地 Qwen3-8B MLX 跑 23 cases/min，托管 GLM-5.3 跑 18。能不能把 Qwen 放进托管排行榜当"最快"？不能，因为契约不同（不同模型/运行时/推理模式/seed/系统身份）。

一个图表能对齐任何三个数字，但不等于它们的分母相等。可比性来自契约，不来自数字的视觉邻近。

横评时要么对齐契约（同模型/硬件/方法），要么明确标注"不同契约的观察，不可直接排名"。

七、实践 checklist：可观测性与基准

  • [ ] TTFT 从"第一个非空可见内容"算，采集器用增量读
  • [ ] 分离客户端 timing 和 provider usage，两套账本
  • [ ] partial output 标 truncated，不当成功
  • [ ] 每个数字旁边写测量边界（模型/runtime/workload/evaluator/scope/制品/价格/失败状态）
  • [ ] null 不当 zero，缺证据留 null
  • [ ] cache 命中率 + TTFT 改善一起看，不只信引擎报告
  • [ ] GPU trace 按 PID 过滤，排除无关进程
  • [ ] 横评对齐契约或标注不可比，别用视觉邻近当可比
  • [ ] 制品封 commit + SHA-256，可复现
  • [ ] 排除项也写出来（为什么 X 不放排行榜）
  • [ ] 预算跑托管前先 dry-run，预留最坏情况，跑完逐条核对
