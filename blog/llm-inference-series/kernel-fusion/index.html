18 · 算子融合与 kernel 选型：torch.compile、CUDA graphs、autotuning

Tim Chan 发布于 2026 年 9 月 14 日

一、动机：两个隐藏成本

推理时 GPU 的算子调度有两个容易被忽略的成本：

  1. device-memory 往返：两个算子串行跑，第一个把中间结果写回 HBM，第二个再读回来。这一写一读是带宽 + 延迟，白白消耗。
  2. kernel launch 开销：每个 kernel 启动有 CPU→GPU 的 dispatch 延迟（几微秒）。算子多、每个小，launch 开销累计就显著——decode 阶段尤其，因为每个 token 要跑很多小算子。

算子融合治第一个：把能合并的算子揉成一个 kernel，中间结果留在片上（寄存器/SRAM），不写回 HBM。 kernel 选型 + autotuning治第二个：给每种 shape/hardware 选最快的实现，并用 CUDA graph 把整段调度的 launch 开销摊掉。

二、算子融合（Atlas #24 核心）

2.1 什么是融合

未融合:  读 → Op A → 写HBM → 读HBM → Op B → 写
融合后:  读 → Op A + Op B(同一 kernel) → 写      ← 中间结果不出片上

Atlas 原文："Fusion keeps intermediate results inside a combined kernel rather than writing and rereading them between operations."

2.2 Transformer 里典型的融合点

融合点 未融合（几个 kernel） 融合后 收益
QKV projection 3 个 GEMM 1 个 GEMM（拼接） launch + 带宽
RoPE 2 矩阵乘 + 旋转 1 fused rope 带宽
LayerNorm 均值/方差/scale/shift 多步 1 fused layernorm 带宽
SiLU/GELU + mul 激活 + 逐元素乘 1 fused 带宽
Attention（FlashAttention 就是融合的极端） QK^T → softmax → mask → AV 多步 1 fused tile kernel 大（见第 07 篇）
RMSNorm 多步 1 fused 带宽

注意：FlashAttention 本身就是"算子融合"的旗舰案例——它把 attention 的多步写回（score 矩阵）压成 tile 内就地计算。第 07 篇讲的是它的算法，这里是从"融合"角度再切一刀。

2.3 融合的代价（Atlas 反复强调的 tradeoff）

"Fusion can raise register pressure or lose an efficient library path. A faster isolated kernel can leave the service bottleneck unchanged."

  • 寄存器压力：揉进越多算子，寄存器占用越高，可能溢出到本地内存（local memory），反而变慢。
  • 丢掉高效库路径：有些算子有高度优化的库（cuBLAS/cutlass），自己融合的版本可能不如调好的库。
  • 孤立更快 ≠ 服务更快：一个 kernel 快了 20%，但服务瓶颈在 KV cache 带宽，整体没变——别只看 micro-benchmark。

三、kernel 选型与 autotuning

3.1 shape/hardware 匹配

同一个算子（比如 GEMM），不同 shape、不同精度（FP8/INT8/FP16）、不同 GPU（Ampere/Hopper/Blackwell）该用不同实现：

  • 小矩阵：可能 cuBLAS 不如手写 kernel。
  • 大矩阵 + FP8：要用 Hopper 的 tensor core FP8 路径。
  • GQA 的 KV GEMM：shape 特殊，要专门 kernel。

3.2 autotuning（Triton/TVM 路线）

把 kernel 参数（tile 大小、并行策略）当搜索空间，对每个 shape 在目标硬件上跑一遍 tuning，记下最快配置。Triton 的 @triton.jit + autotune 是主流：

@triton.jit
@triton.autotune(configs=[triton.Config({...}, num_warps=4), ...], key=['M','N','K'])
def fused_kernel(...): ...

→ autotuning 的产物是 shape → 配置 的查表，运行时按 shape 选。这是为什么"同一个模型在 A100 和 H100 上最优 kernel 不同"。

3.3 vLLM/SGLang 的 kernel 选型

  • vLLM 内置多种 attention / quant kernel（FlashAttention、FlashInfer、xformers、Marlin for INT4），按模型 + 硬件自动选。
  • SGLang 用 FlashIncer / Triton 融合 kernel，重度 autotuning。
  • 经验：别假定默认 kernel 最优，VLLM_ATTENTION_BACKEND 这类环境变量能切后端，benchmark 不同后端。

四、torch.compile 与 CUDA graphs（编译路径）

4.1 torch.compile（inductor）

PyTorch 2.x 的 torch.compile（inductor 后端）把 eager 的 Python 算子图编译成融合的 Triton/CUDA kernel，并做算子融合 + autotuning。推理框架（vLLM、SGLang）把 torch.compile(mode="max-autotune", fullgraph=True) 用在模型上：

  • 收益：融合 + 减少 launch + 选快 kernel。
  • 代价：编译耗时——第一次跑要编译，冷启动慢很多。这就是下一节 Inference Lab 案例的主角。

4.2 CUDA graphs

CUDA graph 把一整段 kernel 调度录制成一个 graph，之后一次 replay，省掉所有 CPU 端 launch 开销。decode 阶段（每个 token 跑固定算子图）特别适合 graph replay。

  • vLLM/SGLang 都有 CUDA graph capture（--enforce-eager 关掉就是开 graph）。
  • 代价：graph 录制要固定 shape/batch，变 batch 时要重新 capture；某些动态控制流不好 graph 化。
  • 收益：decode 的 launch 开销几乎清零，TPOT 明显下降。

五、实证案例：Inference Lab「vllm-compilation-break-even」

这一节是本技术的真实样本——来自第 14 篇 / 已读的 Inference Lab vllm-compilation-break-even。

5.1 现象

开 torch.compile + CUDA graph（compiled 模式）后： - ✅ 稳态单请求更快：compiled 后每个 token 的 decode 更快（融合 + graph replay 省了 launch/带宽）。 - ❌ 冷启动多欠 54 秒：第一次要编译模型、capture graph，启动时间多欠 ~54s。 - 📊 "第 113 请求交叉"：要服务到第 113 个请求，compiled 累计省下的时间才追平冷启动多欠的 54s。

5.2 Inference Lab 的三个反直觉结论

  1. "第 113 请求交叉"是建模，不是观测。 作者强调这个交叉点是从延迟模型外推的，不是实测稳态跑到 113 个请求观测出来的。→ 模型可以指导下次运行，但不必晋升为"上次的结果"。这是第 14 篇"测量边界先于指标"的体现。
  2. 输出漂移：compiled 和 eager 两条路，12 个请求里 4 个输出不同。融合 + graph 改变了浮点执行顺序，输出不逐位一致。→ 开编译要做质量 gate，不是"无损加速"。
  3. break-even 取决于 workload：只有请求数 > break-even 点、且稳态省下的时间能覆盖冷启动债，compiled 才净赚。短时服务 / 频繁重启的场景，compiled 净亏。

5.3 这正好对应 Atlas #24 的全部 tradeoff

Atlas 的告诫 vllm-compilation-break-even 的实证
"A faster isolated kernel can leave the service bottleneck unchanged" 单 token 快了，但冷启动 54s 才是真实成本
"Fusion can raise register pressure or lose an efficient library path" compiled 输出和 eager 不一致（执行顺序变了）
"No fixed speedup is guaranteed" break-even 点随 workload 浮动，不是"开了就快"

→ 这就是为什么把 Inference Lab 那篇放在本篇做案例：它是"算子融合/kernel 选型"tradeoff 最完整的一份实测样本。

六、什么时候该开 compile / 什么时候别开

6.1 该开

  • 长稳态服务：服务跑得久，请求数远超 break-even 点，冷启动债能摊掉。
  • decode 主导：CUDA graph 对 decode 的 launch 开销收益最大。
  • 固定 shape：batch 模式固定，graph 不用反复 capture。

6.2 别开 / 慎开

  • 短时任务 / 频繁重启：冷启动债 54s 摊不掉，净亏。
  • 变 batch 剧烈：graph 反复 capture，capture 本身有开销。
  • 对输出一致性敏感：compiled 有浮点漂移，关键场景要测。

6.3 决策树

服务是长稳态 + decode 主导 + 固定 batch?
  ├─ 是 → 开 torch.compile + CUDA graph，但先测：
  │        (1) 冷启动债多少秒
  │        (2) 稳态每 token 省多少
  │        (3) break-even 请求 = 冷启动债 / 稳态每请求省
  │        (4) 你的真实请求数 >> break-even 吗
  │        (5) 开编译 vs 不开，输出质量对照（漂移检测）
  └─ 否（短时/频繁重启/变 batch）→ 用 eager，或只开 CUDA graph 不开 full compile

关键纪律：break-even 点要自己算，别信框架/文档的声称。 Inference Lab 的核心教训就是"第 113 请求是建模不是观测"——你的环境、workload、硬件的 break-even 要实测。

七、责任边界与证据

Atlas 把 #24 归 Runtime / kernel engineer。inference engineer 不一定要手写 kernel，但要：

  1. 能读懂 profiler（哪些算子在搬 HBM、哪些 launch 多）。
  2. 能开关 + 选 kernel backend（VLLM_ATTENTION_BACKEND、--enforce-eager）。
  3. 算 break-even，决定 compile/graph 开不开。
  4. 测输出漂移（开编译 vs 不开的 token 级对照）。

证据指标：

指标 含义
kernel time / launch overhead profiler 看每算子时间 + launch 占比
end-to-end TTFT / TPOT 真北极
cold-start time 冷启动债（compile/graph capture）
output diff rate 开/关编译的输出差异比例

八、实践 checklist：算子融合与 kernel 选型

  • [ ] 先 profiler 找瓶颈：是 HBM 搬运还是 launch 开销，再决定融什么
  • [ ] benchmark 不同 attention/quant kernel backend，别假定默认最优
  • [ ] 开 torch.compile 前先量冷启动债（Inference Lab 实测 54s 级别）
  • [ ] 自己算 break-even 请求 = 冷启动债 / 稳态每请求省，别信声称
  • [ ] 真实请求数 >> break-even 才净赚，短时服务用 eager
  • [ ] 开编译后做 token 级输出对照，检测漂移（Inference Lab：12 请求 4 不同）
  • [ ] CUDA graph 对 decode 收益大，但变 batch 要重 capture，权衡
  • [ ] "第 113 请求交叉"是建模不是观测——别把外推当实测结果引用
  • [ ] 声明写边界："compiled 稳态 TPOT 降 X%，冷启动 +54s，break-even ~113 请求（建模值）"

九、原书补强：DeepGEMM——手动 kernel 选型的真例（Kiely §4.1.2）

本篇 §3 讲了 kernel 选型“大多自动、少数手动”。精读原书后补一个原书给的真例，让“手动选型”具体化。

DeepGEMM 是“手动 kernel 选型”的教科书案例。 DeepSeek 发 DeepSeek-V3 时一并发了 DeepGEMM——针对 Hopper 架构 FP8 矩阵乘的更高效 GEMM kernel。绝大多数生产 GEMM 来自 cuBLAS（自动），但当你有“两个精确维度的矩阵相乘”这种具体步骤时，可把 DeepGEMM kernel 作为插件插入替换该步、提速。

两个工程教训：

  1. kernel 与硬件硬绑定。 DeepGEMM 为 Hopper 写、硬编码了该架构的 Tensor Core 布局/带宽。换 B200 要么换回 cuBLAS、要么等 DeepGEMM 出 Blackwell 支持（出版时已支持）、要么自己移植。kernel 升级跨架构要重做，不是“一次写到处跑”。
  2. 手动选型 = 精确点插。 不是整模型换 kernel，而是定位到“这步 matmul 维度刚好匹配 DeepGEMM 强项”才插。和本篇 §5 的 Inference Lab 编译 break-even 同源：孤立的更快 kernel 不代表服务瓶颈消除——插之前先 profiler 确认这步真是瓶颈。
