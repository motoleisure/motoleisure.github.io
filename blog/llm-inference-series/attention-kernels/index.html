07 · Attention 算子优化：FlashAttention、PagedAttention、Ring/Context Parallel

Tim Chan 发布于 2026 年 9 月 14 日

Attention 是 Transformer 里计算和访存都最重的算子。它的实现质量直接决定 prefill 速度和 decode 带宽效率。这一篇讲三个层面的优化：单 GPU 内的 kernel（FlashAttention、PagedAttention）、长上下文的内存（Ring/Context Parallel）、以及它们怎么协作。

Attention 是 Transformer 里计算和访存都最重的算子。它的实现质量直接决定 prefill 速度和 decode 带宽效率。这一篇讲三个层面的优化：单 GPU 内的 kernel（FlashAttention、PagedAttention）、长上下文的内存（Ring/Context Parallel）、以及它们怎么协作。

一、为什么 attention 需要专门优化

1.1 标准 attention 的两个问题

朴素 attention（按公式写）：

scores = Q @ K.T / sqrt(d)     # [seq, seq]
attn = softmax(scores)
out = attn @ V                  # [seq, d]

两个致命问题：

  1. 中间矩阵大：scores 是 [seq, seq]，seq=8192 时就是 8192×8192 矩阵。每个 head、每层都要实例化这个矩阵，显存爆。
  2. 读写放大：要先算 scores 写到 HBM，再读回来 softmax，再写回去，再读回来乘 V。一个 attention 来回读写 HBM 几次，bandwidth-bound 下慢得离谱。

1.2 优化目标

  • 减少 HBM 读写（少搬运）
  • 不实例化完整 [seq,seq] 矩阵（省显存）
  • 利用 GPU 内存层级（SRAM/shared memory 快）

二、FlashAttention：分块计算 + IO-aware

2.1 核心思想

FlashAttention（Tri Dao, 2022/2023）的关键：把 Q/K/V 切块，一块一块在 GPU 的 SRAM（shared memory）里算 attention，用在线 softmax（online softmax）避免实例化完整 [seq,seq] 矩阵，算完一块直接写最终 out 到 HBM，不落中间矩阵。

for block of Q:
    load 到 SRAM
    for block of K,V:
        load 到 SRAM
        算 partial scores → 在线 softmax 累加 → 累加到 out
    写 out 块到 HBM

2.2 收益

  • HBM 读写从 O(n²) 降到 O(n²·d/M)（M 是 SRAM 大小），大幅减少搬运。
  • 显存：不存 [seq,seq]，只需 O(n) 的 running statistics。
  • 速度：长序列 attention 提速 2-4 倍，且越长收益越大。

2.3 演进

  • FlashAttention v1：奠基，分块 + online softmax。
  • FlashAttention v2：更好的并行度（按 seq 维切分到 SM），2× 提速。
  • FlashAttention v3：Hopper 专属，用 TMA（Tensor Memory Access）和 FP8，进一步榨干硬件。

几乎所有现代推理引擎都默认用 FlashAttention（或其变体）做 prefill 的 attention。它是底层基础设施，你很少直接调，但要知道它在那。

三、PagedAttention：分块物理分散的 attention

上一篇讲 KV cache 时提到 PagedAttention，这里讲它和 FlashAttention 的关系。

3.1 为什么不能直接用 FlashAttention 做 decode

FlashAttention 假设 K/V 是一块连续显存。但 PagedAttention 的 KV cache 是逻辑连续、物理分散的 block。要做 attention，得在"按页表分散访存"的条件下算。

3.2 PagedAttention kernel

vLLM 写了专门的 PagedAttention kernel：

  • 按 block table 查每个 block 的物理地址。
  • 一个 block 一个 block 地加载 K/V 到 SRAM，和 Q 算 attention 累加。
  • 本质是"分块 attention"，但块的边界由页表决定，不是固定切片。

它复用了 FlashAttention 的"分块 + 在线 softmax"思想，但块的定义来自页表。这就是为什么 vLLM 能既省碎片又算得快——PagedAttention 是"FlashAttention for paged KV cache"。

四、长上下文的并行：Context Parallel / Ring Attention

4.1 问题：单卡放不下超长序列的 KV cache

序列越长，KV cache 越大（线性涨）。128K 上下文的 70B 模型，KV cache 单请求就几十 GB，单卡放不下。要么多卡分（张量并行），要么专门的长序列并行。

4.2 张量并行（Tensor Parallel, TP）

最常见：把每层的权重矩阵按行/列切到多卡，每卡算一部分，用 all-reduce 合并。

  • 适合：模型大（权重放不下）。
  • 代价：每层都要 all-reduce 通信，卡多了通信成瓶颈。一般 TP ≤ 8。

4.3 序列并行 / Context Parallel (CP)

针对超长序列：把一个序列的不同位置切到不同卡，每卡只算一部分 token 的 attention。问题：每个位置的 Q 要看到所有位置的 K（attention 是全局的），卡间要通信 K/V。

4.4 Ring Attention

Context Parallel 的高效实现：把卡排成环，K/V 沿环传递，每卡一边算本地 attention 一边收下一块 K/V。通信和计算重叠，几乎不阻塞。

  • 适合：超长上下文（100K-1M）。
  • 用例：vLLM、SGLang 都支持 CP/Ring Attention 跑长上下文模型（如 Qwen 的 1M context）。

4.5 实践：并行度选择

模型放不下单卡 → 张量并行 (TP)
序列太长 KV cache 放不下 → 加序列并行 (CP)
两者都要 → TP × CP 组合
超大规模多机 → 再叠数据并行 (DP) / expert 并行 (MoE)

五、Decode 阶段的 attention 特殊性

5.1 decode attention 是 GEMV 不是 GEMM

Prefill：Q 是 [prompt_len, d]，K/V 是 [prompt_len, d]，attention 是大块矩阵乘（GEMM），compute-bound。

Decode：Q 是 [1, d]（一个新 token），要和 cache 里 [seq, d] 的 K 做 attention。这是 矩阵-向量乘（GEMV），计算量极小，但要把整个 K cache 读一遍 → memory-bound。

5.2 这就是为什么 decode 优化重点是带宽

decode attention 的瓶颈不是"算 attention 算得慢"，是"把 K cache 和权重从 HBM 读到 SM 慢"。所以 decode 优化方向：

  • 量化权重（少读）
  • prefix caching（不重读已算的 K/V）
  • batching（多个请求的 K/V 一起读，摊薄带宽开销）—— 这就是为什么 batch 越大 decode 吞吐越高（在显存允许范围内）。

六、MHA / GQA / MQA 在 kernel 层面

这些不仅是模型架构（上一篇讲了省 cache），也影响 kernel 实现：

  • MHA：每 head 独立 K/V，attention kernel 标准。
  • MQA：所有 head 共享 K/V，kernel 可以只读一份 K/V 算所有 head 的 attention → 带宽省 H 倍。但要注意 kernel 要正确处理共享。
  • GQA：组共享，介于两者。好的 kernel（vLLM/SGLang）都针对 GQA 优化过读写。

七、实践：怎么知道 attention 是不是瓶颈

7.1 用 profiler

  • NVIDIA Nsight Systems：看 timeline，attention kernel 占多少。prefill 阶段 attention 占比高正常；decode 阶段如果 attention kernel 时间长但 GPU 利用率低，说明是 memory-bound，attention kernel 在等数据。
  • NVIDIA Nsight Compute：看单个 kernel 的 roofline，落在 memory-bound 区还是 compute-bound 区。

7.2 一个归因经验

Inference Lab 的 Metal trace 文章给了一个重要教训：profiler trace 不等于你的负载。 一次 trace 里 36.5%–57.5% 的 GPU interval 属于无关进程（WindowServer 等）。必须按 PID 归因，否则你优化的"瓶颈"可能根本不是你的负载。

错误：trace_total = sum(all intervals)
正确：target_intervals = intervals where pid == my_process

实践：profile 前先确认你的负载是 trace 里的主进程，profile 后按 PID 过滤。别拿含其他进程的 trace 调你的 kernel。

八、实践 checklist

  • [ ] 确认引擎用的是 FlashAttention v2/v3（基本都默认，但旧版可能不是）
  • [ ] 长上下文用 GQA 模型（省 KV cache 和带宽）
  • [ ] 100K+ 上下文考虑开 Context Parallel / Ring Attention
  • [ ] decode 慢时先确认是 memory-bound（用 Nsight Compute 看 roofline）
  • [ ] profile 时按 PID 归因，排除无关进程
  • [ ] decode 优化优先考虑量化 + batching + prefix cache（打带宽战），而非改 attention kernel
  • [ ] TP 度数 ≤ 8（all-reduce 通信开销），再大考虑 CP/DP 组合
