09 · 硬件与显存预算：GPU 显存层级、Apple Silicon 统一内存、多卡并行

Tim Chan 发布于 2026 年 9 月 14 日

推理工程师必须懂硬件，不是"会买卡"，而是"会算账"。这一篇讲 GPU 显存的物理现实、为什么"放得下"不等于"跑得动"、Apple Silicon 统一内存的陷阱、以及多卡并行怎么规划容量。

推理工程师必须懂硬件，不是"会买卡"，而是"会算账"。这一篇讲 GPU 显存的物理现实、为什么"放得下"不等于"跑得动"、Apple Silicon 统一内存的陷阱、以及多卡并行怎么规划容量。

一、GPU 显存层级：你必须知道的三层

1.1 三层存储

层 位置 容量 带宽 延迟
寄存器 / SRAM（shared memory） 片上 KB-MB 级 几十 TB/s 几 ns
HBM（显存） 板载 几十-几百 GB 1-8 TB/s 几百 ns-μs
主机内存 / NVLink 互联 板间 TB 级 几十-几百 GB/s μs-ms

推理的关键现实：权重和 KV cache 在 HBM，每次计算要搬到 SRAM。 decode 阶段瓶颈就是 HBM→SRAM 这条搬运（带宽）。理解这点，所有优化都通了。

1.2 各代 GPU 的关键数字

GPU 架构 HBM 容量 HBM 带宽 FP16 算力 特性
A100 80G Ampere 80 GB 2.0 TB/s 312 TFLOPS 主流，FP16 好
H100 80G Hopper 80 GB 3.35 TB/s 989 TFLOPS FP8 原生，TMA
H200 Hopper 141 GB 4.8 TB/s 989 TFLOPS 大显存+高带宽
B200 Blackwell 192 GB 8.0 TB/s 2250 TFLOPS FP4，超大规模
RTX 4090 Ada 24 GB 1.0 TB/s 165 TFLOPS 消费级，性价比
L40S Ada 48 GB 1.0 TB/s 121 TFLOPS 数据中心消费级

观察：带宽代际增长慢于算力。 这就是为什么 decode（memory-bound）越来越成为瓶颈，以及为什么量化（减带宽需求）越来越重要。

二、显存预算：上线前必做的账

这是 inference engineer 最该养成习惯的练习。别等 OOM 才算，上线前就要算。

2.1 预算公式

推理峰值显存 ≈ 权重 + KV cache 池 + 激活/临时 + 框架/CUDA 开销

各项怎么估：

权重：参数量 × 位宽。

70B FP16 = 70e9 × 2 = 140 GB
70B INT4  = 70e9 × 0.5 = 35 GB
8B FP16   = 8e9 × 2 = 16 GB

KV cache 池：上一篇的公式，乘以目标并发。

单请求 cache = 2 × layers × (in_len + out_len) × hidden × dtype × (kv_heads / heads)
池 = 单请求 cache × 目标并发

激活/临时：prefill 时中间张量。粗估权重的 10-20%，prefill 块大时更多。

框架/CUDA 开销：留 1-4 GB 给 CUDA context、PyTorch、kv cache block table 等。

2.2 一个完整估算示例

场景：Llama-3-70B（80 层，hidden 8192，GQA 8 kv heads of 64），AWQ INT4，A100 80G × 2（TP=2），目标并发 32，平均 in=2048 + out=512。

权重 INT4: 70B × 0.5 / 2(分到2卡) = 17.5 GB/卡

单请求 cache (FP16):
  2 × 80 × (2048+512) × 8192 × 2 × (8/64) 
  = 2 × 80 × 2560 × 8192 × 2 × 0.125
  = 2 × 80 × 2560 × 8192 × 0.25
  ≈ 838 MB/请求

池: 838 MB × 32 = 26.8 GB/卡
（注意 GQA 把 cache 除以 8，否则会大 8 倍）

激活/临时: ~17.5 × 0.15 ≈ 2.6 GB/卡
框架开销: ~2 GB/卡

单卡总: 17.5 + 26.8 + 2.6 + 2 ≈ 48.9 GB
A100 80G 余量 31 GB → 富余，并发还能加

这就是"先算账再上线"。如果算出来超了，要么降并发、要么换更大卡、要么更激进量化。

2.3 这正是 Inference Lab OOM 文章的核心教训

Inference Lab 的 OOM 文章实测：16 GB 权重的 27B 模型，24 GiB M5 Pro，clean boot 79% 空闲内存，256 token prompt 就 OOM。文章的教训：

文件字节 ≠ 内存预算。 "16 GB < 24 GB 所以放得下" 是错的，因为： - 可用显存 ≠ 物理内存（系统、其他进程占走） - 推理峰值 = 权重 + KV cache + 激活 + 临时 + 框架 - MLX active/cache/peak、RSS、swap 是四套账本，不能加成一个数

四套账本不可加——这是 Apple Silicon / MLX 用户特别要记的：

计数器 是什么 不是什么
MLX active allocator 活跃 buffer 不是全部进程内存
MLX cache 可复用 freed buffer 不是活跃状态
MLX peak 高水位线 不是当前值
RSS OS 看的进程驻留 不是 MLX-only
swap 系统级换页 不是进程独有

它们不能叠加成"总内存"。 看一个数（比如 active）就够判断趋势，不要把五个加起来。

三、Apple Silicon 统一内存：优势和陷阱

3.1 优势

Apple Silicon（M1-M5）的统一内存：CPU 和 GPU 共享同一池物理内存。MLX 的文档强调：不需要 CPU↔GPU 拷贝（传统 GPU 要 cudaMemcpy）。这让在小机器上跑大模型异常方便——一台 M5 Max 128G 能本地跑 70B 量化。

3.2 陷阱

但"统一"不等于"无限"。Inference Lab 实测踩的坑：

  1. 可用显存 ≠ 牄理内存。M5 Pro 24 GiB，clean boot 只有 79% free（系统占走 21%）。recommendedMaxWorkingSetSize（Apple 的"不影响性能的分配上限"）是个近似值，不是精确空闲量。
  2. 峰值比权重大。27B INT4 权重 16 GB，但 prefill 时 active 涨到 18.7 GB，peak 18.9 GB——超出可用就 OOM。
  3. lazy evaluation 的延迟压力。MLX 惰性求值，Python 写完计算图不立即算，访问时才触发。压力可能在你以为"已经过危险区"之后才出现。

3.3 Apple Silicon 的容量规划建议

实际可用 GPU 内存 ≈ 物理内存 × 0.6-0.75（系统占用 + 安全余量）
能跑的模型权重 ≈ 实际可用 × 0.5-0.6（留 KV cache + 激活）
  即 24G → 可跑 ~7-9 GB 权重 → 7B INT4 (3.5G) 安全，13B INT4 (6.5G) 紧张
  即 128G → 可跑 ~38-46 GB → 70B INT4 (35G) 紧张但可行

实践：Apple Silicon 跑大模型，别信"16G 权重 < 24G 内存所以能跑"。按上面公式留足余量，且短 prompt 先试（KV cache 小），长 prompt 要单独测。

四、多卡并行：TP / PP / DP / EP

4.1 张量并行（Tensor Parallel, TP）

每层权重切到多卡，每卡算一部分，all-reduce 合并。最常见。

  • 适合：单层放不下 / 想加速单层计算。
  • 代价：每层 all-reduce 通信。度数 ≤ 8（再大通信反噬）。
  • 配置：vLLM --tensor-parallel-size N。

4.2 流水线并行（Pipeline Parallel, PP）

把不同层切到不同卡，请求像流水线一样流过各卡。

  • 适合：层多，TP 度数到顶还不够。
  • 代价：bubble（流水线气泡），效率不如 TP。要 micro-batching 缓解。
  • 较少单独用，常和 TP 组合。

4.3 数据并行（Data Parallel, DP）

多个完整模型副本，各服务不同请求。

  • 适合：单卡能放下整个模型，要扩吞吐。
  • 代价：副本间不共享 cache（除非有分布式 cache）。
  • 简单扩容，但要前面有负载均衡。

4.4 专家并行（Expert Parallel, EP）

MoE 模型专属：不同 expert 放不同卡，按路由分发。

  • 适合：MoE 大模型（DeepSeek、Mixtral 等万亿级）。
  • 代价：路由 + all-to-all 通信复杂。
  • 前沿，配 vLLM/SGLang 的 MoE 支持。

4.5 组合实践

单卡放不下 → TP（首选）→ TP 到顶不够加 PP
单卡放得下要扩吞吐 → DP
MoE 大模型 → TP × EP × DP 组合
多机 → NCCL 互联，节点内 TP，节点间 DP/EP

五、网络与互联：别只看卡，看互联

多卡多机，互联带宽决定通信开销：

互联 带宽 场景
NVLink 300-900 GB/s 节点内 GPU，TP/PP 首选
NVSwitch 更高 多 GPU 全互联
PCIe 4/5 32-64 GB/s 消费级，慢
InfiniBand 200-400 Gbps 节点间，大规模
以太网 RoCE 100-400 Gbps 节点间替代

TP 强依赖 NVLink。消费级多卡（PCIe 互联）跑 TP 通信开销大，往往不如单卡。所以"两张 4090 不如一张更好的卡"在推理里常常成立。

六、硬件选型的实践决策

6.1 按场景

场景 推荐
个人/原型 消费级单卡（4090/5090）或 Apple Silicon
小团队生产 A100/H100 单卡或 2-4 卡 TP
中大规模生产 H100/H200 集群，NVLink + IB
极致大规模 B200 NVL72，或 H100/H200 大集群
边缘/CPU llama.cpp，GGUF 量化

6.2 性价比直觉

  • 消费级（4090）：$每 GB 显存贵，但带宽尚可，原型友好。24G 是硬上限。
  • A100 80G：成熟稳定，FP16 好，性价比基准。
  • H100/H200：贵但 FP8 + 高带宽，大规模划算。
  • B200：超大规模才回本，单卡贵。
  • Apple Silicon：本地/原型无敌，不能扩成集群。

七、分布式通信原语：all-reduce / reduce-scatter / all-gather（Atlas #30 补强）

前面讲了 TP/PP/DP/EP「切什么」，但「切了之后卡之间怎么同步」靠的是通信原语。这一节补 Atlas #30：三个核心 collective、ring vs tree 拓扑、NVLink/IB 带宽差异，以及它们怎么决定 TP/CP/EP 的真实开销。理解了才能看懂「为什么 TP 度数 ≤8、为什么 CP 用环状、为什么 EP 要 all-to-all」。

7.1 三个核心 collective

Atlas 原图的要点：reduction（约简，把多值合成一个）和 gathering（拼接，把分片拼全）是不同操作。

原语 干什么 结果在哪 谁用
all-reduce 所有 rank 的值约简（如求和），结果广播到每卡 每卡都有全量结果 TP（每层）、DDP（梯度）、CP（环状）
reduce-scatter 约简后分片给各 rank，每卡拿一块 每卡拿约简结果的一块 ZeRO、大梯度同步（RS+AG 组合实现 all-reduce）
all-gather 各 rank 的分片拼接成全量，广播到每卡 每卡都有全量 ZeRO 参数重组、TP 的 K/V 收集

关键：reduce-scatter + all-gather 组合 ≈ all-reduce——只是把「全量约简」拆成「分片约简 + 再拼全」，通信量一样但能和计算重叠。这是 ZeRO/Zero-bubble 能藏通信的根。

7.2 ring vs tree 拓扑

  • ring（环）：数据沿环传递，每跳约简/拼接一段。通信量 = (n-1)/n × 数据量（恒定，不随卡数爆炸）。适合大消息（如梯度、TP 的激活）。TP/CP 常用 ring。
  • tree（树）：层次化约简/广播，延迟 = O(log n)。适合小消息 + 对延迟敏感。NCCL 会自动选或混合。
  • NCCL 的 all-reduce 默认根据消息大小在 ring/tree 间切。

7.3 NVLink / IB 拓扑：域内快、跨域慢

  • NVLink 域内（单机 8 卡）：带宽 ~300-900 GB/s，all-reduce 几乎免费。
  • 跨节点（IB/Ethernet）：带宽 ~50-100 GB/s（甚至更低），延迟高。跨节点的 all-reduce 是延迟/带宽杀手。
  • 这就是为什么 TP 度数建议 ≤8（单机 NVLink 域）：TP 每层都要 all-reduce，跨节点 TP 会被通信拖垮。跨节点该用 PP/DP（通信频率低）。
  • CP（Context Parallel）用环状 all-reduce：环正好和「序列分段沿 ring 传」匹配。
  • EP（Expert Parallel）用 all-to-all：token 发往对应 expert 所在的卡，是 all-to-all 模式，对网络拓扑更敏感——跨节点 EP 要高带宽。

7.4 对各并行的影响汇总

并行 核心 collective 通信频率 跨节点可行性
TP 每层 all-reduce 极高 差（≤8 卡/单机）
CP 环状 all-reduce 高 中（要 NVLink/IB）
EP all-to-all 中 中（要高带宽）
PP 点对点 send/recv 低（层边界） 好（跨节点首选）
DP（推理） 无（不同步） 零 极好

7.5 实操：怎么诊断通信瓶颈

  • NCCL debug：NCCL_DEBUG=INFO 看每个 collective 的带宽利用率。
  • profiler：看通信占总时间多少。TP 度数 8 且通信 >20% → 考虑 PP/DP 替代。
  • 拓扑感知：部署时把 TP/CP 卡放同一 NVLink 域，PP/DP 可跨节点。

7.6 tradeoff 与 Atlas 告诫

  • 通信不是「免费」：加卡 ≠ 线性提速，通信开销随并行度上升，Amdahl 定律决定上限。
  • Atlas：「Every participant must use compatible shapes, types」——shape/类型不一致会让 collective hang（这是「加卡反而卡死」的常见原因）。
  • 训练 DDP 的 all-reduce ≠ 推理 DP：推理 DP 不同步（无梯度），所以推理扩副本几乎无通信——别把训练的通信成本套到推理扩容上（第 19 篇边界认知）。

九、原书补强：装得下≠服务得动、多节点切法、Dynamo 定位（Kiely §5.4/§4.4）

精读原书后补三条多卡规划的关键事实。

1. 装得下权重 ≠ 服务得动。 以 DeepSeek-V3.1（671B 参数，FP8 约 1GB/1B 参数 → 权重≈671GB）为例：单张 B200（180GB）直接 OOM；4×B200 = 720GB 理论上能装下权重，但 KV cache 常占掉权重之外 80%+ 的剩余显存，4 张卡没有 KV 余量、无法服务任何合理序列或 batch——必须整节点 8×B200。估算最小 GPU 数 = 精度 × 参数量 × 预期 KV cache 分配，再向上取整到可用实例。这条比“权重装得下就行”严苛得多。

2. 多节点的 dense vs MoE 切法。 跨节点（InfiniBand，慢于 NVLink）时 TP 因同步开销过大不适用，两种标准切法：

  • Dense 模型 → 节点内 TP + 节点间 PP（TP8PP2）：更低单用户延迟。
  • MoE 模型 → EP16：更高系统吞吐（EP 的跨卡通信只在 token 传 expert 之间，不收每层结果，故比 TP 更适合多节点）。

3. NVIDIA Dynamo 的定位。 Dynamo 不是又一个推理引擎，而是跑在 vLLM/SGLang/TensorRT-LLM 之上的编排层，提供分布式 KV 路由、解耦、多节点并行，并带一个SLA-based planner：按用户定义的 TTFT/TPS 约束实时扩缩 prefill/decode worker。Dynamo 是为规模造的（万亿参数级 Kimi 服务大量并发用户）；量不够时直接用引擎、上 Dynamo 是多余开销。
