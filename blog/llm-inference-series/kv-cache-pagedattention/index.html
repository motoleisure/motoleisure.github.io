03 · KV Cache 深度解析：PagedAttention、命中率真相、驱逐策略

Tim Chan 发布于 2026 年 9 月 14 日

KV cache 是推理引擎的"心脏"。它决定你能服务多长上下文、多大 batch、多少并发。这一篇从显存碎片讲起，到 PagedAttention、prefix caching 的命中率真相，再到缓存驱逐——最后用 Inference Lab 的 "cache hit 不证明你跳过了工作" 这篇审计文章收尾。

一、问题起点：KV cache 的显存碎片

上一篇算了 KV cache 有多大。但工程上还有一个更隐蔽的问题：显存碎片。

1.1 连续分配的死结

早期做法（naive）：每个请求来了，预先按它的 max_seq_len 申请一整块连续显存放 KV cache。

假设 max_seq_len = 2048，batch=64。每个请求先占 2048 长度的 cache 槽。但实际很多请求只生成 100 个 token 就结束——预申请的 2048 槽里 1948 个全是浪费。极端情况显存利用率只有 20-40%，大量显存被"预占但没用"的空洞吃掉。

更糟的是外部碎片：请求长度不一，频繁分配/释放，显存被切成大小不一的空洞。一个新请求想要一块连续的大空间，明明总剩余够，但没有一块连续的够大——OOM。

1.2 这就是 PagedAttention 要解决的问题

vLLM 的 PagedAttention（2023 年 SOSP）借用了操作系统的虚拟内存分页思想：

  • 把 KV cache 切成固定大小的 block（通常 16 token 一块）。
  • 一个请求的 cache 不再是一整块连续显存，而是由若干 block 组成，block 之间逻辑连续、物理分散。
  • 用一个 block table（页表）记录"逻辑 block i → 物理 block j"的映射，attention 时按表查地址。
  • block 是全局共享池，请求结束归还，谁需要谁拿。

效果：显存利用率从 ~20% 提升到接近 96%，同样显存能服务 2-4 倍并发。这是 vLLM 当年一战成名的核心。

二、PagedAttention 怎么做 attention

传统 attention（FlashAttention 风格）假设 K/V 在一块连续显存里。PagedAttention 要在"分块物理分散"的情况下算 attention，靠的是一个定制的 kernel：

对每个 query head 的每个位置 q_i:
  for block b in request 的 block 序列:
    从 block table 拿到物理地址
    加载该 block 的 K, V 到 shared memory
    算 q_i 和 block 内 K 的 score → attention → 累加到输出

关键工程点：

  1. block size 选择：太小 → kernel launch 开销、访存不连续；太大 → 碎片回归、预占浪费。vLLM 默认 16，是个经验平衡。
  2. kernel 要手写：PyTorch 原生算不了"按页表分散访存"的 attention，所以要写 CUDA kernel（vLLM 用 Triton/CUDA，SGLang 也有自己的）。
  3. copy-on-write 复用：当两个请求共享一段 prompt 前缀（见下文 prefix caching），物理 block 被共享、只读。只有 diverge 的位置才复制新 block。这是 PagedAttention 顺带支持的。

三、Prefix Caching（Automatic Prefix Caching）

3.1 场景

很多请求有相同前缀。最典型：

  • system prompt：每次对话开头都是同一段几千 token 的系统指令。
  • few-shot 例子：固定的几个示例。
  • RAG 的检索结果：同一文档被多次引用。
  • 多轮对话：前面 N 轮的 token 完全一样。

这些前缀的 prefill（算 K/V）完全可以只算一次，缓存下来，后续请求直接复用。省掉的就是 TTFT 的大头。

3.2 怎么实现

PagedAttention 的 block 结构让 prefix caching 变得自然：

  1. 一个请求 prefill 完，它的 KV cache block 不立刻释放，进 LRU 池子。
  2. 新请求来了，引擎算它的 prompt 哈希，和池子里比对：有没有一段前缀的 block 可以复用？
  3. 命中的 block 直接挂到新请求的 block table（只读共享），只有分叉之后的新 token 才分配新 block。

SGLang 把这个机制做得更激进，叫 RadixAttention：用一棵基数树（radix tree）管理所有缓存的 prompt 前缀，自动找最长公共前缀复用。对 agentic / 结构化场景（频繁复用相同 system prompt + 工具定义）效果显著。

3.3 开启方式（vLLM 示例）

vllm serve Qwen/Qwen2.5-7B-Instruct \
  --enable-prefix-caching

vLLM 默认开启（V1 引擎）。SGLang 默认就带 RadixAttention。

3.4 命中率：别盲目相信"cache hit"

这里有个 Inference Lab 文章专门敲的警钟。引擎报告"cache hit，复用了 8 个 token"——但这不等于它真的跳过了那 8 个 token 的计算。可能的情况：

  • 引擎报告命中，但 prompt path 仍在重算那 8 个（attestation 和实际行为不符）。
  • 命中的前缀虽然长度相同，但 token id 不同（比如同长度但内容不同的请求）——根本不该命中。
  • namespace 隔离导致本该命中却 miss，引擎只报 miss，不告诉你是因为隔离还是冷启还是驱逐。

Inference Lab 的做法是建一个 KV-cache truth auditor：用一个独立的 token oracle（按精确 token 身份和缓存策略重新计算"理论上应该复用几个"），再和引擎的 attestation 比对，再和 prompt path 实际处理的 token 数比对。三路一致，才算"真的命中且真的跳过了工作"。

10 个合成测试用例的结论：

用例 输入 预期复用 引擎报告 实际处理 判定
exact-duplicate 9 8 8 1 verified_hit
interior-mutation 9 3 3 6 partial_reuse
same-length-different-ids 9 0 0 9 verified_miss
suffix-change 9 8 8 1 partial_reuse
namespace-isolation 9 0 0 9 verified_miss
capacity-revisit 4 0 0 4 evicted

关键陷阱是 same-length-different-ids：请求长度一样，但 token 不同，长度相等不等于身份相等，不该复用。一个天真的缓存按长度比对就会误命中。

实践 takeaway：生产环境看缓存命中率指标时，要区分"引擎报告的命中"和"实际省下的计算"。如果 TTFT 没有明显下降但命中率显示很高，要怀疑 attestation 和实际行为是否一致。做关键场景的端到端 TTFT 对照比单看命中率数字更可靠。

3.5 前缀复用的失效条件（Atlas #07 边界）

Atlas #07 的“Tradeoff to own”列了一组常被忽略的前缀缓存不兼容源——第一个分叉 token 之后的匹配不再重启普通前缀复用，且以下任一变化都会让“看似相同的前缀”实际不可复用：

  • 分词器（tokenization）变化：换 BPE/vocab、换 tokenizer 版本 → 同样文本切出不同 token，前缀身份变了。
  • 模型版本 / 权重 revision：同结构但权重更新 → KV 状态语义不同，不能跨版本复用。
  • adapter / LoRA：挂了不同 adapter，KV 是按 base 算的还是带 adapter 算的？混用会让“命中”其实是错的。
  • 位置编码处理（position handling）：RoPE 基频、长度外推、多模态位置拼接不同 → 即便 token id 相同，位置嵌入不同，KV 不兼容。
  • 隔离策略（isolation policy）：namespace/租户隔离使本该命中却 miss（见 §3.4）。

实践：prefix caching 不是“前缀文本相同就一定复用”。监控要盯“预期复用 vs 观测复用”的差距，差距大就查这五类不兼容源——这和 Inference Lab“cache hit 不证明跳过了工作”是同一条纪律。

四、缓存驱逐与容量管理

4.1 为什么需要驱逐

显存有限，KV cache 池子不可能无限大。当新请求需要 block 而池子满了，引擎要决定驱逐谁。这是经典的缓存替换问题，但 LLM 场景有自己的考量。

4.2 常见策略

策略 思路 适合场景
LRU（最久未用） 优先驱逐最久没被访问的 通用，最常见
FIFO 先进先出 简单，但可能驱逐刚要被复用的
基于优先级 按请求优先级/付费等级 多租户，VIP 不被驱逐
基于命中概率 估计未来还会不会被访问 更智能但更复杂

4.3 vLLM 的抢占式调度（preemption）

vLLM 有个独特设计：当显存不够，它不只是驱逐——它可以把整个请求的 KV cache 换出（recompute 或 swap 到 CPU）。

  • RECOMPUTE：直接丢弃该请求的 cache，等显存空了再从头 prefill（用 prefix cache 可以恢复大部分）。
  • SWAP：把 cache 搬到 CPU 内存，需要时搬回来（要 CPU-GPU 带宽，慢）。

这给了引擎"先答应所有请求、实在不行再回收"的弹性，但代价是被抢占的请求延迟突增。生产里要监控抢占频率——频繁抢占说明容量不够，该加卡或限流。

4.4 容量规划公式

一个常被忽略的估算：KV cache 池大小 决定了同时能 hold 多少请求的 cache：

可用 KV cache 池 ≈ 总显存 - 权重 - 激活/临时 - 系统预留
同时驻留请求数 ≈ KV cache 池 / 平均每个请求的 cache 大小

平均每个请求 cache 大小 ≈ 2 × layers × (avg_input_len + avg_output_len) × hidden × dtype × num_kv_heads / num_heads（GQA 下要除以头数比）。

实践：上线前一定要把这个数和你的目标并发数对一遍。如果"同时驻留请求数" < 目标并发，要么加显存、要么用 GQA/MQA 模型（减 KV 头数）、要么靠 prefix cache 提高共享率、要么限流。

五、GQA / MQA：从模型侧省 cache

除了引擎层，模型架构本身也能省 cache。关键在 KV 头数。

  • MHA（传统）：每个 attention layer 有 H 个 query head 和 H 个 KV head，一一对应。KV cache = 2 × L × seq × hidden × H。
  • MQA（Multi-Query Attention）：所有 query head 共享 1 个 KV head。KV cache 直接除以 H。代价是质量略降。
  • GQA（Grouped-Query，Llama-2/3 用）：折中，H 个 query head 分组共享 G 个 KV head（1 < G < H）。质量和带宽平衡。

Llama-3-8B 用 GQA，KV head 数从 32 降到 8，KV cache 直接省 4 倍。这就是为什么 Llama-3 能跑更长上下文。选模型时，KV 头数是个隐藏但重要的维度。

六、实践 checklist：KV cache 工程

  • [ ] 会算 KV cache 大小公式（含 GQA 头数修正）
  • [ ] 容量规划时先算"同时驻留请求数"再定并发目标
  • [ ] 生产开启 prefix caching / RadixAttention，监控命中率 和 TTFT 改善是否一致
  • [ ] 对"长度相同但内容不同"的请求做隔离测试，确认缓存不会误命中
  • [ ] 监控抢占/换出频率，频繁抢占 = 容量不足信号
  • [ ] 选模型时关注 KV 头数（GQA/MQA），它对长上下文成本影响巨大
  • [ ] 用独立 oracle 校验引擎报告的 cache 命中（关键场景），别只信数字
