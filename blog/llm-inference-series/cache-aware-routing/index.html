17 · 缓存感知路由与 KV 分层存储

Tim Chan 发布于 2026 年 9 月 14 日

*Atlas 补强篇（对应 Technique Atlas #09 / #10）*。多副本服务里有两个真实的成本黑洞：一是"每轮对话落到不同 worker，前缀缓存全废，重复 prefill"；二是"GPU 放不下所有可复用上下文，丢了又得重算"。这一篇讲怎么治——缓存感知路由把可复用 cache 纳入 worker 选择，KV 分层存储把 cache 溢到更便宜的地方。两者都有一条铁律：命中率不是目标，总期望完成成本才是。

一、问题：多副本里的两个黑洞

1.1 缓存局部性丢失（#10 动机）

一个多副本 chatbot，前面有 N 个 worker。用户多轮对话每一轮打到 LB（负载均衡器），LB 默认按"最闲的 worker"路由。结果：第一轮 prompt 在 worker A 算了 prefill、建了 KV cache；第二轮（带第一轮上下文）被路由到 worker B——B 没缓存，从头 prefill 一遍。

  • 代价：重复 prefill = 重复算力 + 用户多等一个 TTFT。长上下文场景里这是真金白银。
  • 直觉解法："把带相同前缀的请求路由到同一个 worker"——但这就掉进第二个坑。

1.2 缓存局部性 → 热点

如果死板地"总是路由到有缓存的 worker"，热门前缀会让那个 worker 排队爆满——warm 但过载的 worker 成了慢路径。Atlas 的原图就是这个意思："The worker with the cache is a candidate, not an unconditional destination."（有缓存的 worker 只是候选，不是无条件目的地。）

所以两条都不对： - 只看队列长度 → 丢缓存、重复 prefill。 - 只看缓存命中 → 制造热点、排队变长。

正确答案：比较总期望完成成本。

二、缓存感知路由（Cache-aware routing，#10）

2.1 核心公式

选 worker 时不能只看 hit/miss，要比较每个候选的总期望完成成本：

cost(worker) = queue_time           # 已排队的等待
             + (1 - hit) × prefill_cost   # 没命中要重算 prefill 的代价
             + hit × transfer_cost        # 命中但要从慢层搬回 KV 的代价
             + execution_time             # 实际 decode
  • 命中的 worker 候选：省掉 prefill_cost，但要加 transfer_cost（如果 KV 在慢层）。
  • 没命中的 worker：要付 prefill_cost，但可能队列空。
  • 选 cost 最小的那个，而不是 hit 最高的那个。

2.2 什么时候命中反而更慢

这是 Atlas 反复强调的、最反直觉的点："A cache hit in slow storage can be slower than recomputation."（慢存储里的 cache 命中可能比重算还慢。）

  • KV 在 GPU HBM：命中 ≈ 省掉 prefill，纯赚。
  • KV 在 Host RAM：要 PCIe 搬回，几十 GB/s 带宽，长上下文可能几毫秒到几十毫秒——比 prefill 算还快，赚。
  • KV 在本地 SSD / 远端网络存储：搬运带宽更低、延迟更高，搬回来的时间可能比重算 prefill 还长。这时"命中"反而是亏的。

→ 路由器要拿到 KV 当前在哪个 tier 的信息（residency），不是只"命中过"。tier 级别决定 transfer_cost。

2.3 热点与 failover

  • 完美局部性制造热点：所有同前缀请求挤到一个 worker。
  • failover 要处理 residency 丢失：worker 挂了、扩容时新 worker 没缓存、cache 被驱逐（LRU）——residency 信息会过期。路由器要能优雅降级到"按队列长度+prefill 成本"的常规路由。
  • residency 信息一致性：多个 router 副本时，cache residency 表要一致或最终一致，否则路由决策打架。

2.4 和第 11 篇成本路由的区别

第 11 篇：质量门控路由 本篇：缓存感知路由
路由依据 模型质量分级（大模型 vs 小模型） KV cache residency（命中/不命中/tier）
目标 省 cost（便宜模型兜底） 省 TTFT + prefill 算力
联动 按请求难度路由 按请求前缀路由

两者正交，可叠加：质量门控决定"用哪个模型"，缓存感知决定"打到这个模型的哪个副本"。

三、KV-cache 分层存储（#09）

3.1 动机

一个文档服务不可能把所有可复用上下文都留在 GPU HBM。丢了又重复 prefill 很贵。于是分几层：

GPU HBM   ←── 最近、最快、最贵、容量最小
   ↓
Host RAM   ←── PCIe 带宽，容量大、便宜
   ↓
本地 SSD    ←── 容量更大、带宽更低
   ↓
网络/远端存储 ←── 容量最大、延迟最高（RDMA/对象存储）

Atlas 原图："More capacity usually means a longer path back to the GPU."（容量越大，回 GPU 的路越长。）——tier 越往下越便宜越能装，但取回越慢。

3.2 拿什么存、存哪、何时丢

owner 的三个决策：

  1. 留什么在快层：高频复用的前缀（system prompt、常见 RAG 前缀、热门会话）留 HBM。
  2. 溢到哪：低频但还可能复用的，按访问概率 + 搬运成本决定是 RAM 还是 SSD。
  3. 何时丢 / 何时重算：当 tier 命中的搬运时间 > 重算 prefill 时间，直接丢掉重算更划算。

→ 这就回到 2.2 的铁律：tier hit rate 不是目标，"搬回 vs 重算"的总成本才是。

3.3 实操组件（2026）

  • LMCache（vLLM 生态）：跨请求、跨副本的 KV cache 池，支持 GPU→CPU→SSD 分层，vLLM 集成。
  • Mooncake（Moonshot）：KV cache为中心的分离存储，prefill/decode disaggregated 场景的 KV 转移。
  • PagedAttention 的 block 粒度：KV cache 按 block 管理，block 可以在 tier 间搬运、引用计数、LRU 驱逐——这是分层存储能做的基础（第 03 篇讲的 PagedAttention）。

3.4 tradeoff 与证据

Atlas 列的证据指标：

指标 含义
tier hit rate 各层命中比例（HBM/RAM/SSD 各多少）
transfer time 把 KV 从慢层搬回 GPU 的时间
bytes moved 搬运量（看带宽压力）
recompute cost 重算 prefill 的时间（对比基准）
end-to-end latency 最终用户延迟（真北极）

关键诊断：如果 SSD tier hit rate 高但 E2E 没降反升——说明搬运时间 > 重算时间，应该把 SSD 的东西直接丢掉重算，或者把 SSD 降级为"只存、不主动搬回"的冷备份。

四、一个量化：搬回 vs 重算

假设一个 8K 前缀、70B 模型、GQA，KV cache ≈ 2×8K×2KB ≈ 32 MB。

层 带宽 搬回时间 重算 prefill（对比）
HBM 2-3 TB/s ~0.01 ms —
Host RAM (PCIe) ~50-80 GB/s ~0.4-0.6 ms prefill ~5-15 ms → 搬回更赚
本地 SSD (NVMe) ~3-7 GB/s ~5-10 ms prefill ~5-15 ms → 可能持平甚至亏
网络存储 视链路 几十 ms prefill ~5-15 ms → 大概率亏，重算更赚

数字为量级估算。结论稳定：越往下的 tier，"命中"的含金量越低，到达某层后命中不如重算。 这就是为什么不能"命中率越高越好"。

五、和 Inference Lab 的实证联动

第 14 篇 / kv-cache-truth-auditor 那篇的核心警告在这里直接适用：

"Cache hit 不证明你跳过了工作。"

  • 命中 ≠ 省了——可能只是从 HBM 命中（真省），也可能从 SSD 命中（搬运比重算还慢，反而亏）。
  • null ≠ zero：residency 表说"没命中"不等于"这个前缀从没算过"——可能算过但被 LRU 驱逐了，可能还在别的 tier。路由决策别把"没命中"当"没缓存"。
  • 独立 oracle 校验：tier hit rate 这个框架报的数，要和"实际 prefill 调用次数 / token 算力"对照——框架说命中率 80%，但 prefill 调用量没降，说明命中是"假命中"（慢层搬回后又被重算，或 residency 信息失准）。

这就是 Inference Lab 的三方核对纪律在缓存分层场景的直接应用。

六、责任边界

Atlas 把 #09 归 Inference / platform engineer，#10 归 Serving-platform engineer。inference engineer 要：

  1. 设计 residency 表与路由 cost 公式（不是写 LB 代码，但要定义 cost model）。
  2. 选 tier 策略（哪些留 HBM、溢到哪、何时丢）。
  3. 评估"搬回 vs 重算"边界，决定 tier 的取舍线。
  4. 监控 tier hit rate 和 E2E 的关系——防止"高命中但更慢"的假优化。

七、实践 checklist：缓存感知路由与 KV 分层

  • [ ] 路由 cost 公式包含 queue + (1-hit)×prefill + hit×transfer + exec，不只看命中率
  • [ ] residency 表带 tier 信息（HBM/RAM/SSD/网络），transfer_cost 按 tier 区分
  • [ ] 算清"搬回 vs 重算"的边界，决定哪些 tier 只作冷备份、不主动搬回
  • [ ] 防 hot spot：命中是候选不是无条件目的地，加队列长度约束
  • [ ] failover / 扩容时 residency 丢失要优雅降级到常规路由
  • [ ] 监控 tier hit rate 与 E2E 关系：高命中但没降延迟 → 查假命中
  • [ ] 独立 oracle 校验：框架命中率 vs 实际 prefill 调用量对照（Inference Lab 三方核对）
  • [ ] null ≠ zero：residency 表"没命中"不等于"没缓存过"，别据此全量重算
  • [ ] LMCache/Mooncake 这类组件 benchmark 搬回带宽，别信文档数字
  • [ ] 声明写边界："命中率 80%（HBM 60% / RAM 20%），E2E 降 35%——不是'开了缓存感知就快'"

八、原书补强：KVBM 与全局 G4 缓存（Kiely §5.3.2/§5.3.3）

精读原书后补两个本篇缺的组件/机制。

1. KVBM（KV Block Manager）——Dynamo 的 tier 搬运 API。 原书点名 NVIDIA Dynamo 通过 KVBM 提供 KV cache block 在不同显存层（GPU VRAM ↔ Host RAM ↔ SSD ↔ 网络）之间移动的 API。原则：最常用的 block 留在高带宽层，不常用的下沉到慢层待命。本篇 §3 讲了 tier 分层与“搬回 vs 重算”边界，KVBM 就是落地这套的工程接口（而非自己写搬运逻辑）。

2. 全局 G4 缓存——跨副本保活。 cache-aware routing 之外，可用 G4 网络存储建一个跨副本的全局 KV cache：routing 仍重要（热 G1 副本仍比读 G4 快），但全局缓存保证节点轮换/autoscale 缩容时缓存序列不丢、所有副本最终都能取到任意已算序列。这是“命中率 vs 总完成成本”之外的第三维考量：缓存生存性——单副本缓存再热，节点一换就没了；全局 G4 用带宽换生存。
