我把 FrontierAgent 做成了 DSH 的插件：零额外密钥 + 8 个踩坑实录

Tim Chan 发布于 2026 年 9 月 3 日

上一篇把 FrontierAgent 装上了 Mac，但它一直是座孤岛。这篇记录把它做成 DSH 插件的全过程——对话框里一条 /frontier 派活，复用当前模型跑完，结果自动回到对话；「能跑」和「跑得对」之间隔着 8 个坑。

上一篇把 FrontierAgent 装上了 Mac（《我在 Mac 上部署了开源 Agent「FrontierAgent」》）。但它一直是座孤岛：要切终端、开 TUI、手动复制结果，还单独维护一套模型端点和密钥。这篇记录我把它做成 DSH 插件的全过程——在对话框里一条 /frontier 派活，FrontierAgent 用 DSH 当前正在用的模型跑完，结果自动回到对话里。架构不复杂，但"能跑"和"跑得对"之间，隔着 8 个坑，每一个都记录下来。

一、动机：能跑的 FrontierAgent，为什么还要再折腾

上一篇结束时，FrontierAgent 的状态是：本地部署完成，TUI 可用，搜索工具（monid/Fathom）接好，模型端点打通。但日常用下来有两个挥之不去的别扭：

  1. 工作流断裂。我在 DSH（我的主力 Agent 工作台）里对话，想做个深度调研，得切到另一个终端窗口、./run.sh 开 TUI、输入任务、等结果、再手动把结论复制回来。一次调研切四次上下文。
  2. 两套模型账本。FrontierAgent 的模型配置躺在它自己的 .env 里（独立端点、独立 Key），跟 DSH 的模型配置是两本账。我在 DSH 里 /model 换了模型，FrontierAgent 毫无反应；密钥轮换、额度管理也全都不覆盖它。

目标很明确：

  • 在 DSH 里一条命令派活给 FrontierAgent；
  • FrontierAgent 跑的时候用 DSH 当前配置的模型——我在 DSH 里换模型，下一次调研自动跟着换；
  • 不搞第二套密钥，子进程最好连 provider key 都碰不到。

二、动手前：把两边的扩展点都摸一遍

FrontierAgent 侧：它提供什么可编程表面

翻 apodex/cli.py 和 docs/，关键发现四条：

发现 意义
--print 一次性模式 uv run frontier-agent --print "任务" 跑完打印结果退出，天然适合被脚本调用
-y / --max-turns / --input / --output-format jsonl 无人值守运行所需的旗标齐全
apodex/cli.py:43 自己 load_dotenv(override=False) 注入的环境变量优先于仓库 .env——这是整个方案的钥匙
依赖里已有 mcp>=1.28.1 理论上可以给它包一层 MCP server（后面会解释为什么没走这条路）

顺带确认了一个冷知识：FrontierAgent 原生支持 Anthropic Messages 协议。frontier_agent/core/runtime/loop/model_profile.py:45 定义了 WireProtocol = Literal["chat_completions", "anthropic", "responses", "bedrock"]，frontier_agent/infra/anthropic_client.py 是完整实现（真流式、tools、extended thinking、prompt cache 都有）。但出厂 profile 一个都没启用，全部默认走 chat_completions——所以它对外只会说 OpenAI 兼容协议。这个事实后面会反复用到。

DSH 侧：三条扩展缝

缝 机制 现状
Skill 往 ~/.dsh/skills/ 丢一个 SKILL.md，模型按说明自己组命令 零配置改动，但模型得自己拼 CLI 参数
MCP 客户端 @deepseek-ai/dsh-mcp-client，把外部 MCP server 的工具注册成 mcp__xxx__yyy 已经装在我的 web profile 里，只差一条配置
原生 Cordis 插件 ctx.tools 注册工具、ctx.llm 调模型、ctx.jobs 管后台任务 我在 ~/Documents/dsh-plugins/ 已有 4 个先例

为什么 MCP 和 Skill 都不够

核心需求是"用 DSH 当前配置的模型"，注意"当前"两个字——它要求每次调用时动态解析，而不是配置时写死。逐条对：

  • Skill：纯文本指令，模型通过 bash 调 CLI。能跑，但模型参数只能写死在说明里，且子进程直接持有 provider key。
  • MCP：stdio 条目的 env 是加载时静态求值的，无法在每次调用时读 DSH 的实时模型选择和凭据。除非 MCP server 自己去解析 DSH 的内部存储——那叫重新实现半个 DSH。
  • 另外 DSH 没有 OpenAI 兼容网关（它的 api-gateway 是内部 Typert RPC 桥，不是给外部客户端用的），所以"让 FrontierAgent 直连 DSH 的模型端点"没有现成入口。

结论：只有原生插件能在调用时读 ctx.llm 和会话状态。路线定了。

三、最终架构：回环 shim，模型调用全部回流 DSH

FrontierAgent 只会说 OpenAI 协议，DSH 的模型能力藏在 ctx.llm 里。那就中间架一座桥——一个回环 OpenAI 兼容服务器，背后接 ctx.llm.stream()：

/frontier 命令（GUI 输入）
  └─ frontier_research 工具
       └─ spawn `uv run frontier-agent --print --output-format jsonl ...`
            注入环境变量：
              OPENAI_BASE_URL = http://127.0.0.1:<随机端口>/v1
              OPENAI_API_KEY  = <一次性 token>
              OPENAI_MODEL    = <解析出的模型>
            ↓
          FrontierAgent 的每次模型调用 → 打回 shim
            ↓
          shim 翻译成 ctx.llm.stream({ provider, model, ... })
            ↓
          DSH 的 adapter / 凭据库 / 重试策略 / 密钥轮换，原样生效

这套架构的收益逐条看：

  1. 零额外密钥。子进程拿到的"API key"是一次性回环 token，真正的 provider key 始终不出 DSH 宿主进程。
  2. 模型跟着 DSH 走。/model 换成什么，下一次 /frontier 就用什么。
  3. UA 封锁问题自动消失。上一篇里端点屏蔽 AsyncOpenAI/Python UA 的坑，这里不存在了——请求最终是 DSH 发的，UA、header、重试全是 DSH 的行为。
  4. 一次注册，两个入口。模型可以调 frontier_research 工具，人可以直接打 /frontier 命令，共用同一条执行路径。

模型解析的优先级（index.js 的 resolveSelection()）：

优先级 来源 说明
1 插件 config 里钉死的 provider/model 想让调研任务固定走便宜模型时用
2 会话的实时路由 你在 DSH 里当前用的模型，/model 切换立即生效
3 部署默认模型 兜底

插件本体 5 个 JS 模块，分工如下：

模块 职责
index.js 工具注册、/frontier 命令、模型解析、job 接线
shim.js 回环 HTTP 服务器，随机端口 + 每次调用一枚一次性 bearer token
translate.js OpenAI 请求 → DSH 消息/工具（system 提取、tool_calls、tool 结果）
respond.js DSH 流式块 → OpenAI SSE chunk（含 tool_call 增量、usage 统计）
run.js 子进程管理：argv 构建、环境变量清洗、失败判定

一个必须说的设计细节：FrontierAgent 失败时也可能以 exit 0 退出，所以 run.js 不光看退出码，还扫描输出里的 workflow failed 标记行，两者取或——否则一次失败会被汇报成成功，模型会基于空结果继续推理。

四、踩坑实录

坑 1：pnpm install 要清空 node_modules——那会把正在跑的插件全解链

装插件的标准流程是往 profile 的 package.json 加 link 依赖，然后 pnpm install。我一跑，pnpm 表示要清空整个 node_modules 重建——而那个目录里链着我正在运行的其他 4 个插件，清空等于让线上 DSH 当场残疾。

解法：手工建符号链接。这个插件只 import node: 内置模块，没有任何第三方依赖，根本不需要 pnpm 的依赖解析：

ln -s ../../../Documents/dsh-plugins/dsh-frontier-agent \
      ~/.dsh/profiles/web/node_modules/dsh-frontier-agent

💡 教训：包管理器说"我要重建一切"的时候，先问一句"它要重建的东西里有没有正在服役的"。手工 symlink 不优雅，但它精确、可逆、不动别人。

坑 2：workspace 是真目录，里面躺着 27 个历史成果

第一次真实端到端测试，FrontierAgent 在任何模型调用之前就死了：

native workspace link is not replaceable

排查：.apodex/runtime/native/workspace 按设计应该是一个指向当次运行沙箱的软链，但它现在是个真目录——里面是之前几次运行产出的 27 个文件（字幕翻译的 zh_*.json、t1-t5.py 脚本）。FrontierAgent 要在这里重建软链，遇到真目录拒绝覆盖。

解法：移走，不删：

mv .apodex/runtime/native/workspace \
   .apodex/runtime/native/workspace.saved-20260901-152805

💡 教训：工具报错"某路径不可替换"时，先 ls 那个路径——里面可能有用户数据。这个原则后来在 stop 脚本、测试夹具上反复救场：凡是会删东西的修复，都先改成移走。

坑 3：模型根本看不见这个工具——委托型路由不转发宿主工具

这是最伤的一个坑，现象极其迷惑：插件装好了、测试全绿、DSH 重启了，但模型说"我没有 frontier_research 这个工具"。

我最初以为是没重启，查进程启动时间——重启明明发生了。然后查我自己：发现我这个会话的默认模型是 qd/claude-opus-5，而 qd 这条路由走的是 llm-claude 适配器，它的工作方式是派生一个 CLI 子进程，把整个回合委托出去。

翻源码对比两个适配器：

llm-pi-ai:   context.ts:117  → 把 DSH 工具表放进 request.tools，转发给模型 ✅
llm-claude:  零转发。README 原话：工具处理留在 CLI 自己的回合内 ❌

也就是说：在这条路由上，模型用的是子进程自带的工具集，DSH 注册的任何工具（包括我新加的）都不可见。 我的 /frontier 命令原本设计成"steer 一条消息，让模型去调 frontier_research"——等于让模型喊一个不存在的人。

解法：命令不再委托给模型，自己动手：收到 /frontier 就启动 FrontierAgent、注册后台 job，跑完后用 agent.followup() 把结果作为一条用户消息注入会话。这条路只依赖消息注入，不依赖工具可见性，任何路由都通。

💡 教训：给宿主写插件时，永远不要假设"模型看得见宿主注册的工具"。委托型/代理型路由（把回合交给子进程的）天然不带宿主工具表。设计命令和自动化路径时，优先走消息注入这种路由无关的通道。

坑 4：空会话里，命令卡片被欢迎页吞了——用户以为没发送，连点四次

修完坑 3，用户反馈："/frontier 能发出去了，但对话里什么都没显示，等几分钟结果返回了才突然出现。"

查会话日志，命令其实秒回了：

seq=3  command/run   frontier  "用一句话回答：Omarchy 是什么？"
seq=4  command/done  +14ms     "FrontierAgent started on qd/claude-opus-5 (job frontier-1)"

14 毫秒，回执也写进了会话。问题是它没有地方显示。DSH 的渲染层有一条规则（session.ts:793）：

// 只有命令行、没有其他内容的会话，算"空会话"
chat.order.some(key => chat.nodes.get(key)?.kind !== 'command')

命令属于"控制平面"，不算对话内容。空会话渲染的是居中的欢迎页，对话区组件直接 return null——卡片存在于状态里，但画不出来。等 FrontierAgent 跑完，followup() 注入了一条真正的消息，会话"激活"，卡片和结果才一起冒出来。

更糟的是后果：用户以为没发送，连点了四次，四个 FrontierAgent 进程真的全部启动，各自烧着 claude-opus-5 的预算，其中一个跑了 13 分钟。

解法：启动的同时，立即往会话追加一条插件来源的 user/message（notice），会话瞬间激活，卡片马上可见。注意这里不能用 agent.inject()——它走收件箱，只在某个模型步骤主动领取时才浮现，空会话上照样什么都不显示；必须直接 append 到会话日志。

agent.session.append({
  role: 'user',
  content: [{ type: 'text', text: `FrontierAgent 已启动（${route}，job ${jobId}）...` }],
  source: { kind: 'plugin', form: 'notice' },
})

💡 教训：长任务的用户体验底线是即时可见的确认。"我发了但界面毫无反应"在用户侧永远解读为"没发出去"，下一步就是重试——而对一个烧钱的嵌套 Agent 来说，重试 = 预算风暴。任何超过 10 秒的操作，启动瞬间就要在用户看得见的地方留下凭据。

坑 5：从 agent.options 读模型，读到的是"种子"不是"当前值"

某天 /frontier 突然报：FrontierAgent started on k/qwen3.8-max。但用户当前用的明明是 qd/claude-opus-5，配置文件里也没有任何地方钉过 qwen3.8-max。

会话日志是铁证：整个会话从头到尾每一次请求都是 qd/claude-opus-5，只有我的工具报了 k/qwen3.8-max。

根因：我读的是 agent.options，而它是 agent 创建那一刻写下的种子，之后永不更新（api-proxy.ts:1053，只在 create/resume 时塞入）。用户后来 /model 换模型，改的是另一个对象——请求阶段的实时路由引用。种子里躺着的是创建瞬间的旧值。

时间线更是直接指认现场：settings.yaml 的修改时间比命令发出时间早 5 秒——那 5 秒里配置被写入过一次又改掉，而 agent 的种子恰好定格在写入的那个瞬间。

解法：改读 session.requestHeader().config——这个会话上一次请求真正发出去的路由，/model 切换立即反映。同时修掉一个连带隐患：原来 provider 和 model 是分别回退的，可能凑出"A 家的 provider + B 家的 model"这种根本不存在的组合；现在路由整条取，不拆。

💡 教训：凡是语义上要求"当前值"的状态，都要问一句：我读的到底是 live source 还是创建时的快照？快照型字段（options、initial config、seed）在长生命周期对象上是默认谎言。

坑 6：qwen3.8-max 不接受 reasoning effort "high"，turns=1 直接暴毙

坑 5 还没修的时候，那次错误路由（k/qwen3.8-max）真的跑起来了，然后第一轮就挂：

turns=1  tool_calls=0  stopped_by=llm_error

原因：我把会话的 reasoningEffort: high 原样传给了目标模型，而 qwen3.8-max 不接受这个参数，LLM 调用直接 exhausted。一次都没搜，一条事实都没查——关于任务本身它什么都没做。

这坑的阴险在于报错形态：llm_error 看起来像网络问题、像端点故障、像任务太难，第一反应没人会想到"是 effort 参数不兼容"。

现状与对策：目前插件仍原样透传 effort（用户当前路由 claude-opus-5 支持 high，所以日常没再触发）。彻底的修法是按目标模型的能力清单过滤参数——已列入待办。临时规避：给不支持 effort 的模型钉配置时，路线整条钉死。

💡 教训：跨模型透传参数时，"上一个模型接受的参数"不等于"下一个模型也接受"。嵌套 Agent 的失败要先看参数兼容性再看任务难度——turns=1 + tool_calls=0 就是参数层死亡的指纹。

坑 7：我自己写错的探针，浪费 30 分钟证明了一个不存在的泄漏

测试套件跑完后运行器不退出。我怀疑句柄泄漏，写了个探针统计 Server 句柄：

Server handles: before=1 after=0   ← 期望
探针实际输出:  dispose 后仍有 1 个句柄未关

"找到真 bug 了！"——我顺着这个结论读销毁路径、翻 Node 的 closeAllConnections 文档、准备大改。折腾 30 分钟后，回头审探针本身，发现探针是坏的：

cordis 的 ctx.effect(cb) 收的是"返回 disposer 的回调"，而我的假 ctx 只把回调存起来，最后调用它拿回 disposer——但从未执行那个 disposer。也就是说 shim.close() 从头到尾没被调用过。我的探针实际测量的是："不关服务器会不会泄漏句柄？"——答案当然是会。

修正探针后：

Server handles: before=1 after=0
[exit code: 0]        ← 进程自己干净退出

没有泄漏。测试运行器不退出是收尾时序问题，与插件无关。

💡 教训：探针报异常时，第一反应应该是验证探针本身，尤其当探针是刚写的、没被测过的代码。用一个未被验证的工具去验证别人，等于把地基打在流沙上。那 30 分钟本可以在 10 分钟内止损：先让探针在"已知正常"的场景里跑一遍。

坑 8：FrontierAgent 失败也 exit 0——退出码不可信

写 run.js 时读 README 发现的：FrontierAgent 的部分失败路径仍以退出码 0 结束。如果只看退出码，一次彻底失败会被汇报成"研究完成"，上游模型会拿着空结论继续推理——错误就这样悄无声息地传播。

解法：双信号判定。detectFailure() 扫描输出里的 workflow failed 标记行，与退出码取或；命中则把 run 标记为 failed 并携带原文细节，而不是 completed。

💡 教训：包装任何外部进程时，先查它的失败语义再写成功判定。"退出码 0 = 成功"是被无数工具背叛过的假设。

五、验收

测试：5 个测试文件、52 个用例全绿。覆盖请求/响应双向翻译、shim 鉴权与端口、子进程 argv/环境清洗/失败判定、工具注册与模型解析（含"种子值必须被忽略"的回归用例）、命令路径。

其中两个回归用例就是坑 5 的疫苗：往解析器里故意塞一个过时的 agent.options，断言它被完全无视。

真实端到端（FrontierAgent → shim → 模型 → 回流）：

[thinking] The user is simply asking me to reply with READY...
READY
✓ done · turns=1 · 8,385 tokens (in 8,360 · out 25)
exit code 0

四个环节逐一确认：

环节 证据
FrontierAgent 真的把请求打回了 shim 回环端口收到 POST /v1/chat/completions，bearer token 校验通过
shim 正确转发给 ctx.llm.stream() provider/model 与解析结果一致
流式响应正确翻译回 SSE FrontierAgent 收到逐 token 流，thinking 正常
usage 统计穿过翻译层 8,385 tokens 与 FrontierAgent 自报一致

六、复盘：五条带得走的经验

  1. "工具已注册" ≠ "工具可用"。 委托型路由（把回合交给子进程的适配器）不转发宿主工具表。给宿主写插件，自动化路径优先走消息注入这类路由无关通道，别把关键路径押在模型能看见某个工具上。（坑 3）

  2. 创建时状态 ≠ 当前状态。 agent.options 这类种子字段在长生命周期对象上是默认谎言。要"当前值"就找 live source——上一次请求的路由、实时引用、每次调用时的解析。（坑 5）

  3. 长任务必须有即时可见的确认。 用户侧"发了没反应"永远等于"没发出去"，下一步就是重试。对一个按次烧钱的嵌套 Agent，重试就是预算风暴——我的用户连点四次，起了四个 opus 任务。（坑 4）

  4. 探针报异常，先审探针。 刚写的、未被验证的测量工具，没有资格给别人的代码定罪。让探针先在已知正常的场景里自证清白。（坑 7）

  5. 跨模型参数透传要做能力匹配。 turns=1 + tool_calls=0 + llm_error 是参数层死亡的指纹，不是任务太难。嵌套 Agent 排查顺序：参数兼容 → 端点连通 → 任务本身。（坑 6）

已知限制（README 有完整列表）

  • top_p / top_k / extra_body 不过桥；
  • 图片不过桥（Durable attachment 无法在 shim 侧凭空创建）；
  • 每次运行是新进程，不支持 --resume；
  • 子进程带 -y 自动批准，能在 cwd 里改文件跑命令——传一个你愿意被改的目录；
  • 产物实际落在 <cwd>/.apodex/runs/<session>/outputs/。
