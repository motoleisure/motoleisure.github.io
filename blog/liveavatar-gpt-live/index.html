把 GPT-Live-1 跑通的最小活样本：HeyGen 仓库逐行拆解

Tim Chan 发布于 2026 年 9 月 13 日

HeyGen 的 liveavatar-gpt-live-demos（MIT）用 GPT-Live-1 驱动实时数字人，开箱是日语家教。clone 下来逐文件精读源码：架构图里的每一根线，在真实代码里长什么样。

第 25 期我画了 GPT-Live-1 的架构图——全双工音频、前后端分离、Responses 委托、结果+continue 环。这一期钻进一个把它真正跑通的仓库:heygen-com/liveavatar-gpt-live-demos(MIT)。它用 GPT-Live-1 驱动 HeyGen LiveAvatar(实时数字人),开箱是一个日语家教——边说边把生词卡(term · 读音 · 释义)弹到画面上,每隔几个词把自己缩到角落做一次复习面板。我把它 clone 下来逐文件精读了源码(server/src/gptlive.ts v3 桥、session.ts 三腿接线、turns.ts turn 投影、tools.ts/prompts.ts 委托与工具、mediaServer.ts LITE 腿),不是只读 README。这一期讲的是:架构图里的每一根线,在真实代码里长什么样、踩了哪些图里看不到的坑。

一、先认出这个仓库:GPT-Live-1 架构图的最小活样本

一句话定位:HeyGen 官方放出的"最小可读参考集成"——刻意裸到只剩接线,你要读的是 wiring,不是一个框架。fork 它、换 persona、保留那张脸。 它对"如何应用 GPT-Live-1"的回答是:把数字人当成纯"音频→脸"渲染器,喂一条永不结束的连续语音流,所有工具调用通过 GPT-Live 的 Responses 委托链落在屏幕上。

仓库身份卡:

  • 仓库:github.com/heygen-com/liveavatar-gpt-live-demos,MIT,作者 dyi1。
  • 技术栈:Node ≥20.12 + pnpm,TypeScript,21 个 .ts 文件 + 10 个 .md 文档。
  • 两个外部依赖:LIVEAVATAR_API_KEY(HeyGen LiveAvatar)、OPENAI_API_KEY(需 GPT-Live 访问,GA 可用)。
  • 默认模型写在 server/src/config.ts:live 模型 = gpt-live-1(GPT_LIVE_MODEL 默认)、后端 Responses 模型 = gpt-5.4-nano(GPT_LIVE_RESPONSES_MODEL 默认)、默认音色 marin。
  • 开箱 persona 是 server/prompts/*.md 两个 markdown 文件:改它们就换 demo,不用碰代码。

注意那个后端模型名——gpt-5.4-nano 是写死在 config 里的。第 25 期架构图里我只敢写"后端≈GPT-5.4 系列"的推断,这个仓库把它坐实了:GPT-Live-1 的委托后端走 gpt-5.4 系列。

二、核心架构:三条 websocket + 一个 LITE 会话

这是整件事的骨架,来自 docs/ARCHITECTURE.md,和代码逐行对得上:

browser ──► POST /api/session/start ──► LiveAvatar /v1/sessions/token + /start   (服务端)
browser ◄── LiveKit room                                    (avatar 音频+视频)
browser ◄─► /ws/{session_id}                     (mic 上行;turns+visuals 下行)
server  ◄─► wss://api.openai.com/v1/live/sessions              (GPT-Live v3)
server  ──► LITE media-server ws_url              (avatar 的耳朵:音频缓冲)

LITE 会话是整件事的关键。 它"裸启动"(不带 agent 配置),一次返回三样东西:livekit_url + livekit_client_token(给浏览器看)+ ws_url(直通 avatar 媒体服务器的 websocket,让服务端把 GPT-Live 的音频直接灌进去,不经过浏览器)。LITE 协议很小:agent.speak(PCM16 24kHz base64 块)、agent.interrupt、session.keep_alive;一条铁律——在服务端报告 session.state_updated: "connected" 之前发的命令会被静默丢弃,所以 GPT-Live 腿必须等这个事件再开口,否则开场白就丢了。

浏览器永远不持 key 或 session token。 avatar 音频故意不走浏览器 websocket,而是已经和视频唇同步后通过 LiveKit 抵达浏览器。浏览器只做两件事:上行 mic 音频(/ws/{session_id}),下行收 turns + visuals。mic 用 AudioWorklet 降采样到 24kHz PCM16 base64,无 VAD——turn-taking 完全交给模型。

为什么不用 LiveAvatar 自带的 web SDK?仓库给了两条理由,都和工具调用无关:一是会话归属——SDK 假设浏览器持 session token 自己调 start(),但这里服务端必须自己调 /v1/sessions/start,因为 ws_url 只在那个响应里回来,音频腿没它不存在;二是会重复一套传输——服务端 start 之后浏览器只需 join LiveKit 房间挂两条轨道,约 50 行 livekit-client。

三、两个模型的分工:前后端分离的活样本

server/src/gptlive.ts 的第一条 session.start 把两个模型的角色写死了:

  • live 模型(gpt-live-1)说话、管 turn-taking,不持任何工具。 它被告知自己"不能在屏幕上画东西",要画面就把这轮 turn 委托给后端。
  • Responses 后端(gpt-5.4-nano)回答被委托的 turn,持有工具(shared/tools.ts 里三个工具:show_term_card / show_learned_words / hide_card),被告知每条回复必须同时带口述答案和工具调用——只调工具不说话,avatar 就沉默。

这就是第 25 期"前后端分离"架构图的真实落地:live 管对话和实时音频,Responses 管推理和工具。session.start 里 delegation.type = "responses" 把这个分工在会话级别固定下来,会话生命周期内不可变(代码注释:session.update 之后也只能改 delegation.responses 的设置,delegation 的类型定了就不能动)。delegation.responses 里还塞了 tool_choice: "auto"、parallel_tool_calls: false、reasoning: { effort: "low" }——后两个是精心选的:一次只出一个画面(模型没法自己说服自己多出),工具环也就简单到"一次调用 = 一个结果 + 一个 continue";委托在画面时序的关键路径上,"挑一张卡填字段"不需要深思。

四、委托机制:结果+continue,这是最实的一段

工具调用怎么从模型嘴里落到屏幕上,逐环节拆(server/src/gptlive.ts + session.ts + tools.ts):

① live 模型不持工具,要画面就把 turn 委托给后端。 LIVE_DIRECTIVE 里写死:"你不能自己在屏幕上画东西……学习者要词/短语/翻译时,把这轮委托给你的后端,让它答。委托绝不意味着暂停:自然地说下去,让视觉自然出现在你的话旁边——绝不静默等待,绝不说'等一下',也绝不说'画面出来了'之类。"

② Responses 后端一条回复里既答话又调工具。 RESPONSES_INSTRUCTIONS 那句承重:"ALWAYS answer in words as well as calling tools……a tool call with no text is an error。" 后端回复的文本会被服务自动注入回 live 会话并由 realtime 模型朗读——这是"后端告诉 realtime 模型说什么"的内置路径。编排器绝不能自己再放一遍这段文本(会双重播报)。

③ 工具调用从 response.output_item.done 驱动,不是它的孪生兄弟。 v3 里工具调用走两步:先到 response.function_call_arguments.done(不带 call_id 和 name),再到 response.output_item.done(带完整的 call_id/name/arguments)。桥只从后者驱动,用 call_id 去重(handledCalls Set)。

④ 结果 = response.item.create 然后 response.create——结果本身什么都不做。 这是 v3 最反直觉的一点,代码注释反复强调:"v3: the result alone does nothing. response.create must follow, or the backend never resumes and the avatar's spoken half never arrives。" 桥对每个完成的 function_call 调 onToolCall(name, args) 拿到结果(形状约定 {shown, error?, words?}),然后背靠背发两条:

send(ResponseItemCreate, { item: { type: "function_call_output", call_id, output: JSON.stringify(result) } });
send(ResponseCreate, { event_id: `continue_${callId}` });

后端收到 continue 继续它的回复——正是这个"继续"把语音和屏幕同步起来:复习流程是"工具触发 → 服务端从自己的词库渲染面板 → 结果把面板上确切的词回传 → 模型继续的回复正好念出这些词"。

⑤ 没答的调用会冻住整条会话。 注释明确:"an unanswered call stays pending and blocks every later delegation(confirmed by OpenAI; this was the frozen-delegation bug)。" 所以每条路径都发结果:渲染成功、失败、或参数解析不了——唯一例外是缺 call_id(根本没法答)。这是 v3 最大的隐藏陷阱:漏答一个,后面所有委托全堵死,avatar 卡在半句再也说不下去。

五、"callable ≠ called":散文委托一次都不触发

这是仓库最值钱的实测结论,代码注释原话:

"prose asking the live model to delegate its own teaching moments never fired once(backend_model_usage: []), while an explicit learner request('teach me the word for respect') delegated instantly。GPT-Live's delegation is trained for capability gaps(current information, deep reasoning), and teaching 'hello' is within its own ability, so it answers directly no matter what the prose says。"

含义很重:你写进 prompt 让它"教这个词时委托后端"是没用的,它自己能教就直接教了,不会委托。 GPT-Live 的委托是按能力缺口(查新信息、深推理)训练的,"教 hello"在它自己能力范围内,所以无论你散文怎么要求它都不委托。docs/MAKING_VISUALS_FIRE.md 整篇就在讲:哪些触发模式才真能让 visual 落地——"一个注册了但活会话里从不触发的工具,是预期失败,不是接线 bug"。

仓库的对策因此很务实:已知生词卡(教案里那三个词)服务端自己推——session.ts 监听转录,听到模型说出那个词就自己把卡推上去(taughtLessonTerms Set 去重),根本不靠模型委托。只把"学习者临时要一个新词/翻译"这种真正的能力缺口留给委托。这是第 25 期架构图没碰到的实操坑:图里画了"委托→工具→结果",但没告诉你模型什么时候才肯委托。

六、v3 删掉的两件事:音频没时间线,没有 turn 事件

v3 相对 v2 砍了两个东西,代码和文档都专门讲了为什么、怎么办:

① 音频 delta 不再带时间线。 v2 给每个音频 delta 盖 start_ms/end_ms 戳、还省掉话语间的静默;桥得重建那段静默,免得嘴比声音跑得快。v3 把时间线字段删了——契约变成"解码块、按顺序播"——所以没什么可重建的,块按到达顺序转发就行。仓库的注释点了一句要盯着:如果唇同步漂移,唯一剩下的时间信号是转录 delta 上的 start_ms/end_ms。

② 没有 turn 事件,turn 要自己投影。 v3 只发 session.input_transcript.delta 和 session.output_transcript.delta(200ms 帧,带文本和 session 时间线 start_ms/end_ms,空帧省略)。可下游全都要 turn(转录 UI、生词卡推送、复习点、打断 watch),所以 turns.ts 把 delta 投影成 turn:同说话人的 fragment 合进一个 turn;说话人静默超过 TURN_GAP_MS(1500ms)就关 turn——bursty 交付按 session 时间线判,最后一个没人跟的 fragment 按墙钟判。user/assistant turn 独立追踪、可重叠,这就是全双工。

第 25 期架构图里画的"无 turn 事件,要自己投影"那一节,在这里就是 turns.ts 这 113 行。

七、打断(barge-in):全双工该怎么剪

GPT-Live 全双工,音频比播放快,媒体服务器可能攥着几秒模型已经放弃的语音——用户压过 avatar 时,那个队列就是还在说的东西。session.ts 的处理很细,值得逐条留底:

  • 不是每个用户 turn 都算打断。 "mm-hmm" 是 backchannel,模型会穿过它说下去。只看 turn 开口就清缓冲会把 avatar 切在半句——而且 GPT-Live 以为自己已经说完了剩下的,再也不回来。
  • 用户 turn 只启动一个 watch,不直接清。 grace 期(YIELD_GRACE_MS 600ms)后,只在模型确实停止产音频时才清缓冲:静默 ≥350ms(YIELD_QUIET_MS)且 ≤6s(YIELD_STALE_MS,过了就没什么还在放了)。中断冷却 1s(INTERRUPT_COOLDOWN_MS),防一个 turn 投影切 avatar 两次。
  • 代码注释给的实测:GPT-Live 被真打断时自己 yield,测量约 420ms。
  • 清了缓冲就告诉浏览器 interrupted,让转录反映"后半句没被听到"。

对应第 25 期"中途插话"那张图:那个 session.append 三通道(instructions/thinking/commentary + "不改后端")的机制,在这个仓库里没有用来做中途插话注入。真正的"中途插话"在这里是用户音频自然打断,靠 turn 投影 + 媒体服务器清缓冲处理,不靠 append 注入指令。三通道 append 被用在了更保守的地方——下一节讲。

八、三通道 append 与 speak-first:打招呼得这么发

v3 给 live 会话灌文本有三种 append,语义不同,代码注释讲清了:

  • instructions:要模型服从的指令(先开口、签到、把这轮交给后端)。OpenAI 测过的"先开口"路径就走这个。
  • commentary:要模型说出口的信息,会转述。
  • thinking:静默上下文,模型以后可能用。注意:v2 里那个静默的 channel: "commentary" 在 v3 映射到这里(thinking),不是 commentary——按词义映射,否则会把本该静默的进度文字念出来。

三通道都吃一个纯字符串(≤500 token)和一个必填的 delegation_id(null 表示一般会话上下文)。

开场白走的是 OpenAI 测过的 v3 路径:一条 session.instructions.append(delegation_id null)既带"立刻先开口"指令又带开场词,不是 commentary。GREETING_PREAMBLE 原文:"The session just started. The user is listening but has not spoken yet. Immediately speak first to open the conversation; do not wait for the user to speak……" 注释给的实测数字:500/500 会话先开口。关键在于 response.create 在这个 API 里是后端命令(启动/继续委托工作),绝不启动一轮语音 turn——所以"先开口"只能靠 instructions append。空 greeting.md 是特性不是 bug:意思是"别说,让用户先开口"。

三通道 append 在这个仓库还被用在两个保守的地方:静默签到(12s 没人说话就 append 一条 instructions 催模型"你现在就开口")和复习触发(每教 4 个新词,在 turn 边界 append 一条 instructions 让模型"做完当前交换再宣布复习、把这轮交给后端")。注意——这两个都走 instructions(要服从的指令),不是 commentary(要转述的信息)。仓库刻意避免中途 append 来调节奏,因为 append 落下来是新上下文模型会立刻执行,会打断它正在跑的练习循环("再说一遍こんにちは"变成"好,再见是さようなら",练习被切在半词)。

九、服务器侧状态:模型输出不可信,词表别交给模型

两条铁律,贯穿 tools.ts 和 session.ts:

  • 模型输出不可信。 dispatcher(tools.ts)对长度做 clamp(term≤60、reading≤80、meaning≤120、title≤60),客户端只用 textContent 渲染(防注入)。
  • 复习词表是服务器状态,不是模型记忆。 每张 show_term_card 推出去的词,服务端在会话上记一份(按 term 去重,按教学顺序)。show_learned_words 从这个 store 渲染——模型只给标题,工具结果把面板上确切的词回传,模型不能记错、编造或漏词。状态寿命 = 会话寿命。
  • staging 是 per-widget、客户端决定,绝不是工具参数。 term_card 是全帧 avatar 上的下三分之一;learned_words 给 stage 设 data-pip,把 avatar 缩到右下角。把布局挡在工具 schema 之外,既不让模型跟产品吵布局,又把 schema 压到只剩内容。

还有一个设计呼应第五节:已知生词卡服务端推,不靠模型委托。 教案(LESSON_WORDS)里的词,服务端监听转录,听到模型说出那个词就自己把卡推上去——因为模型对"教 hello"这种它自己能力内的事不会委托。这是把"callable ≠ called"那条实测结论直接变成了代码策略。

十、会话生命周期 + 与第 25 期架构图的交叉印证 + 落地

会话生命周期几条要记:/api/session/start 一调就计费,活在单进程内存里,重启即丢(退出时上游会 stop);哪条腿(GPT-Live / 媒体服务器)先退就结束会话——"单腿会话是一张没人听的账单";浏览器断开立即结束,60s 空闲超时(mic 帧是唯一存活信号)+ 10min 上限是兜底;拆解顺序 GPT-Live 先 session.close,它的 drain 还会把最后几个字送进媒体腿然后媒体腿才关——顺序反了会切词在半句。

这个仓库是第 25 期那套 GPT-Live-1 架构图最小可读的活样本,几乎逐条坐实:

第 25 期讲的 本仓库的印证
前后端分离:live 管对话,后端管推理+工具 live=gpt-live-1、后端=gpt-5.4-nano,delegation.type="responses"
Responses 委托模式 delegation.responses.{model,tools,tool_choice,parallel_tool_calls} 在 session.start 里写死
session.append 三通道中途插话 三通道(instructions/commentary/thinking)逐字核验;但本仓库把 append 用于开场白/签到/复习,中途插话靠自然打断+清缓冲
工具调用→委托→结果→确认 response.item.create(function_call_output)+ response.create(continue),逐行实现
无 turn 事件,要自己投影 turns.ts 从 transcript delta 投影 turn,TURN_GAP_MS=1500
v3 音频无时间线 arrival IS timing,按到达顺序转发

本仓库新增、第 25 期没有的七条事实:

  1. 后端模型名坐实为 gpt-5.4-nano——第 25 期只敢写"≈GPT-5.4 系列"的推断,这里写死。
  2. "callable ≠ called"——委托按能力缺口触发,不按散文(实测 backend_model_usage: [])。
  3. speak-first 走 instructions.append,500/500 会话先开口(OpenAI 测过)。
  4. GPT-Live 被真打断时自己 yield ≈420ms(实测)。
  5. v3 把 v2 的 channel:"commentary" 映射到 thinking,不是 commentary。
  6. 没答的工具调用会冻住后续所有委托(OpenAI 确认的 frozen-delegation bug)。
  7. 自定义音色必须以 {id} 发,裸字符串留给命名音色(marin/cedar……)。

给想用 GPT-Live-1 做产品的人,落地启示六条:

  1. 把数字人当纯音频→脸渲染器,别强行造 turn 边界。 turn-based 协议(speak/speak_end/interrupt)和全双工模型天然不咬合;喂一条永不结束的连续流、模型自己 yield,反而最简单、最不丢词。
  2. 工具调用必须"结果 + continue"配对发,且每条路径都发(含失败)。 漏一个就冻住后续所有委托——这是 v3 最大的隐藏陷阱。
  3. 别用散文骗模型委托它能力内的事。 "教这个词时调工具"不会触发;把已知视觉走服务端推,只把真正的能力缺口(查新词/翻译/外部信息)留给委托。
  4. 后端回复文本会自动被 live 朗读——编排器不要再放一遍;同时后端必须"答话+调工具"同一条回复,否则 avatar 沉默。
  5. staging 挡在 schema 之外、词表挡在模型之外、模型输出全部 clamp + textContent——把不可信的边界划清楚。
  6. LITE 模式让服务端直灌音频、浏览器只看 LiveKit,既省往返又让浏览器不持 key。如果只是浏览器驱动集成,LiveAvatar web SDK 也行(speakAudioChunk()),代价是语音走浏览器。
